# 正文抓取单机提效探讨：协程 / 并发及其它模式

**文档编号**：26091802  
**类型**：独立探讨（非落地设计定稿）  
**关联**：`26091801-正文任务域名打散调度方案.md`（认领打散 + Frontier 已落地）  
**目标**：在**礼貌抓取（同站间隔）不放松**的前提下，讨论单机如何把墙钟时间压下来。

---

## 1. 现状瓶颈（为何「已经打散」仍偏慢）

当前链路（L2 / `radar_kb` unified）大致是：

```
FastAPI 事件循环
    └── daemon 线程 TaskScheduler.run_forever()   ← 同步 while True
            └── 每次只 execute 1 条正文
                    └── NewsHtmlContentExecutor.execute()
                            └── asyncio.run(_execute_async)   ← 每任务新建/跑完一个 loop
                                    ├── httpx 抓正文
                                    └── embedding 写向量
```

| 点 | 含义 |
|----|------|
| **串行** | 全机同一时刻只有 1 条正文在飞 |
| **打散只改顺序** | 换站减少「干等同站 gap」，吞吐仍 ≈ `1 / 单条耗时` |
| **每任务 `asyncio.run`** | 异步能力没用在「多任务重叠」上，只包了一层 IO |
| **与 API 同进程** | 调度在独立线程，一般不堵 uvicorn；但 CPU（切分/JSON）仍共享 |

实测量级（见同日日志）：约 **3.5～4.5s/条** → **~15 条/分钟** → 三千级积压约 **数小时**。

墙钟时间主要花在：

1. HTTP 下载等待  
2. Embedding HTTP 等待  
3. （偶发）Agent 兜底更长  

这些都是 **IO 等待**，理论上非常适合用**有界并发**叠起来——前提是**同站仍限速**。

---

## 2. 提效原则（先定约束，再谈模式）

1. **同站礼貌硬约束**：同一 `source_url_id`（或 host）并发 ≤1，且间隔 ≥ 配置 gap（你们已有 Frontier gap + `SiteRateLimiter`）。  
2. **跨站可重叠**：不同站的「下载+embedding」可以同时进行。  
3. **有界并发**：全局同时 in-flight 条数有上限（如 8～32），防打爆本机 FD / 代理 / embedding 配额。  
4. **崩溃可恢复**：RUNNING 租约 + 超时回收（已有 stale reset）必须保留。  
5. **不拖垮 FastAPI**：正文并发不要和请求循环抢同一事件循环到饿死；或独立进程跑 worker。

---

## 3. 可选升级路线

### 方案 A：同线程 asyncio 有界并发（「协程池」）— 优先探讨

**形态**：调度从「同步串行」改为「async 主循环 + `asyncio.Semaphore(N)` + 每站一把锁/队列」。

```
async content_loop:
  refill Frontier / fair claim
  while True:
    task = await frontier.pop_ready_async()   # 等到有「已冷却站」的任务
    await global_sem.acquire()
    asyncio.create_task(run_one(task))        # 不 await，允许多任务重叠

async run_one(task):
  try:
    async with per_site_lock[key]:            # 同站互斥
      await site_limiter.acquire(key)
      result = await fetch_and_embed(task)    # 真正的 async httpx，禁止 asyncio.run
      await finish_db(task, result)
  finally:
    global_sem.release()
    frontier.mark_fetched(key)
```

**优点**

- 单机、单进程即可；与现有 `async` 抓取/限速代码最贴。  
- 跨站吞吐可接近 `min(N, 活跃站点数) / 单条耗时`。  
- 同站仍串行+间隔，防封模型与现在一致。

**代价 / 坑**

- 必须拆掉 `asyncio.run`（嵌套 loop、每任务重建客户端都是反模式）。  
- `TaskScheduler` 现跑在 **threading 线程**里：要么  
  - 该线程 `asyncio.run(content_main())` 只跑正文并发；发现仍同步；或  
  - 整段 radar_kb 改成一个 asyncio 任务挂到 FastAPI lifespan（注意别堵 HTTP）。  
- pymysql 同步写库要 `asyncio.to_thread` 或改 async 驱动，避免堵事件循环。  
- embedding 若有 QPS 限，要**单独信号量**（例如全局 embed ≤4）。

**粗算加速**（假设单条 4s，同站 gap 不影响跨站）：

| 全局并发 N | 理论量级（理想） | 说明 |
|------------|------------------|------|
| 1（现状） | ~15/min | 基线 |
| 4 | ~60/min | 常见「稳妥」起点 |
| 8 | ~120/min | 站点数够多时 |
| 16+ | 继续涨，但易触 embedding/代理墙 | 需压测 |

若积压 2800 条：N=1 ≈3h；N=8 理想可到 **~20–30 分钟**（实际打七折更现实）。

---

### 方案 B：多线程 / 线程池 Worker

**形态**：主线程只 claim + 入队；`ThreadPoolExecutor(max_workers=N)` 跑 `execute`。

**优点**：改动面可以较小（仍调用现有同步 `execute`）。  
**缺点**：

- 每线程若继续 `asyncio.run`，开销大且连接池难共享。  
- 同站限速要**跨线程安全**（现有 `SiteRateLimiter` 是 asyncio.Lock，线程场景要换成 threading 锁或统一走 async）。  
- GIL 对纯 IO 影响不大，但对「线程数 × Agent」内存更高。

适合作为「过渡」：N=2～4 试水；长期仍建议 A。

---

### 方案 C：多进程（独立 `python -m radar_kb content` × K）

**形态**：K 个进程，各自 fair claim + `SKIP LOCKED`，各跑串行或各自小并发。

**优点**

- 与 API 进程隔离，reload 不互相拖死。  
- 崩溃面隔离；水平扩展直观。  

**缺点**

- 同站限速是**进程内**的：K 个进程打同一站 ≈ 间隔 ÷K，防封变差 → 需 Redis/DB 共享 `last_fetch_at`，或 **按 `source_url_id` 一致性哈希到固定进程**。  
- 运维比协程池重。

**建议**：多机/多核且要隔离时用；单机优先 A，必要时「1 个 content 进程 + 协程并发」。

---

### 方案 D：管道并行（抓取 ∥ 向量化）

即使全局仍串行「任务」，也可：

```
download(task_i) → queue → embed(task_{i-1})
```

双缓冲：下载下一篇时 embedding 上一篇。

**加速有限**（通常 &lt;2×），但实现比全并发简单，可作 A 的前置小步。

---

### 方案 E：外部队列（Redis / SQS）+ 专用 consumer

认领打散后推入 Redis list/stream；多 consumer async 消费。

**优点**：模式成熟、易扩缩。  
**缺点**：多组件；与「先吃干 MySQL 队列」目标不完全一致。本仓库短期非必须。

## 4. 和现有 Frontier / 分组认领的关系

| 已有能力 | 并发升级后怎么用 |
|----------|------------------|
| 按站 fair claim | 继续用：保证内存里多站库存 |
| ContentFrontier + gap | 升级为「每站异步队列 + next_allowed」；`pop_ready` 变为 await |
| SiteRateLimiter 单例 | 必须保留，并在**真正发 HTTP 前** acquire |
| 发现优先 / 让路 | 并发池可「发现时段暂停新正文 task」或降低 N |

**不要**为了提速取消同站 gap；提速应来自**跨站重叠**。

---

## 5. 推荐演进路径（探讨结论）

```
阶段 0（已完成）
  串行 + 分组认领 + Frontier 换站

阶段 1（小步，可选）
  管道：download ∥ embed；去掉无意义的 asyncio.run 嵌套浪费
  预期：~1.3～1.8×

阶段 2（主推）
  单进程 asyncio 有界并发 N=4～8 + 每站串行
  预期：~3～6×（站点数 ≥ N 时）
  配置：CONTENT_GLOBAL_CONCURRENCY / 沿用 SAME_KEY_GAP

阶段 3（按需）
  独立 content 进程；或多进程 + 按站哈希分片 + 共享限速
```

**不建议**：无界地 `create_task` 上千；多 uvicorn worker 各跑一套 radar_kb 却不共享限速。

## 6. 风险清单

| 风险 | 缓解 |
|------|------|
| 目标站仍封禁 | 每站并发=1 + gap；403 熔断（已有 Agent 闸门可扩展） |
| Embedding 429 | 独立 embed 信号量 / 重试退避 |
| FastAPI 卡顿 | content 独立 asyncio loop 线程，或独立进程 |
| RUNNING 堆积（reload） | 缩短 stale；进程退出 release 本 worker 锁 |
| 调试变难 | 日志带 `in_flight=`、`site=`、`sem=` |

## 7. 若落地阶段 2，接口草图（仅示意）

```text
RADAR_KB_CONTENT_GLOBAL_CONCURRENCY=8
RADAR_KB_CONTENT_EMBED_CONCURRENCY=4
RADAR_KB_CONTENT_SAME_KEY_GAP_MIN_SEC=5   # 保持
```

伪代码级验收：

1. 同 `source_url_id` 相邻两次 HTTP 间隔 ≥ gap。  
2. 全局 in-flight ≤ N。  
3. 多站积压时，吞吐相对串行 ≥ 3×（压测 10 分钟）。  
4. kill -9 后 stale 回收，无永久卡死。

---

## 8. 总结

- **可以**用协程（asyncio 有界并发）让单机更高效；本质是 **跨站 IO 重叠**，不是取消礼貌间隔。  
- 多线程/多进程也能做，但要么为过渡，要么要解决**跨进程同站限速**。  
- 与当前「分组认领 + Frontier」不冲突，反而是并发版调度的库存基础。  
- 性价比最高的下一步：**去掉每任务 `asyncio.run`，上 N=4～8 的 async worker 池 + 每站互斥**。
