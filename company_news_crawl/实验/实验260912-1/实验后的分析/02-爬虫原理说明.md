# 爬虫原理说明（面向产品/方案讨论）

## 一句话

借助经验写的 **规则式 Python 脚本**：HTTP 下载页面 → 启发式从列表找详情链接 → 再用写死的 DOM 规则 + 通用正文库抽标题/日期/正文。不是按公司定制爬虫，也不是让大模型理解页面。

## 两段式流程

```
种子 news_list_url
  → GET 列表 HTML
  → 从 <a href> 池中过滤出候选详情 URL
  → 截断前 N 条
  → 逐个 GET 详情 HTML
  → 抽 title / published_at / content_text
  → 写 JSONL（默认不连库）
```

## 列表 URL → 每篇公告 URL：怎么找到的？

1. 下载列表页整页 HTML  
2. 收集所有 `<a href>`，拼成绝对地址  
3. 通用过滤（经验规则）：
   - 优先同域名
   - 路径含 news / xinwen / detail / article / gsxw 等更优先
   - 排除 login / 静态资源等
4. 去重、排序，取前 N 条

**不是**先知道公告 ID 列表，而是把列表页当链接池来捞。  
因此：门户/卡片页会把产品、酒店、导航一并捞进来；**默认不翻页**（静态 `index_N` 或 JS 下一页都不会跟）。  
列表锚文本里常有日期+标题，但当前实现基本 **只用 href，不用锚文本填字段**。

## 拿到详情 URL 后如何解析？是否写死规则？

**是写死的通用规则 + 通用正文库**：

| 字段 | 做法 |
|------|------|
| 标题 | 优先第一个 `h1` → class/id 含 title → `<title>` |
| 日期 | 只认 `time[datetime]`、class/id 含 date/time 等节点内的日期文本 |
| 正文 | 优先 trafilatura（启发式主内容抽取）；失败再找 `.content` / `article` / `main` |

没有每家公司专用 parser，也没有 LLM 参与抽取。  
优点：快、可控、好部署；缺点：DOM 稍不规范就漏字段或抓脏（见日期缺失分析）。

## 和「Agent 爬取」的区别

| | 当前 MVP | Agent 化（讨论中的目标形态） |
|--|----------|------------------------------|
| 决策 | 固定规则 | 失败时由模型选策略/修字段 |
| 成本 | 低 | 仅难例升高 |
| 确定性 | 高 | 需 schema/校验约束 |
