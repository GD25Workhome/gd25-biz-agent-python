# 巨潮 PDF 下载失败 — 升级方案简介

> 日期：2026-09-16  
> 背景：`radar_crawl` 阶段 B 对 `static.cninfo.com.cn` PDF 出现批量 403；浏览器打开同 URL 正常。  
> 详细排查记录见：`ai_docs/26091608-巨潮PDF下载403问题小结.md`  
>  
> **进展（同日）**：根因已实证为 WAF 按 **TLS 指纹（JA3/JA4）** 拦截非浏览器客户端，而非单纯 IP 拉黑。  
> `radar_crawl/adapters/cninfo.py` 已改为 `curl_cffi` + `impersonate="chrome"`，同机可恢复下载。下文保留原分层方案，便于对照后续风险。

---

## 1. 目标

在不大改业务语义（列表入库 → PDF 抽字 → 回写 `radar_raw_document`）的前提下：

1. **恢复**被 403 卡住的正文回填能力；
2. **降低**再次触发静态站风控的概率；
3. 为偶发失败留一条**轻量旁路**，避免把 Claude Agent SDK 当成批量下载器。

---

## 2. 总体思路：分层下载，而非 Agent 主路径

```text
主路径（默认）
  强化客户端下载 PDF（现为 curl_cffi 仿 Chrome TLS）→ pypdf 抽字 → 写库

失败且可重试（如 403 / 5xx / 超时）
  ↓
旁路 A：浏览器态下载（Playwright）或核对指纹版本 / 代理出口
  → 仍抽字 → 写库

仍失败（少量）
  ↓
旁路 B（可选）：人工排查 / 云上 Worker 重跑
  或 极少条用 Agent+浏览器辅助（不当日频主力）

永久失败（扫描件无字等）
  → 保持 fetch_status=2，记录 pdf_error，不盲重试
```

原则：**下载问题用下载手段解**；Agent 只适合「抽字段/修 HTML」类不确定性，不适合替代附件拉取。

---

## 3. 升级项简介

### P0 — 客户端升级（优先；已用 curl_cffi 落地）

| 项 | 说明 |
|----|------|
| 改动点 | `radar_crawl/adapters/cninfo.py` 的 Session / `download_and_extract_text`；由 `pdf_fill_worker` 调用 |
| 做法 | 用 `curl_cffi.requests.Session(impersonate="chrome")` 仿真浏览器 TLS 指纹；必要时再对顽固 403 降级 Playwright |
| 为何 | 「网页能开、脚本 403」常见差在 TLS 指纹，而非 URL 无效 |
| 产出 | `pypdf` 抽字与落库逻辑不变，只换「拿到 bytes」的方式 |

### P0 — 出口与限速（仍建议保留）

| 项 | 说明 |
|----|------|
| 云上/K8s 跑 pdf Worker | 生产出口与办公网隔离；已有 `deploy/k8s/radar-crawl.yaml` |
| 显式代理开关 | 需要时支持环境变量配置合法 HTTP(S) 代理（当前适配器仍默认清系统代理） |
| 降并发 / 加间隔 | 如控制 `RADAR_PDF_CONCURRENCY`、加大请求间隔，降低行为层风控 |

### P1 — 失败分类与可重试

| 项 | 说明 |
|----|------|
| 可重试 | `403` / 超时 / `5xx` → 带退避重试，勿狂刷 |
| 不可重试 | `pdf_text_empty`（扫描件）、`not_pdf` → 维持失败，可后续接 OCR 专题 |
| 运维 | 提供「按 `pdf_error` LIKE 403% 重置 `fetch_status=0`」的受控 SQL/脚本 |

### P2 — Agent 兜底（明确边界）

| 项 | 说明 |
|----|------|
| **不做** | 每条 403 都拉起 Claude Agent SDK 批量下 PDF |
| **可做** | 仅对旁路 A 仍失败、且业务急需的**极少数**单据，用 Agent + 浏览器工具辅助 |
| 结论 | Agent 是可选保险丝，不是本问题的主升级项 |

### P3 — 长期数据源（可选）

评估深证信官方数据 API / 交易所镜像，降低对裸爬 `static.cninfo.com.cn` 的依赖。

---

## 4. 建议落地顺序

1. ~~验证换出口~~ / **换 TLS 客户端（已完成）** → 重置失败单重跑（止血）。  
2. 生产镜像重装依赖（`curl_cffi`）并控制并发。  
3. 失败原因枚举、可重试标记、连续 403 告警暂停。  
4. 评估官方 API；Agent 仅按需试点。

---

## 5. 非目标

- IP 欺骗 / 恶意绕过 WAF  
- 用登录态「假装」解决 TLS 指纹拦截  
- 用 Claude Agent SDK 替换 `pdf_fill_worker` 日频批量任务  

---

## 6. 大量下载是否还会被封？

**会有风险，但机制不同。**

| 层级 | 含义 | 指纹修复后是否还在 |
|------|------|--------------------|
| TLS / 客户端识别 | 「你是不是脚本」 | 已被 `curl_cffi` 大幅缓解 |
| 行为 / 频率 | 「短时间下了多少、多快」 | **仍在**，与像不像浏览器无关 |
| IP 信誉 | 异常流量后对出口降权或封禁 | **可能出现**（高频、无退避时） |

因此：

- **中小批量**（当前雷达日频、并发 1～3、有间隔）：通常可接受，接近正常人浏览量级。  
- **短时猛刷**（例如一次重置几百条、高并发无间隔）：即使指纹正确，仍可能触发限流、二次验证，甚至升级为 IP 级限制。  
- **建议**：重置历史失败单时 **低并发 + 间隔**；生产保持 `RADAR_PDF_CONCURRENCY` 保守；若再出现 403，先区分是指纹失效还是频率封禁（同机浏览器能否打开可作对照）。

---

## 7. 一句话

**先用仿浏览器 TLS（`curl_cffi`）过客户端门禁，再用限速与失败分类管住行为层；大量下载仍可能被频率风控，Agent 不作 PDF 下载主力。**
