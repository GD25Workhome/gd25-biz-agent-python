# 区域解析到区 —— 决策记录

> **状态（2026-10-20）**：决策已落地。本文保留决策过程与坑；当前实现口径以 `华院Agent设计/02-技术设计/02-评分、自检与落库规则.md` 与代码为准。文中“待裁定 / 未实现 / 讨论稿”等措辞如与代码冲突，以代码为准。

> 定位：解释缺陷 3「区域只解析到市级」**为何只改了一半**，并把「怎么改到位」固化成设计。
> 关联：原缺陷与修复记录已删除（见 git 历史）；`261020-01-商机发现与事件归族.md`（同风格）。

## 1. 要解决的问题（上推一层）

**现象**：展厅明明在「北京市朝阳区」，落库却归到「北京市」（`region_source=COMPANY_INHERITED`）；需求 13 的「展厅所在区域」**按区筛不到**。

**后果**：地域筛选/统计在**区级失效**；同城多个展厅被并到同一个"市"。

**本质**：`place` 是**自由文本**（"北京市朝阳区" / "重庆经开区东港片区" / "美国旧金山"），
而 `region` 字典是**结构化层级**（国家→省→市→区）——中间缺一层**确定性的「文本 → 层级」解析**。

---

## 2. 目标 / 非目标

**目标**
1. 国内地址解析到**最细可用层级**（区/县）；直辖市至少到区。
2. 国外能识别**国家** + `is_domestic=0`。
3. 解析退化要**可发现**（不静默变成市级）。

**非目标**
- 不做地理解析/经纬度/地址补全；
- 不改 `region` 字典数据；
- **不依赖 LLM 猜行政区划**（模型最多做消歧/外语名辅助）。

---

## 3. 现状：改到哪一步（**为什么"只改了一半"**）

> 图例：✅ 已做 / ❌ 未做。

### 3.1 已做的一半 —— **把"解析"交给 Agent（工具）** ✅

- 新增工具 `backend/domain/tools/region_lookup_tool.py`：`region_lookup(keyword, parent, limit)` / `region_children(region, limit)`，只读 `region` / `region_alias`，逐级下钻、同名可 `parent` 消歧、国内外用 `is_domestic`。
- 接线：`tools/__init__.py` 注册；v3 `flow.yaml` 的 `tools` 加入；`RadarEventScoreResult` 新增 `place_region_id`（容错）；`region_resolve.resolve_event_region(..., place_region_id=)` **优先采用**该 id（`AI_PARSED`）；`execute.py` 传入。
- 提示词：加「**展厅所在区域（必做）**」步骤 + `place_region_id` 输出字段 + 自检行（`place` 是中文地名而 `place_region_id` 为空 → 补查）。

### 3.2 代码侧兜底 **B** —— ✅ 已做（261020）

- `radar_score/region_resolve.py` **仍只有**「整串：编码精确 → 名称精确 → 别名 → 名称模糊 → 别名模糊」。
  → `"北京市朝阳区"` 整串在 `region` 表里**不存在**（表里是"朝阳区"），模糊 `LIKE '%北京市朝阳区%'` 也命中不到 → **退化**成"继承企业城市"（市级 110100）。
- 提示词的那个自检行是**模型自己执行**的（不可靠），**代码里没有硬兜底**。
- 也没有"解析可疑"告警。

### 3.3 实测（261019 晚重跑）

| 项 | 结果 |
|---|---|
| 工具本身 | ✅ `朝阳区 + parent=北京市 → 110105`；`region_children(110100) → 东城/西城/朝阳/丰台…`；`旧金山 → is_domestic=0` |
| 模型是否调用 | ❌ **没调用** → `place_region_id` 为 `null` |
| 最终落库 | ❌ 仍是 `region_source=COMPANY_INHERITED`、市级 |

**结论**：工具没问题，**问题在"把确定性映射交给了模型自觉"**。

### 3.4 A 侧"补齐"（261020，已修）

排查提示词与解析链路时又发现一个**真 bug** —— 说明 A 这一半此前**其实也没走通**：

| 问题 | 说明 | 修复（261020） |
|---|---|---|
| **路由没解析 `place_region_id`** | `parse_radar_event_score_from_obj` 的显式构造里**没有** `place_region_id` → 模型就算填了也被丢（schema 默认 None） | 解析层补 `place_region_id=_parse_optional_int(...)` |
| 示例 JSON 过时 | 示例仍是**单对象**、且**不含 `place_region_id` / `event_name` / `event_relation` 等新字段** → 模型照抄示例就漏字段 | 换成 **`radar_event_scores` 数组**示例，含 `place_region_id` 与顶层共享 `evidences` |
| 区域步骤位置错 | 放在「推荐检索序列（至少覆盖 3–5 条）」**第 7 位** → 模型按 3–5 条收工就走不到 | 独立成「**输出前必做：确定展厅所在区域**」（每条事件都做） |
| 自检太软 | "未用 region 工具核实 → 补查；确查不到才留空" 给了台阶 | 改为"**未完成**：必须先 `region_lookup`；确认查不到才留空，并在 `score_reason` 注明" |
| 共享证据未被解析 | 提示词说 `evidences` 整轮共享，但解析层按元素取 → 会触发"有分必有据"失败 | 解析层把顶层 `evidences` / `discarded` **注入缺省元素** |

> 结论：A 已补齐（**但仍以 B 为准** —— 提示词只提高调用率，不能保证）。

## 4. 根因：为什么"交给模型"这一半不够

| 方案 | 谁决定 | 可靠性 | 实测 |
|---|---|---|---|
| **A. 工具（模型主动调用）** | 模型 | **概率性**（可能不调 / 调错 / 调了不填） | ❌ 没调 |
| **B. 代码兜底（分段切分）** | 代码 | **确定性** | 未做 |

- 「`place` → 区县」本质是**查字典 + 字符串切分**，是**确定性**问题，不该依赖模型自觉；
- 模型可以**辅助**（同名区消歧、外语译名），但**必须有代码兜底**——这与 `261020-01` 里"确定性的算术/字典放代码、语义判断放 Agent"是同一条原则。

## 5. 要实现的逻辑（以 B 为主，A 保留为辅助）

### 5.1 代码兜底：分段切分（`region_resolve.py`）✅ 已实现（261020）

- **切词**：把 `place` 按行政区后缀切候选（省 / 市 / 区 / 县 / 新区 / 自治州…），如 `"北京市朝阳区" → ["北京市", "朝阳区"]`；
- **从最细到最粗**逐个 `resolve_region_by_text`，**取最细命中**（朝阳区 110105）；
- **兜底链**（改后顺序）：
  ① Agent 的 `place_region_id` → ② **分段切分（新）** → ③ 整串匹配（现状） → ④ 继承企业城市 → ⑤ `UNKNOWN`。
- **单测**：`北京市朝阳区 → 110105`、`上海 → 310000`、`重庆经开区东港片区 → 南岸区/经开区`、`美国旧金山 → 国家 + is_domestic=0`。

### 5.2 可发现性（补）

- 当 `region_source=COMPANY_INHERITED` 但 `place` 里**明显含区名**时，打一条「解析可疑」告警，便于发现同类漏解析。

### 5.3 提示词（保留 A，不删）

- 工具与"必做"步骤**保留**（做消歧/外语名/兜底确认）；**但不再把正确性押在它身上**。

## 10. 实施结果（261020，B 已落地）

**最终兜底链**（`resolve_event_region`，与 §5.1 提案略有精化）：

```
0. Agent 的 place_region_id                              → AI_PARSED
1. place 整串（编码/名称/别名/模糊，保持新旧口径一致）        → AI_PARSED
2. 分段切分：候选「从最细到最粗」，逐个解析 + 同名按上级消歧   → AI_PARSED   ← B 核心
3. 领先行政区：文本以「省/市名（去后缀）」开头 → 取该市        → AI_PARSED   ← 补（"重庆经开区…"→重庆市）
4. 国外：国家名是文本前缀                                  → AI_PARSED
5. 继承企业城市（place 含区/县 → 打「解析可疑」告警）          → COMPANY_INHERITED
6. 都失败                                                → UNKNOWN
```

**新增代码**（`radar_score/region_resolve.py`）：`_clean_place` / `_split_place_candidates` / `_filter_by_parents` / `_resolve_candidate` / `_resolve_by_splitting` / `_resolve_leading_admin` / `_resolve_country_prefix` / `_has_district_token`。

**真库实测（company=3182 北京）**：

| place | 结果 | 来源 |
|---|---|---|
| `北京市朝阳区` | **110105 朝阳区** | AI_PARSED ✅ |
| `上海` | 310000 上海市 | AI_PARSED ✅ |
| `重庆经开区东港片区（广滨三路）` | **500100 重庆市**（原为北京） | AI_PARSED ✅ |
| `美国旧金山` | 9000233 美国（domestic=0） | AI_PARSED ✅ |
| `朝阳区` | 110105 北京朝阳区 | AI_PARSED |
| `吉林省长春市朝阳区` | **220104 长春朝阳区**（消歧正确） | AI_PARSED ✅ |
| `杭州` | 330100 杭州市 | AI_PARSED ✅ |
| `某不存在的地名` | 继承企业（北京） | COMPANY_INHERITED |

**测试**：新增 `_clean_place` / `_split_place_candidates` / 分段消歧（北京→110105、长春→220104）/ `_has_district_token` 用例；相关 **113 passed**。

**与提案的差异**：① 把"整串"放在分段**之前**（精确更可信，模糊仍由它承担，保持新旧口径一致）；② 新增第 3 步「领先行政区」——否则 `重庆经开区东港片区` 只能切出"东港片区/重庆经开区"，命不中而白退到企业城市。
