> 本文只讲评分语义、自检、事件决策、区域解析与直写落库；HTTP / Flow 见 `01`，调度见 `03`。

## 1. 两维分、总分与等级

### 1.1 分值白名单

| 维度 | 合法值 |
|---|---|
| `evidence_score` | `85 / 75 / 55 / 45 / 25 / 5 / 0` |
| `specificity_score` | `15 / 10 / 5 / 0` |
| 历史兼容 | `evidence_score = 60 / 10` 放过但记录（v2 遗留） |

`total_score = evidence_score + specificity_score`（不另做加权）。

### 1.2 等级区间

| 总分 | 等级 |
|---|---|
| `>= 75` | S1 |
| `50–74` | S2 |
| `25–49` | S3 |
| `< 25` | S4 |

模型输出 `suggested_level` 只作建议；最终以区间推导为准（R3），并受 R4 / R5 / R6 封顶。

## 2. 落库前自检 `self_check.py`

入口：`radar_score.self_check.check(score, today=None) -> SelfCheckOutcome`

`SelfCheckOutcome`：

```text
ok: bool
level_final: S1|S2|S3|S4|None
cap_reason: str|None
notes: list[str]
dropped_evidence_nos: list[int]   # R9 剔除的证据序号
```

### 2.1 规则清单

| 规则 | 作用 |
|---|---|
| **R1 分值白名单** | 非法 `evidence_score` / `specificity_score` → `ok=False`，不落库 |
| **R2 有分必有据** | `total_score > 0` 时，kept 证据至少一条 web `http(s)` URL 或知识库 `doc_id`；否则 `ok=False` |
| **R3 建议等级一致性** | `suggested_level` 与区间推导不一致 → 以区间为准，记录 note |
| **R4 弱证据封顶** | `evidence_score <= 25` → 最高 S3 |
| **R5 固定 S4** | `evidence_score == 0` → S4 |
| **R6 潜在档封顶** | `is_potential=true` 或 `signal_category` 非空 → 最高 S3 |
| **R7 时效闸门** | 基准 = `fact_time_earliest`，缺失回退 `signal_time`；超出 12 个月滚动窗口 → 置 `expired_or_done=true`、分数/等级置 null |
| **R9 日期 / 来源纪律** | `publish_date == 跑批日` 或命中行情 / 聚合页抑制表 → 该条证据 `kept=false`，不整体判失败 |

> 当前实现是 **R1–R7 + R9**；R8 未在代码中落地。`rule_gate` 与 `self_check` 共用 `radar_score/rules/` 的同一套纯函数，避免图内 / 图外口径漂移。

### 2.2 R7 细节

- 窗口：评估日往回 `SIGNAL_VALIDITY_MONTHS`（默认 12）个月的**滚动窗口**；`validity_floor` 每次现算。
- 基准矛盾：`validity.basis_conflict(basis, evidences)` 发现「模型基准 vs 证据候选」差 >183 天时，**只检测、不自动改判**；把 `admission_hint` 改为 `pending_verify`，交人工核验。
- 超窗：`expired_or_done=true`、`admission_hint=expired`、`total_score/evidence_score/specificity_score/suggested_level` 全部 null；`ok=True` 但 `level_final=None`，后续 `decide_action` 会 NOOP，不落库。

### 2.3 R9 细节

- 日期纪律：`publish_date == 跑批日` 视为「跑批日戳」，剔除该条证据。
- 来源抑制：`radar_score/rules/sources.py` 对行情 / 聚合页 host / path 做抑制；公告 / 新闻 / cninfo 等豁免。
- 剔除只影响该条证据，不整体判失败；剔除序号写入 `dropped_evidence_nos` 与 `revision`。

## 3. 事件决策 `event_update.py`

**当前定稿：只插、不更、不关（INSERT / NOOP）。** `UPDATE` 已停用，`update_event()` 保留但不调用。

### 3.1 聚合键

```text
(space_object, place, procurement_scope)   # 同 company_id 内
```

`space_object` 为空时不做文本键匹配（避免把不同需求误并）。

### 3.2 决策矩阵

| 条件 | 决策 |
|---|---|
| 与展厅无关（`exhibition_related=false`） | **NOOP** |
| 已完成 / 失效（`expired_or_done=true`） | **NOOP**（不落库，也不写关闭） |
| 无匹配历史 | **INSERT**，`parent_event_id=NULL`（根） |
| 命中已发布（`published=1`） | **NOOP**（不覆盖发布态） |
| 命中已关闭 / 失效 / 已签署（`closed` / `opportunity_status ∈ {closed,signed}`） | **NOOP**（不复活） |
| 命中未发布、未关闭 | **INSERT**，`parent_event_id=root_event_id`（同商机时间线挂根） |

### 3.3 命中目标优先级

```text
1. Agent 指认 matched_event_id（必须 ∈ 本企业 history）
2. 文本键匹配 (space_object, place, procurement_scope)
   -> 多个候选：未失效优先 -> 总分降序 -> 最新（history 已按 update_time 倒序）
```

### 3.4 输出

```text
EventDecision(
  action: INSERT|NOOP,
  event_id: 命中的既有事件 id（NOOP / 审计也带）,
  reason: 决策原因,
  parent_event_id: INSERT 时的族根
)
```

## 4. 区域解析 `region_resolve.py`

入口：`resolve_event_region(conn, place, company, place_region_id=None) -> dict`

优先级：

```text
0. Agent 用 region 字典工具得到的 place_region_id 命中 -> AI_PARSED
1. place 整串命中（编码 / 名称精确 / 别名 / 模糊） -> AI_PARSED
2. place 分段切分（最细优先 + 同名消歧） -> AI_PARSED
3. 国外：国家名前缀命中 -> AI_PARSED
4. 继承企业默认城市 -> COMPANY_INHERITED
5. 都解析不到 -> 区域列留空，region_source=UNKNOWN
```

写出的列：`region_id` / `region_name` / `region_path_ids` / `country_id` / `is_domestic` / `region_source`。

保护规则：

- `region_source=MANUAL` 的事件，运营手工区域不被自动重算覆盖；当前只插不更，天然不会覆盖。
- `COMPANY_INHERITED` 含区名时打「解析可疑」告警，便于人工核验。

## 5. 直写落库 `radar_event_store.py`

### 5.1 事务边界

- `insert_event` / `replace_evidences` / `touch_latest_event` / `update_job_success` / `update_job_failed` **都不 commit**。
- `execute.run_event_end_to_end` 负责最终 `commit` 或 `rollback`；异常整体回滚。
- 单任务一事务：事件 / 证据 / 企业指针 / 任务状态要么全成功，要么全回滚。

### 5.2 `radar_event` 关键列

| 分组 | 列 |
|---|---|
| 关联 | `company_id`、`event_job_id`、`parent_event_id` |
| 事件 | `space_object`、`event_name`、`action`、`place`、`time_text`、`signal_summary`、`signal_time`、`signal_time_evidence_no`、`event_tags_json` |
| 准入 | `exhibition_related`、`subject_confidence`、`admission_hint`、`admission_pass`、`admission_reason` |
| 分数 | `evidence_score`、`specificity_score`、`total_score`、`score_reason`、`score_items_json` |
| 等级 / 状态 | `system_level`、`final_level`、`validity_status`、`verify_status`、`fact_status`、`expired_or_done`、`published` |
| v3 扩展 | `target_scope`、`suggested_level`、`suggested_level_reason`、`procurement_scope`、`event_stage`、`exhibition_stage`、`is_potential`、`signal_category`、`verify_priority_*`、`planned_time`、`expected_time`、`actual_time`、`date_precision` |
| 区域 | `region_id`、`region_name`、`region_path_ids`、`country_id`、`is_domestic`、`region_source` |
| 元信息 | `rule_version`、`agent_trace_id`、`creator`、`updater`、`create_time`、`update_time`、`tenant_id`、`deleted` |

写入前按 `_EVENT_MAX` / `_EVIDENCE_MAX` 截断，避免 MySQL 1406 整单回滚。

### 5.3 `radar_event_evidence`

| 列 | 说明 |
|---|---|
| `event_id` | 事件 id |
| `evidence_no` | 事件内稳定序号，从 0 起 |
| `source_type` | `web` / `knowledge_base`（当前 v3 基本为 web） |
| `doc_id` / `chunk_id` | 知识库字段，可为空 |
| `title` / `summary` / `quote` / `url` / `publish_date` / `source_host` | 证据内容 |
| `authority_tier` / `source_level` / `content_grade` | 权威档 / 来源级别 / 正文完整度 |
| `cite_reason` | 引用理由 |
| `kept` | 是否纳入计分 |

`replace_evidences` 按事件重建证据；`evidence_no` 必须连续、与 `score_items.evidence_nos` / `signal_time_evidence_no` 对齐。

### 5.4 企业指针

`touch_latest_event(conn, company_id, event_id)`：

- 只前移：`latest_event_id < event_id` 才写；
- NOOP 不动；
- 客户雷达列表 / 详情按 `radar_company.latest_event_id` JOIN 事件。

### 5.5 任务收口

- `update_job_success`：`status=2`、`event_id`（NOOP 可为 None）、`agent_trace_id`、`acp_raw_json`、`stats_json`、`revision_json`、`cost_ms`、清 `error_message` / 锁。
- `update_job_failed`：`status=3`、`error_message`（≤900）、清锁。
