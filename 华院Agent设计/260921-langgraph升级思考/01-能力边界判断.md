# 能力边界判断：新闻列表 Agent 能否用 langgraph 替代

**文档编号**：260921-01
**类型**：现状判断 / 可行性分析（非改造方案）
**对象**：`backend/domain/news_crawl/`（新闻 URL 列表发现 Agent）
**结论一句话**：**能替代，框架不是瓶颈。** 当前唯一的实质约束是 `claude` CLI 子进程这个运行时形态（这恰是 langgraph 的优势侧），以及一批**尚未启用**的 Agent SDK 独有能力。

---

## 0. 前提对齐：这是两套并存的技术栈

问"能不能用 langgraph 替代"，先要纠正一个常见误解——**这个 Agent 用的不是 langgraph**。

| | 新闻列表 Agent | langgraph 侧 |
|---|---|---|
| 位置 | `backend/domain/news_crawl/` | `backend/domain/flows/` |
| 框架 | Claude Agent SDK（`claude_agent_sdk`） | LangGraph（`StateGraph` + `create_agent`） |
| 形态 | **CLI 子进程** + 进程内 MCP server | 进程内协程，YAML → 图 |
| 工具协议 | MCP（`create_sdk_mcp_server`） | LangChain `BaseTool` |
| 循环 | SDK 内部 tool-use 循环 | `create_agent` 的 ReAct 图 |

两套东西在同一个仓库里并行跑，所以"替代"是一个真实的架构选择，不是概念混淆。

---

## 1. 结论先行：这个 Agent 用到的能力，langgraph 一项都不缺

原因不是 langgraph 强，而是这个 Agent 被**刻意收窄了能力边界**。

`backend/domain/news_crawl/agent_runner.py:168-184` 里写死了：

```python
disallowed_tools=["Bash", "WebFetch", "WebSearch", "Read", "Write", "Edit"],
skills=[],
setting_sources=[],
```

无 session 记忆、无子 Agent、无文件系统、无内置工具。**Claude Agent SDK 那些"独有能力"，它一个都没启用。**

### 逐项对照

| 这个 Agent 实际用到的能力 | 当前靠谁实现 | langgraph 有对应物吗 |
|---|---|---|
| 模型自主的 tool-use 循环<br>（读清单→挑链接→记录→翻页→提交） | SDK 内部循环<br>`agent_runner.py:196-210` | ✅ `create_agent`，本项目 `backend/domain/agents/factory.py:213` **已在用** |
| 4 个自定义工具<br>（fetch_list_page / record_news_urls / get_state / save_results） | `@tool` + `create_sdk_mcp_server`<br>`crawl_tools.py:540-544` | ✅ 改成 `StructuredTool`，语义等价 |
| 工具返回值引导循环<br>（`pages_remaining` / `hint` / `pagination_stopped`） | 纯 Python，在工具里<br>`crawl_tools.py:309-310`、`:324-333` | ✅ 框架无关，原样搬 |
| 反幻觉校验（只能记录抓过的候选） | `CrawlStore.fetched_candidates`<br>`crawl_tools.py:435-456` | ✅ 框架无关 |
| 去重、已知 URL 过滤、硬停 | `CrawlStore` 纯 Python | ✅ 框架无关 |
| HTTP + HTML 清洗（`simplify_list_html`） | httpx + bs4<br>`crawl_tools.py:156-214` | ✅ 框架无关 |
| 凭证 / 配置隔离 | `CLAUDE_CONFIG_DIR` + `setting_sources=[]` | ✅ 走 `config/model_providers.yaml` 的 provider，天然隔离 |
| **模型** | 网关 `deepseek/deepseek-v4.1-flash` | ✅ **同一个模型** |

最后一行是决定性的。

### 1.1 模型不必换，所以"辨识力会退化"不成立

- 抓新闻 Agent：`.env.example:29` → `ANTHROPIC_MODEL=deepseek/deepseek-v4.1-flash`
- langgraph 侧：`config/model_providers.yaml` 的 `huayuan` provider → base_url `https://ai-api.unidtai.com/openapi/llm/compatible-mode/v1`，`default_model: "deepseek/deepseek-v4.1-flash"`

**同一个网关、同一个模型。** 只是协议不同（Anthropic 兼容端点 vs OpenAI 兼容端点，见 `backend/infrastructure/llm/client.py` 用 `ChatOpenAI`）。

所以要区分清楚：`company_claude_cral/00-结论摘要.md` §1.2 说的"Agent 的增量价值是辨识与定界"，那个增量来自**模型**，不来自框架。框架换了、模型不换，辨识力就在。

### 1.2 耦合面很小

`crawl_tools.py` 562 行里，SDK 耦合的部分只有 `@tool` 装饰器 + `create_sdk_mcp_server` 调用，**约 20 行**。主体（`simplify_list_html`、`normalize_url`、`CrawlStore`、反幻觉校验）是纯 Python，可整段复用。

---

## 2. 真正"替代不了"的，是这个 Agent 没用的那部分

Agent SDK 确实独有、langgraph 没有对应物的能力：

| Agent SDK 独有能力 | 本 Agent 是否启用 | 替代后的影响 |
|---|---|---|
| 子 Agent（Task 工具） | ❌ `skills=[]`、无 | 无 |
| Skills | ❌ 显式关闭 | 无 |
| 内置工具生态<br>（Bash/Read/Write/WebFetch/WebSearch/Grep…） | ❌ `disallowed_tools` 全禁 | 无 |
| 自动上下文压缩（compaction） | ⚠️ **隐式生效** | **有影响，见 §3.1** |
| hooks | ❌ 未用 | 无 |
| CLI 层权限模式（`bypassPermissions`） | ✅ 在用 | 需换成图内授权模型 |
| 外部 MCP server 即插即用 | ❌ 只用进程内自建 server | 无 |

**这张表是"Agent SDK 的能力上限"所在，但当前 Agent 明确把这些全关了。** 所以结论是：限制存在，只是没被触发。真正的"不能用 langgraph 替代"要等到你需要子 Agent 分工或 Skills 复用那天才成立。

> ⚠️ 注意 compaction 是个例外：它不是显式开关，而是 CLI 在长上下文时自动做的。换到 langgraph 后这一层消失，必须自己补——这正是 §3.1。

---

## 3. 换过去要重建的 4 件事（其中 1 件是变好）

### 3.1 上下文管理 —— 最实际的差异

Agent SDK 有自动 compaction；langgraph 得自己管。

风险量级：`simplify_list_html` 一页可能吐几百行链接清单，`NEWS_CRAWL_MAX_TURNS=50`（`backend/app/config.py:308`）下上下文涨得很快。当前靠 CLI 隐式压缩兜底，换框架后这层没了。

**必须做**：把"给模型看的清单文本"和"state 里的结构化结果"分开——原始清单只作为工具返回值出现一次，state 只保留 `NewsItem` 结构化结果。

### 3.2 硬停：从"靠模型自觉"变成"靠图强制" —— 变好

现状：`pagination_stopped` 是**提示词要求**（`prompts.py:37-41`）+ **工具拒绝**（`crawl_tools.py:324-333`）联合约束的。模型理论上可以反复试探，只是工具会一直拒绝它。

换 langgraph 后：条件边直接判定"命中已知 URL / 达到 max_pages → END"，图强制终止，模型不听话也没用。

这恰好补上了当前设计最脆弱的一环——**把终止条件押在提示词遵守度上**。**工程可控性比现在更强。**

### 3.3 成本 / turn 上报

`ResultMessage.total_cost_usd` / `num_turns`（`agent_runner.py:204-210`）这套要改用 LangChain callback 统计。stats 字段契约（`agent_runner.py:251-260`）要对齐，否则下游观测断档。

### 3.4 工具返回契约

现在是 `_text_result` 把 JSON 塞进 text block（`crawl_tools.py:108-113`），要改成结构化返回。

---

## 4. 两个必须留意的边界

### 4.1 不要顺手把工具改成预分类

`crawl_tools.py:10-14` 和 `prompts.py:6-7` 反复强调：**工具只回未分类的同域链接清单**，是实测有效的关键——"预分类会让 Agent 退化成规则执行者"。

**外层图编排 ≠ 工具层预分类。** 这两件事必须分清：

- ✅ 外层图管"何时停、何时翻页、何时重试"——放条件边
- ❌ 工具层不要告诉模型"哪条是新闻、哪条是翻页 URL"——仍是未分类清单

### 4.2 为这一个场景上 langgraph 其实偏重

你要的只是"带工具的单轮辨识循环"。`company_claude_cral/00-结论摘要.md` §4 列了三条路线：

| 路线 | 代价 | 适用 |
|---|---|---|
| A. Claude Agent SDK | CLI 子进程，进容器难 | 离线攻坚 / 冷启动 |
| **B. 原生 API tool loop** | **最低，能立刻进容器** | **嵌入日常链路** |
| C. LangGraph 编排 | 编排代码量最大 | 生产主流程，接主工程既有 flow 体系 |

langgraph 的价值在于将来要接主工程的 flow 体系、要可回放 / 可限流、要和其他节点串成流水线时。**只做"抓新闻列表"这一件事，路线 B 更划算。**

## 7. 一句话总结

**框架不是瓶颈。** 这个 Agent 的能力 = 90% 的确定性 Python（工具层）+ 10% 的模型辨识（ReAct 循环），langgraph 两样都能承载；而它刻意关掉了所有 Agent SDK 独有能力，所以"替代不了"的论据在当前配置下不存在。

真正的决策变量是三个，且都与 langgraph 无关：
1. 要不要**继续依赖 CLI 子进程**（进容器 / 高并发的代价）
2. 要不要**继续用同一个网关的同一模型**（换模型才是真的会退化）
3. 值不值得为这一件事引入**图编排的复杂度**（或先用路线 B）
