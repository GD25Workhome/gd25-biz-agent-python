## 2. 与 `实验后的分析/04-设计取向.md` 的关系：**修正核心主张**

既有 04 文档的主张是：

> **规则主路径 + Agent 旁路修复**
> "Agent 只做 `llm_filter_links` / `llm_repair` 等节点"

本文的差异有两点，都很实质：

### 2.1 "修复"是逐次付钱，"定界沉淀"是一次性付钱

既有 04 把 Agent 定位为**运行期修复节点** —— 意味着**每次运行失败都要调 LLM**。本文主张 Agent 的主战场是**冷启动期的定界**，产物是 `site_profile`，之后**热运行零 LLM**。

差异在成本结构上：

| | 既有 04（运行期修复） | 本文（冷启动定界） |
|---|---|---|
| LLM 调用频次 | 每次运行 × 失败站数 | 每站一次（或改版时） |
| 长期成本 | 与运行次数线性增长 | **摊销后趋近于 0** |
| 依赖运行期稳定性 | 高 | 低 |

### 2.2 Agent 的能力边界被划得不够清

既有 04 说"失败才 Agent 修复"，但没区分**哪些失败 Agent 能修**。本文的边界（`01` §0）：

- ✅ Agent 能治：**定界类**（P1 入口、P2 翻页、P3 噪声）
- ⚠️ 部分能治：**字段类**（P4）—— 且**实测 Agent 版并未改善详情抽取**
- ❌ 不能治：**通道类**（P5 反爬/JS）

→ **不做这个区分，就会出现"详情抽不干净也去调 Agent"的浪费**（而实验证明那条路当前是无效的）。

## 5. 既有分析里，本文**不采纳**的两条

诚实记录分歧，避免后面翻案时说不清。

### 5.1 "翻页生效 1/6" —— 数字成立，但归因需要补充

见 `01` §2。**既有数字 1/6 是对的，本文初稿一度误判为 0/6，已更正。**

但"1/6"这个数字容易被读成"翻页功能部分可用、只需优化"。补充归因后是：

- 唯一生效的华岭股份，靠的是它的翻页/文章 URL 都落在 `/news/` 下、**撞上 `NEWS_KEYWORDS` 里的 `news` 子串**（实测只命中这一个词）—— **是关键词蒙中，不是翻页发现逻辑正确**
- 唯一被人工逐条核对的平安，`index_2.shtml` 有 25 条全新链接，规则版命中 **0/25**
- 同时代码里确有两个真实缺陷：`pagination_urls` 是 `sorted()` 后当 FIFO 用，**没给"下一页"任何优先级**；`crawl_one.py:128` 的 `all_list_items[:max_articles]` 截断发生在**详情抓取之前**，所以"限制文章数"实际只省了详情请求、并未减少翻页

**影响**：不是"从 1 优化到 0.9"，而是"这套发现逻辑不成立，得重建"。这个差别直接影响优先级判断。

> 注：本文初稿曾把这一节写成"0/6 假阳性"，并误称 `NEWS_KEYWORDS` 含 `html`。两处均已核对源码更正 —— 见 `01` §2 的完整勘误。

### 5.2 "Agent 适合难站 Worker"——方向对，但表述会误导成本

既有 04 的结论"上限高，但成本/耗时/不确定性高 → 适合难站 Worker / 模板生成，不适合 2904 站篇篇全开"是**正确的**。

但本文要强调一个更容易被忽略的推论：**即使 Agent 在所有站上都成功，成本结构也要求它必须是低频的**（单站 $0.48~0.82 vs 规则 $0）。所以"Agent 不适合篇篇全开"**不是因为效果不好，而是因为经济性**——即便效果满分，也不能篇篇开。

**这个区分很重要**：它意味着**优化方向不是"让 Agent 更便宜"，而是"让 Agent 调用次数更少"**（沉淀 profile、规则自动推导、按站族共享）。

## 7. 需要与他人对齐的三个问题

写在这里，供讨论时直接使用：

1. **凭证路线**：走本机第三方 Anthropic 网关（`unidtai.com`，实验所用），还是走本工程已有的 Ark/豆包网关（`OPENAI_BASE_URL`）？后者零新增基建但要去掉 Claude Agent SDK 依赖。**这个决定影响全部代码。**

2. **"沉没进规则"还是"运行期修复"**：Agent 的产出是要固化成 `site_profile`（本文主张），还是每次运行时按需调用（既有 04 主张）？这决定成本模型是否成立。

3. **全库还是难站**：本架构是奔着 2904 站的 `list_with_date` 族去的，还是只服务 235 个 hard/portal/SPA？如果是后者，整个 profile 体系的复杂度可以大幅简化。

> 这三个问题在没有共识前，阶段 1（n=6 验证）可以照做 —— 它不依赖这三个答案。
