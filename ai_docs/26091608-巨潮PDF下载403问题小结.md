# 巨潮 PDF 下载 403 问题小结

> 排查日期：2026-09-16（当晚根因复核，结论已更正）  
> 数据表：`radar_raw_document`（exhibition MySQL）  
> 相关模块：`radar_crawl`

> **勘误（2026-09-16 晚）**：原结论「出口 IP 被封」被证伪。同机、同出口 IP、同一时刻的
> 对照实验证明 403 来自 WAF 的 **TLS 指纹（JA3/JA4）拦截**：python `requests` 与 `curl`
> 均 403，`curl_cffi`（Chrome 指纹仿真）同机同 IP 即 200。代码已修复，见 §4。
> §3 原因表、§7 自测、§8 结论均已按新证据重写。

---

## 1. 问题现象

- **阶段 A（列表）正常**：`www.cninfo.com.cn` 全文检索接口仍可返回 JSON。
- **阶段 B（PDF）失败**：下载 `static.cninfo.com.cn` 上的公告 PDF 时返回 **HTTP 403 Forbidden**。
- 最近 2 天（按 `update_time`）共 **60** 条文档更新，**全部** `fetch_status=2`（失败），成功 0。
- 失败原因均已写入 `extra_json.pdf_error`，形如：
  ```text
  403 Client Error: Forbidden for url: https://static.cninfo.com.cn/finalpage/...
  ```
- 本机实测：历史上曾成功的 PDF URL、今天失败的 URL、甚至 `https://static.cninfo.com.cn/` 根路径，**当前均 403**。
- 403 页面中可见请求 ID 与出口 IP（排查时为 `139.226.59.190` / `.204`），当时据此怀疑 CDN/WAF 按源 IP 拒访静态站——**后经对照实验证伪**，见下一条。
- **关键观察**：同一台机器上**浏览器可以正常打开并下载同一 URL**，脚本 403。说明拦截对象不是 IP，而是「非浏览器 HTTPS 客户端特征（TLS 指纹）」。当时未重视这一线索，导致误判。
- **对照实验（同机、同出口 IP、同一时刻，未伪造 IP/未伪造代理）**：

  | 客户端 | 结果 |
  |--------|------|
  | python `requests`（系统现用） | **403** |
  | `curl` 直连 / `curl` 走系统代理 127.0.0.1:8118 | **403** |
  | `curl_cffi`（`impersonate="chrome"`） | **200**，完整 PDF（102,662 字节） |

对照更早数据：9/9–9/11 仍有大量成功（如 9/11 成功 278 / 失败 8）；历史失败主因多为 `pdf_text_empty(可能是扫描件需OCR)`，与本次 403 不同。

## 2. 涉及脚本与链路

| 角色 | 路径 | 职责 |
|------|------|------|
| 统一入口 | `python -m radar_crawl` / `python -m radar_crawl pdf` | 拉起 Worker；`pdf` 模式仅跑正文回填 |
| 阶段 A | `radar_crawl/workers/crawl_worker.py` | 巨潮列表元数据入库，`fetch_status=0`，**不下 PDF** |
| 阶段 B（出问题处） | `radar_crawl/workers/pdf_fill_worker.py` | 抢单 → 调下载抽字 → 回写 `content_text` 或标记失败 |
| HTTP + PDF 抽字 | `radar_crawl/adapters/cninfo.py` → `download_and_extract_text()` | `requests` 内存下载 → `pypdf.PdfReader` 抽文本（不落盘） |
| 状态落库 | `radar_crawl/db/repository.py` | 成功：`fetch_status=1`；失败：`fetch_status=2` + `extra_json.pdf_error` |

关键实现要点：

- PDF **不写临时文件**，只在内存中；磁盘占用主要来自 MySQL 正文，不是本地 PDF。
- 解析依赖第三方包 **`pypdf`**（`requirements-radar-crawl.txt`）。
- 适配器当前 **强制清掉系统代理**（`trust_env=False` + 删除 `*_PROXY`），本机代理不会生效。
- 开关：`RADAR_CNINFO_FETCH_PDF`；并发/页数：`RADAR_PDF_CONCURRENCY`、`RADAR_PDF_MAX_PAGES` 等。

状态约定：

| `fetch_status` | 含义 |
|----------------|------|
| 0 | 仅列表，待抽 PDF |
| 1 | 正文抽取成功 |
| 2 | 正文抽取失败 |

## 3. 可能失败原因（按可能性）

| 优先级 | 原因 | 依据 |
|--------|------|------|
| **高（已实证）** | `static.cninfo.com.cn` 的 WAF 按 **TLS 指纹（JA3/JA4）** 拦截非浏览器 HTTPS 客户端 | requests/curl 同机同 IP 均 403；`curl_cffi`（Chrome 指纹）同机同 IP 即 200；浏览器也能正常下载 |
| 中 | 短时高频下载触发**频率型**限流 | 今日失败集中在约 05:46–05:47 一批；默认并发约 3。低频单发同样 403 说明它不是主因，但恢复后仍需控频 |
| 中低 | 扫描件 PDF 无文本层（历史问题，非本次主因） | 更早失败多为 `pdf_text_empty` |
| 低 | 需登录才能下 PDF | 公告 PDF 公开链；curl_cffi 未登录即可下载 |
| 低 | URL 本身失效 | 同一 URL 换客户端即可下载 |
| **已排除** | 出口 IP 被封/拉黑 | 同一出口 IP 下浏览器与 curl_cffi 均能下载；且「系统代理出口 ≠ 直连出口」两种路径 curl 都 403，与 IP 无关 |

**不推荐、也不应采用**：IP 欺骗。HTTPS 需要真实可达源地址，无法靠伪造 IP 下载，且属于不当绕过。

## 4. 解决方案（正规路径）

### 短期（恢复抽字）

1. **改 HTTP 客户端（已完成，已实证）**：`radar_crawl/adapters/cninfo.py` 的 `_session`
   由 `requests` 换成 `curl_cffi.requests.Session(impersonate="chrome", trust_env=False)`；
   `requirements-radar-crawl.txt` 用 `curl_cffi>=0.16,<1.0` 替换 `requests`。
   2026-09-16 实测：列表检索（www.cninfo.com.cn）25 条正常；
   `1224768496.PDF` 下载抽字 **2432 字符**，与库内 id=734 记录一致。
   换出口 IP / 上云**不能**解决指纹拦截，不再需要；原建议作废。
2. 代码部署后，将失败行重置为可重试（示例，执行前请再确认范围）：
   ```sql
   -- 仅示例：按公司/时间收窄后再执行
   UPDATE radar_raw_document
   SET fetch_status = 0,
       extra_json = JSON_REMOVE(extra_json, '$.pdf_error')
   WHERE deleted = b'0'
     AND fetch_status = 2
     AND JSON_UNQUOTE(JSON_EXTRACT(extra_json, '$.pdf_error')) LIKE '403%'
     AND update_time >= '2026-09-16 00:00:00';
   ```
3. 恢复后 **降低并发、加大间隔**（如 `RADAR_PDF_CONCURRENCY=1`，增大 `RADAR_REQUEST_INTERVAL` / poll），防频率型限流。

### 中期（工程改造）

1. **显式代理配置**：改掉「一律禁用系统代理」；支持环境变量指定 HTTP(S) 代理（合法换出口，非伪装）。
   注：本次 403 与代理无关（curl 走系统代理同样 403），此项保留为通用能力，不再是 403 的解药。
2. **403 分类与退避**：识别 `pdf_error` 含 403 时暂停/告警，避免狂刷加重封禁。
3. **失败可重试策略**：区分「永久失败」（空文本扫描件）与「可重试」（403/5xx/超时）。
4. **同病防治**：`backend/domain/news_content/content_fetcher.py`（httpx）等通用 HTML 抓取
   链路遇到同类「浏览器能开、脚本 403」时，优先怀疑 TLS 指纹，改用 `curl_cffi`（支持 async）。

### 长期（稳定数据源）

1. 评估 [深证信数据服务平台](https://webapi.cninfo.com.cn/) 官方 API（商业签约），替代裸爬静态站。
2. 必要时用上交所/深交所等镜像作兜底（覆盖与字段不如巨潮全）。

## 7. 自测建议

同机对照实验即可定性：`curl` 403 而 `curl_cffi` 200 → TLS 指纹拦截（与 IP 无关，无需换出口）。

```bash
# 对照组：预期 403（非浏览器 TLS 指纹）
curl -s -o /dev/null -w "%{http_code}\n" --noproxy "*" \
  -A "Mozilla/5.0" -e "http://www.cninfo.com.cn/" \
  "https://static.cninfo.com.cn/finalpage/2025-10-29/1224768496.PDF"

# 实验组：预期 200
python - <<'EOF'
from curl_cffi import requests as cr
r = cr.get("https://static.cninfo.com.cn/finalpage/2025-10-29/1224768496.PDF",
           impersonate="chrome", timeout=30)
print(r.status_code, len(r.content or b""))
EOF
```

## 8. 一句话结论

**问题在阶段 B 的巨潮静态 PDF 下载被 `static.cninfo.com.cn` 的 WAF 按 TLS 指纹拦截——非浏览器 HTTPS 客户端一律 403，与出口 IP 无关，也不在 `pypdf` 解析本身。修复方式是底层 HTTP 客户端换成 `curl_cffi`（Chrome 指纹）：已于 2026-09-16 改完 `cninfo.py` 并实证恢复（下载抽字 2432 字符与库内记录一致）。部署后重置失败单重抽，并保持低频即可。**
