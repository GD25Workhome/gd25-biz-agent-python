# 01 - 现状与问题定义

## 0. 为什么要先定义问题

既有文档说的"抓取不稳定"是个笼统说法。它至少混了 5 类**性质完全不同**的问题，而它们的解法、可否用 Agent 解、成本，全都不一样。不拆开讨论，就会出现"用 Agent 治一切"的误判。

先给结论表：

| # | 问题 | 性质 | 实测状态 | Agent 能治吗 |
|---|------|------|----------|--------------|
| P1 | 入口不是新闻列表（门户/栏目页） | **定界**问题 | 大悦城、神州数码、节能国祯均失败 | ✅ 能（Agent 最擅长） |
| P2 | 翻页不跟随 | **定界**问题 | **仅 1/6 站**，且唯一成功的靠关键词巧合；平安实测 **0/25**（详见 §2） | ✅ 能（已验证 25/25） |
| P3 | 噪声链接混入（公告/产品/导航） | **定界**问题 | 平安吸入 `/gonggao/`；神州数码 49 篇里 24 条产品页 | ✅ 能（已验证） |
| P4 | 字段抽错（标题变导航、日期空） | **抽取**问题 | 平安曾 100% 标题错、日期 null | ⚠️ 部分（实测 Agent 版详情抽取**反而没变好**） |
| P5 | 反爬 / JS 渲染 | **通道**问题 | 神州数码曾 521；SPA 直接放弃 | ❌ 不能（Agent 拿不到 HTML 就无从判断） |

**关键洞察：Agent 的有效区是 P1~P3（定界/辨识），不是 P4（抽取），更不是 P5（通道）。**

既有分析其实已经隐含这个结论（"规则主路径 + Agent 旁路修复"），但没把 P4/P5 划到 Agent 能力圈之外。本文补上这条边界。

## 1. 当前实现长什么样（一句话）

`company_news_crawl` 是一个**纯启发式、零 LLM、按单一站点（平安）写的规则爬虫**：

```
__main__.py → crawl_batch（顺序 for）
             → crawl_one（BFS 翻页 + 站点分类 + 逐篇抓取）
             → adapters: HttpClient / SiteProfiler / ListExtractor / ContentExtractor
             → db: JSONLSink（MySQL schema 存在但从未连接）
```

核心脆弱点，全部在"用 URL 猜语义"：

- **抽链**：`NEWS_KEYWORDS` 命中 URL 就收；未命中但 `path 深度 > 1` **也收** → 这就是 P3 的根因。
- **抽字段**：固定 CSS 选择器列表 + `title == 黑名单词` 的**精确匹配**黑名单 → `中粮集团成员企业` 这种导航文案不会命中黑名单，直接入库。
- **翻页**：`extract_pagination_links()` 靠 URL/锚文本关键词猜下一页。

## 2. P2 现状：翻页 1/6，且生效的那一站机制可疑

既有 `实验260913-2` 的结论是"翻页生效公司数：1/6"：

| 代码 | 公司 | A(max-pages=1) | B(max-pages=4) | 交集 | only-B 新增 | 判定 |
|------|------|---------------:|---------------:|-----:|------------:|------|
| 000001 | 平安银行 | 98 | 98 | 98 | 0 | 否 |
| 600486 | 扬农化工 | 91 | 91 | 91 | 0 | 否 |
| 920139 | 华岭股份 | 39 | 64 | 39 | **25** | **是** |
| 000955 | 欣龙控股 | 70 | 70 | 70 | 0 | 否 |
| 300582 | 英飞特 | 0 | 0 | 0 | 0 | 否 |
| 920478 | 峆一药业 | 48 | 48 | 48 | 0 | 否 |

> ⚠️ **勘误（本文初稿曾断言此"1/6"是假阳性，复核后确认为误判，特此更正。）**
>
> 初稿的推理是："`max_articles` 上限在**翻页循环之后**才生效，且 `pagination_urls` 是 `sorted()` 后当 FIFO 用（没有给'下一页'任何优先级），所以 A/B 差异可能只是同一次抽链被截断的位置不同。"
>
> 这个推理**错在两处**（已核对源码更正）：
> - `all_list_items[:max_articles]` 在 `crawl_one.py:128`，截断发生在**详情抓取循环之前**（step 5 在 131 行），不是"翻页循环之后"。翻页循环在 113~118 行结束。所以截断影响的是**详情抓取范围**，不改变**列表项集合**。
> - 但**即使按初稿的误解，也解释不了华岭这一行**，因为：
>
> 1. **`交集 = A_count = 39`** —— B 是 A 的**严格超集**，A 的 39 条全被 B 包含。若是"截断位置不同"，A 应有 B 没有的尾部（`only_A > 0`），而实测 `only_A = 0`。
> 2. **新增的 25 条 URL 形态不同**：A 组抽到的是列表页与首页文章；B 组新增的是 `/news/html/?15.html` ~ `/news/html/?18.html` 这类文章 ID 页，还有一个带 `page=1` 参数的列表 URL。这是**第二个列表页**的产物形态，不是首页池里的另一段。
> 3. 华岭 `site_type=cms`，入口 `/news/class/?1.html` 是典型 CMS 归档 —— 该站的翻页链接**确实被现有规则发现了**。
>
> → **判定：华岭的翻页增量是真的。既有结论 1/6 成立。** 本文初稿的 0/6 断言作废。

**但"1/6"里那唯一的 1 仍需注意归因：** 华岭能成功，靠的是它的翻页/文章 URL 都落在 `/news/` 路径下，**撞上了 `NEWS_KEYWORDS` 里的 `news` 子串**（实测：`/news/html/?15.html`、`/news/class/index.php?page=1` 均只命中 `news` 一个关键词）。这是**关键词恰好蒙中**，不是"翻页发现逻辑正确"。同一套逻辑在平安上失败，本质差别是：

- 平安翻页 URL 是 `index_2.shtml` —— `pagination_keywords` 含 `index_`，**理论上能命中**
- 但 B 组对平安 `index_2.shtml` 的命中是 **0/25**（人工确认该页 HTTP 200、含 25 条全新链接）

→ **最硬的单点证据（不依赖汇总表）：平安的 `index_2.shtml` 可访问且有 25 条新链，规则版抓了 0 条。**

所以准确的表述是：**翻页能力 = 1/6，且唯一成功的一站靠关键词巧合；在唯一被人工逐条核对过的站（平安）上明确为 0/25。**

→ **这条对架构的意义：** 平安是既有分析认定的"规则友好型样板站、普通偏易"，而它恰恰是翻页完全失效的站。所以 Agent 在这个点上的收益（25/25 vs 0/25）是**从 0 到 1**，不是锦上添花。**但也正因为它是从 0 到 1，这个涨幅不可外推到详情抽取（P4）——那里规则是多少有些效果的。**

## 3. P4 实测：抽取没有变好

这是本文与既有乐观表述最重要的分歧点，必须有证据。

`ClaudeTest01` 是"列表 + 详情"版本，它的 `extract_article_fields()` 是**纯规则**（`h3/h1` 取标题、`h5/time/.date` 取日期、`.wrapper/.article-content/.content` 取正文），只是加了列表字段兜底。

实测结果（读 `ClaudeTest01/output/pingan_news.json`）：

- `published_at` 非空 **20/20**、`title` 均正确 → **看起来"修好了"**
- **但这是兜底掩盖的假象**：标题/日期走的是**列表页字段**（`fallback_title` / `fallback_date`），不是在详情页抽对的
- **正文仍然脏**：正文开头是裸日期再紧跟正文，例如 `"2026-08-26\n35年前，中国正式加入APEC…"` —— 详情页的 `h5` 日期被吞进了 `content_text`

也就是说：**P4 的两个子问题（标题、日期）被"列表兜底"绕过了，第三个子问题（正文干净度）原样保留。** 而 `ClaudeTest02`（只抽链、不开详情）的验证器根本不检查正文，所以这个缺陷在两次实验里都没有被裁判拦住。

→ **Agent 版详情抽取 = 规则版详情抽取**（代码就是规则），唯一新增的是列表字段兜底。
→ **结论：Agent 实验没有证明详情抽取会变好。要让它变好，得单独设计，并配独立的裁判。**

## 4. P3 的量级：噪声不是小瑕疵，是主流量

| 站点 | 落库数 | 其中噪声 | 噪声占比 |
|------|-------:|---------:|---------:|
| 神州数码 | 49 | 产品页 ~24 | **~49%** |
| 大悦城 | 36 | 非新闻 ~33 | **~92%** |
| 平安银行 | 49 | 公告/导航 ~10 | ~20% |

大悦城 33/36 的标题是同一个值 `中粮集团成员企业` —— 这是**同一段导航文案被重复采了 33 次**，不是"抽得不完美"，是"抽的东西根本不是新闻"。

→ **P3 不修，文章数这个指标毫无意义**。既有实验报告里的 total_articles 数字（134 篇、380 篇）都含大量此噪声。
→ 这也是 Agent 最该发力的地方：**它必须能回答"这条链接是不是一条新闻"**，而不是"这条链接像不像新闻链接"。

## 5. P5 边界：反爬在当前样本里不是主要矛盾

既有分析已指出"反爬/SPA 不是主矛盾"，本文支持并强化：

- 6 站 A/B + 3 站首轮实验里，**没有一站的失败主因被证实是反爬**。神州数码的 521 是**偶发**（同一次实验里另一次返回 200）。
- 平安、大悦城、华岭、欣龙、峆一、扬农 —— 均能拿到 200 + 完整 HTML。问题全部出在**拿到 HTML 之后**。
- 唯一被明确归因为通道问题的是 SPA（神州数码"下一页"是 JS 驱动），而它在当前实现里的处理是**直接放弃**（`crawl_one.py:102` 返回零文章）。

→ **结论：先把"拿到 HTML 之后"的问题解决掉，再谈通道。** 现在上 Playwright/浏览器渲染，是在给一个还没被证实存在的瓶颈买单。

## 6. 问题优先级（建议）

```
P2 翻页        ← 从 0 到 1，且已验证 Agent 可解   → 先做
P3 噪声定界    ← 决定数据可用性，Agent 已验证可解   → 同时做
P1 入口定界    ← 决定覆盖率（门户/栏目页误判）      → 紧接
P4 字段/正文   ← 有兜底不至于全错，但需独立设计     → 之后（唯一 Agent 未证明的）
P5 反爬/渲染   ← 尚未证实是瓶颈                    → 最后，用数据驱动
```

注意这个优先级**不等于**"Agent 优先级"。P4 优先级低但也不是 Agent 的强项；P5 优先级低且 Agent 完全不能治。
