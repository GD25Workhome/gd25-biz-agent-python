# 新闻 URL Agent 抓取 — 总体设计

> 范围：把 `实验0913-2` 验证过的「Agent 从入口页发现新闻 URL」能力，做成 gd25 的一个 Agent 接口，供 exhibition 调用。
> 日期：2026-09-14（v2：收缩为同步单接口）
> 详细设计：`02-gd25侧详细设计.md`、`03-exhibition侧详细设计.md`

---

## 1. 要解决什么

### 1.1 能力来自哪里

`实验0913-2` 用真实站点验证了：**Claude Agent SDK 可以从一个新闻列表入口页出发，自行发现后续列表页、区分「列表页 vs 详情页」、排除导航栏目，产出新闻详情 URL 清单。**

实测（6 站 × 3 次独立进程）：

| 代码 | 公司 | 通过 | 列表页数 | 后续页新 URL |
|---|---|---|---|---|
| 000001 | 平安银行 | 3/3 | 8/8/8 | 174 |
| 000955 | 欣龙控股 | 3/3 | 8/8/8 | 139 |
| 920478 | 峆一药业 | 3/3 | 6/6/6 | 90 |
| 920139 | 华岭股份 | 3/3 | 3/3/3 | 24 |
| 600486 | 扬农化工 | 0/3 | 4/4/4 | 0（通道限制） |
| 300582 | 英飞特 | 3/3 | 8/8/8 | 140 |

- 总通过 **15/18**，通过站点的 **run 间方差为零**
- 单次成本 **$0.73**（$0.33–$1.05），耗时 **2~4 分钟**

### 1.2 能力边界（必须继承）

> Agent 能解决**「下一页的 URL 是什么」**；解决不了**「下一页的内容服务端根本没给」**。

| 分区 | 内容 | 本设计 |
|---|---|---|
| 可做 | 发现入口页新闻 URL | ✅ |
| 可做 | 发现后续列表页（翻页） | ✅ |
| 可做 | 区分列表页 / 详情页 / 导航栏目 | ✅ |
| 可做 | 用历史 URL 判断「已抓过」并停止翻页 | ✅ |
| 不做 | 打开详情页抽正文 | ❌ 只采列表入口 URL |
| 不做 | 绕过 JS 渲染 / 反爬 | ❌ 通道问题，Agent 治不了 |

### 1.3 现状问题

1. `company_news_crawl` 规则版翻页不稳定：欣龙控股、峆一药业**零增量**，英飞特零产出。
2. 该模块**未接入任何服务**，只有 CLI；`db/repository.py` 全是 TODO。
3. exhibition 的 `radar_company` 表**没有新闻列表页 URL 字段**。

## 2. 职责划分（本次设计的核心）

```text
┌─────────────────────────────────────────────────────────────┐
│ exhibition (Java)                                            │
│                                                              │
│  ① 取企业新闻列表页 url                                       │
│  ② 取上次已抓详情页 url list（known_urls）                     │
│  ③ 调 gd25 的 Agent 接口（同步，等 2~4 分钟）                   │
│  ④ 拿到「之前没抓过的」url list                                │
│  ⑤ 落库（url_norm 去重）                                      │
│  ⑥ 异步化 + 超时管理（自己负责）                                │
└───────────────────────────┬─────────────────────────────────┘
                            │ POST /api/v1/huayuan/news-url-crawl
                            │ {news_list_url, known_urls, ...}
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ gd25 (Python FastAPI)                                        │
│                                                              │
│  跑一次 Claude Agent：                                        │
│    · known_urls 进提示词，看到熟悉的 url 就停翻页              │
│    · 从入口页开始发现新闻 url                                  │
│    · 只返回 known_urls 之外的                                   │
│  返回 {news_urls, list_pages_fetched, stop_reason}            │
└─────────────────────────────────────────────────────────────┘
```

**一句话**：exhibition 负责「传 url + 传历史 list → 落库」；gd25 负责「跑 Agent，返回没抓过的 list」。

### 2.1 明确不做的事（本次设计范围外）

| 不做 | 原因 |
|---|---|
| gd25 侧任务表 / 队列 / 消费者 / 状态机 | 需求不需要；exhibition 自己管异步 |
| gd25 侧轮询接口 / `task_id` | 同步接口一次返回，无需轮询 |
| gd25 连 exhibition 的 MySQL | gd25 本次**完全不碰数据库** |
| 打开详情页抽正文 | 只采列表入口 URL |
| 替换 `company_news_crawl` | 规则版仍是日常热跑路径，本次是增量 |

> **v1 → v2 的修正**：初版在 gd25 侧设计了任务表、`asyncio.Queue` 消费者、`pending/running/success/failed` 状态机、轮询接口与心跳回收。这些**都是需求未要求的自增长**。v2 全部删除 —— 异步是 exhibition 的职责，gd25 只提供一个跑完就返回的接口。

## 3. 接口契约

### 3.1 请求

```http
POST /api/v1/huayuan/news-url-crawl
Content-Type: application/json

{
  "news_list_url": "https://www.xinlong-holding.com/news.php?catid=93",
  "known_urls": [
    "https://www.xinlong-holding.com/newsxx.php?catid=93&id=318",
    "https://www.xinlong-holding.com/newsxx.php?catid=93&id=317"
  ],
  "company_name": "欣龙控股",
  "stock_code": "000955",
  "max_pages": 8,
  "trace_id": "f0d48c988dcb745651e6d3c94acd4156"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `news_list_url` | string | **是** | 新闻列表入口页 URL |
| `known_urls` | string[] | 否 | 上次已抓的详情页 URL list；Agent 据此判断是否已翻到历史区域 |
| `company_name` | string | 否 | 辅助站点消歧 |
| `stock_code` | string | 否 | 辅助站点消歧 |
| `max_pages` | int | 否 | 列表页上限，默认 **8**，范围 1~20 |
| `trace_id` | string | 否 | 32 位 hex，便于双边日志串联 |

`known_urls` 传空数组或省略 = 全量抓取（首次抓取场景）。

### 3.2 响应

```json
{
  "news_urls": [
    {"url": "https://...", "title": "...", "published_at": "2026-08-26"}
  ],
  "list_pages_fetched": 3,
  "stop_reason": "hit_known",
  "stats": {
    "candidate_count": 31,
    "known_hit_count": 12,
    "agent_turns": 14,
    "agent_cost_usd": 0.42,
    "duration_ms": 96000
  },
  "trace_id": "f0d48c988dcb745651e6d3c94acd4156"
}
```

| 字段 | 说明 |
|---|---|
| `news_urls` | **只含 `known_urls` 之外的**新闻详情 URL |
| `list_pages_fetched` | 实际抓了几个列表页（用于判断是否真翻页了） |
| `stop_reason` | 见 §3.3 |
| `stats.candidate_count` | Agent 在列表页上识别出的候选总数（含已知） |
| `stats.known_hit_count` | 命中 `known_urls` 的条数 |

### 3.3 `stop_reason` 枚举

| 值 | 含义 | exhibition 应对 |
|---|---|---|
| `hit_known` | 命中 `known_urls`，主动停止翻页 | 正常（增量场景） |
| `max_pages` | 达到 `max_pages` 上限 | 正常；长期如此可调大 |
| `no_next` | 找不到后续列表页（到末页） | 正常 |
| `no_detail_links` | **列表页抓到了但抽不到详情链接** | ⚠️ **通道问题信号**，需人工核查 |
| `fetch_failed` | 列表页全部抓取失败 | 接口返回 **502** |

`no_detail_links` 是关键：站点若靠 JS 渲染，Agent 会正确返回「零链接」。**这不是正常空结果**，必须能区分并告警 —— 否则会静默失败。

### 3.4 HTTP 语义

| 情况 | 状态码 |
|---|---|
| 正常返回（含 `news_urls=[]`） | **200** |
| 参数非法（url 非法、max_pages 越界、known_urls 超限） | **422** |
| Agent 超时（服务端墙钟超时） | **504** |
| 列表页全部抓取失败 / Agent 异常 | **502** |
| 未配置 Anthropic 凭证或功能未启用 | **503** |

> `news_urls=[]` 且 `stop_reason=no_detail_links` 仍返回 **200** —— 这是「成功执行但结果为零」，与「执行失败」语义不同。调用方应据 `stop_reason` 判断是否告警。

## 5. `known_urls` 的作用（本次设计的机制核心）

需求原文：**「提交时给到其最近的10条新闻地址，用来让Agent进行去重，如果Agent发现有重复的新闻，则不需要再进行翻页了。」**

实现方式是**两层**，都在 Agent 内部：

### 5.1 L1 — 提示词层：让 Agent 知道「已抓到哪」

`known_urls` 作为提示词上下文注入，Agent 在翻页过程中自行比对：

```text
若当前页大量出现调用方给出的 known_urls，
说明已翻到历史区域，应停止翻页并 save_results。
```

**为什么不硬停**：同一页可能既含历史条目又含新条目（实验里首页就混着滚动推荐）。硬停会丢新 URL。让 Agent 判断，同时把命中数作为可观测指标。

### 5.2 L2 — 结果层：返回前减去 known_urls

```python
new_urls = [u for u in store.news_urls if url_norm(u) not in known_norm_set]
```

**这是兜底**：即使 Agent 判断失误多翻了几页，返回结果也不会含已知 URL。

### 5.3 与「后端存储时再次去重」的关系

需求还要求「异步抓取完成后，后端存储时再次去重」。因此去重共三层：

| 层 | 位置 | 依据 | 作用 |
|---|---|---|---|
| L1 | Agent 提示词 | `known_urls` 命中 | **短路停止翻页**（省钱） |
| L2 | Agent 返回前 | `url_norm` 减去 `known_urls` | 保证返回值干净 |
| L3 | exhibition 落库 | `url_norm` 唯一索引 | **最终一致性保证** |

L3 在 exhibition 侧 —— 见 `03`。

**经济意义**：正常全量跑 8 页 ≈ $0.73。若首次翻页就大量命中 `known_urls`，成本降到 **$0.2 左右**。实验结论「Agent 的价值在识别、不在发现」在这里落地：**高频场景靠短路省掉，低频冷启动才用满。**

## 6. 超时与异步（责任在 exhibition）

### 6.1 为什么 gd25 侧不做异步

Agent 单次 2~4 分钟，同步接口意味着调用方要挂长超时。**但这是调用方的选择，不是被调用方的**：

- 若 exhibition 的触发场景是**后台任务/定时任务** → 同步完全够用
- 若触发场景是**运维台点按钮** → exhibition 自己用 `@Async` + 前端轮询**自己的**状态字段

无论哪种，**异步状态都归 exhibition 管**，因为「给哪个企业抓、抓了几次、成没成」本身就是业务数据。

gd25 因此保持**无状态**：不建表、不存任务、不落盘结果。

### 6.2 超时参数

| 侧 | 项 | 值 |
|---|---|---|
| gd25 | 服务端墙钟超时 | **600s**（实验最长 4 分钟，2.5 倍余量）→ 超时返回 504 |
| gd25 | Agent `max_turns` | 50 |
| exhibition | 客户端读超时 | **≥ 620s**（须大于服务端） |

`RadarAgentClient` 已有先例：`radar-event-score` 用 `radar-event-score-timeout-ms: 1200000`（20 分钟）。本次服务端 600s 就够，客户端给 620s。

### 6.3 重试的代价

⚠️ 重试 = 重跑一次 Agent = **$0.73**。设计上要减少重试：

- gd25 侧超时设足（600s），不要误杀
- exhibition 侧**不做自动重试**；失败的记状态、人工或次日再触发
- 若必须重试，先确认是超时（可重试）还是通道问题（重试无用）

## 7. 成本模型

| 场景 | 单次成本 | 说明 |
|---|---|---|
| 全量（`known_urls=[]`） | **$0.73** | 抓满 `max_pages` |
| 短路（首页即命中） | **~$0.20** | 只抓 1~2 页 |
| 典型增量 | **$0.3~0.5** | 抓 2~4 页 |

实测 18 次均值 **$0.7253**（$0.332–$1.053）。

**控制建议**：
1. 优先确保 `known_urls` 传对（这是省钱的唯一杠杆）
2. 日常热跑可先走规则版，仅规则失败时才调 Agent（两层架构）
3. `max_pages` 默认 8；调到 20 意味着单次可能 $2+

## 10. 验收口径

沿用实验的双判据：

```text
单站成功 = list_pages_fetched >= 3  AND  news_urls 非空
```

**回归基线**：可抓站点应保持实验的 **3/3 通过、run 间方差为零**。

**上线前三条工程自查**（来自实验的方法学教训 —— **裁判比被测对象更容易错**）：

1. 用真实数据验证 `url_norm` 去重有效且不误合并（两侧规则必须一致，见 `03` §5）
2. 用真实 `known_urls` 验证短路生效：`stop_reason=hit_known` 且成本显著下降
3. `news_urls=[]` 时能从 `stop_reason` 区分「站点真没新闻」与「通道阻断」

> 实验里出了 5 个判分器 bug（全是假阴性），其中一个会**惩罚能力更强的 Agent**（因为它发现了裁判没假设到的翻页路径）。线上更可能的失败模式不是「Agent 做不到」，而是**验收环节误判了 Agent**——所以第 3 条不是可选项。
