# 若改造成 Agent 的设计取向

前提：Agent **可以**提高准确率，但前提是用在规则失败处，而不是替换日频批量采集。

## 推荐骨架：规则主路径 + Agent 旁路修复

```
列表 GET（规则）
  → 抽链（规则）
  → [可选] Agent：链清洗 / 发现真列表 URL
  → 详情 GET（规则）
  → 字段抽取（规则）
  → 质量门：标题像导航？日期空？正文像公示噪声？
  → 失败才 Agent 修复（HTML 片段 / 锚文本 / 必要时浏览器）
  → 成功经验沉淀为 site_profile / 模板，下次回规则
```

约束：结构化 JSON 输出、日期必须可指回原文、每站 LLM 预算上限、失败可回退搜索通道。

## 方案对比（讨论结论）

### 1. 保守：LangGraph（更适合当前生产）

- 把上述流水线做成显式状态机；Agent 只做 `llm_filter_links` / `llm_repair` 等节点
- 与现有华院 Python flow 习惯一致，可测、可限流、可回放
- **准确率提升点**：定点修复（日期/错标题/产品链过滤/找真列表），批量 static 仍走规则

→ **推荐作为生产主方案**

### 2. 激进：Claude Agent SDK

- 提供接近 Claude Code 的工具循环（读文件、命令、MCP、子 Agent）
- 适合「给一个难站，自己试到抽出合格字段」
- 上限高，但成本/耗时/不确定性高 → 适合 **难站 Worker / 模板生成**，不适合 2900 站篇篇全开

### 3. Cursor SDK（确有 `@cursor/sdk` / Python SDK）

- 跑的是 Cursor 同款 **编码 Agent**（本地或云端 workspace）
- 强项：改解析器、写站点适配器、开 PR 沉淀代码
- **不适合**当作线上高频网页采集 runtime
- 合理用法：离线根据失败样本进化 `company_news_crawl` 规则/模板

## 选型表

| 目标 | 更合适 |
|------|--------|
| 日频覆盖、成本可控 | 规则 + LangGraph 质量门 + LLM 修复 |
| 门户/卡片/怪 DOM 攻坚 | Claude Agent SDK（或等价强工具 Agent）旁路 |
| 自动改爬虫代码沉淀模板 | Cursor SDK / 云端编码 Agent |
| 展厅评分 | 继续读知识库；评分 Agent 不现场爬官网 |

## 讨论中的共识表述

当前实现 ≈ 「借助经验的规则式 py 脚本做网页抓取」。  
要涨准确率：用 LangGraph 把「规则爬 + 失败才 Agent」产品化；Claude Agent SDK 打怪站；Cursor SDK 进化爬虫代码，而不是替代爬虫。
