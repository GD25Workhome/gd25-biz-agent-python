## 阶段 1：把 n=1 变成 n=6（1~2 天，可控成本）

**目标：消除"过拟合到平安"这个最大偏差。**

### 方法

用**完全相同的裁判口径**，在 `实验260913-2` 的 6 个站上重跑 Agent 抽链：

| 代码 | 公司 | 规则版翻页 | 备注 |
|------|------|-----------|------|
| 000001 | 平安银行 | 0/25 | 已知样板（实验里已过） |
| 920139 | 华岭股份 | 25（**真的**，但靠关键词巧合） | **未参与设计，关键样本** |
| 600486 | 扬农化工 | 无 | 未参与设计 |
| 000955 | 欣龙控股 | 无 | 未参与设计 |
| 920478 | 峆一药业 | 无 | 未参与设计 |
| 300582 | 英飞特 | 无 | 规则版零产出，**最难** |

**关键约束：这 4 个未参与设计的站，提示词与简化器不得为其做任何针对性调整。** 一旦调了，n=6 的价值归零。

### 验收指标（可证伪）

| 指标 | 门槛 | 不达标的含义 |
|------|------|--------------|
| 翻页发现成功率 | ≥ 4/6 站能发现翻页规律并跟随 ≥2 页 | 方案不通用，退回"仅用于难站" |
| 抽链噪声率（非新闻链占比） | ≤ 10% | 定界能力不足，提示词/简化器需改进 |
| 每站 Agent 成本 | ≤ $1.0 | 成本模型不成立 |
| 每站 Agent 耗时 | ≤ 3 分钟 | 延迟不可接受 |
| 失败可解释性 | 每个失败站能定位到"提示词/简化器/通道/站点本身"四类之一 | 无法定位 → 不可工程化 |

### 必须同时做的：**跑 3 次**

单次运行无稳定性数据（见 `02` §3.3）。至少每站跑 3 次，记录：

- 成功率方差（3 次里有几次过）
- 成本方差
- **失败模式是否可复现**（同样的站，是否同样位置失败）

> 如果 3 次里结果不稳定 → 说明方案方差大，**必须加倍强调 profile 沉淀**（因为沉淀正是为了消除运行期方差）。

## 阶段 2：补详情抽取的独立裁判（1 天）

**目标：解决"唯一实测没变好"的环节（P4）。**

`ClaudeTest02` 的裁判不检查正文，所以 ClaudeTest01 的脏正文溜过去了。必须新增独立裁判：

```python
def verify_article(article, list_ctx, html) -> dict:
    return {
        # 1. 日期可回溯：抽到的日期必须出现在列表页该链接的 nearby 文本里
        "date_traceable": date_in(list_ctx.nearby_text, article.published_at),

        # 2. 正文头部不是裸日期（ClaudeTest01 实测缺陷）
        "no_bare_date_head": not BARE_DATE_HEAD.match(article.content_text[:40]),

        # 3. 正文不含许可证公示/招聘/免责声明等噪声模块
        "no_noise_module": not NOISE_PATTERNS.search(article.content_text[:300]),

        # 4. 标题与正文一致（标题应出现在正文前 200 字，或与正文首段高重叠）
        "title_matches_body": title_consistency(article.title, article.content_text),

        # 5. 正文长度在合理区间（防"抓到导航文案"和"抓到整页"两个极端）
        "body_len_ok": 200 <= len(article.content_text) <= 20000,

        # 6. 正文不是"整页文本"（护栏：正文长度不应接近 whole-page 文本长度）
        "not_whole_page": len(article.content_text) < whole_page_len * 0.9,
    }
```

### 对照组设计

| 组 | 抽取方式 |
|----|----------|
| C0 | 现行 `company_news_crawl.ContentExtractor`（规则） |
| C1 | ClaudeTest01 的 `extract_article_fields`（规则 + 列表兜底） |
| C2 | **只用列表页字段**（不打开详情）—— 下界基线 |
| C3 | LLM 抽取（**用路线 B 的一次函数调用**，非 Agent） |

**假设待验证：** C3 是否显著优于 C1？

> **如果 C3 ≈ C1，则"Agent 让内容抓取更稳定"这个命题在抽取环节不成立**，架构应把 LLM 完全排除出抽取环节，只用于定界与槽位发现。这是个**高价值的否定性结论**，能省掉大量成本。

**注意 C2：** 如果只用列表页字段（标题+日期）质量就够（因为很多站的列表页已有 `date + title`），那么**详情抽取的必要性本身就要重估** —— 可能只需要正文，甚至正文也可以只要摘要。

## 阶段 3：site_profile 闭环（2~3 天）

**目标：验证"一次性 Agent 摊销"这个核心经济假设。**

### 3.1 先做**无 Agent 版**（重要）

在引入 Agent 之前，先验证：**能否用纯规则自动推导出 `url_path_allowlist` 和 `pager.template`？**

```python
# 候选白名单：对同域链接做路径聚类，取占比最高的模式
# /about/news/1787727208700.shtml → ^/about/news/\d+\.shtml$
# 去数字后的路径模板出现频次 ≥ M → 判定为该站的详情路径模式

# 候选翻页模板：对可能的翻页 URL 做差分
# index_2.html / index_3.html → index_{n}.html, start=2
```

**如果能自动推出来，Agent 在很大一部分站上根本不需要出场。**

> 这是本计划里**性价比最高的一步**。平安一条 `/about/news/\d+\.shtml` 白名单就能滤掉全部噪声（P3），而推导它不需要 LLM。

### 3.2 再引入 Agent 兜底

只在"规则推导不出 profile"的站上调 Agent。记录：

| 指标 | 门槛 |
|------|------|
| 规则自动推导 profile 覆盖率 | 越高越好（**先测出这个数，再定 Agent 需要覆盖多少**）|
| Agent 冷启动 profile 成功率 | ≥ 70% |
| profile 可复用性 | 同站第 2 次运行**不调 LLM**（硬要求）|
| profile 稳定性 | 7 天后重跑，命中率不下降 > 10pp |
| 重建触发准确性 | 故意改版 → 失败率上升 → 能触发重建（不误触发即可）|

### 3.3 profile 落库

不接 MySQL 也能先做（JSON/YAML 文件 + 版本目录即可）。但**必须**有：

- `parse_version` 递增、旧版保留（可回滚）
- **profile → 生效效果** 的自动记录（否则无法判断该版本是否变差）

## 阶段 4：编排接入（按需）

只有在阶段 1~3 全部通过后才做。

- **路线 C（LangGraph）**：接主工程既有 flow 体系（`backend/domain/flows/builder.py` 的 `StateGraph` + `node_creator_registry`）
  ```
  resolve_profile → crawl_with_profile → quality_gate → write_sink
                                    ↓ fail
                              collect_failures → maybe_rebuild_profile
  ```
- 与既有 `radar_crawl`（CNINFO，worker + MySQL 任务队列）的架构约定**保持一致**：`华院Agent设计/python爬虫脚本改造/26091101-总体设计.md` 明确写了"不把采集做成 LangGraph / ReAct 工具，采集是独立可发布服务"。**建议遵守这个约定**：news crawl 做成独立服务，LangGraph 只做外层编排，不把采集塞进 Agent 工具链。

## 成本模型

| 场景 | 单站成本 | 2904 站总成本 | 备注 |
|------|---------:|--------------:|------|
| 纯规则（现状） | $0 | $0 | 但覆盖率/质量很低 |
| **日频 × 全库 × Agent** | $0.48~0.82 | **$1400~2400 / 轮** | ❌ 不可持续 |
| **冷启动一次性 Agent** | $0.48~0.82 | **$1400~2400 / 一次性** | ⚠️ 一次性可谈，但要分期 |
| **规则自动推导 profile（阶段 3.1）** | $0 | $0 | ✅ 优先，能覆盖多少先测出来 |
| 上述 + Agent 只兜底剩余站 | 只有兜底站花钱 | 取决于兜底比例 | ✅ **目标形态** |

**成本控制的三个抓手（按性价比排序）：**

1. **规则自动推导 profile**（阶段 3.1）—— 零成本，先榨干
2. **按站族共享 profile 推导器**——同族站用同一套探针，减少需要单独定界的站数
3. **分批冷启动**——一次性成本也要分期，不要一次跑全库

**止损线：** 如果阶段 3.1 测出"规则自动推导覆盖率 < 30%"，且阶段 1 的 n=6 通过率 < 4/6，则本方案对全库不成立，应收缩为**只服务难站**（235 个 hard/portal/SPA），主路径维持规则 + 质量门。
