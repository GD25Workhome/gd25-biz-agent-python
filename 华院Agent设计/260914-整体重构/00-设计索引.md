## 一、这次要做什么

**把实验验证过的能力做成一个 Agent 接口**：从企业新闻列表入口页出发，用 Claude Agent SDK 发现并翻页采集新闻详情 URL，返回**调用方还没抓过的**那部分。

```text
exhibition (Java)                            gd25 (Python FastAPI)
  ① 取新闻列表页 url                     ──>  POST /api/v1/huayuan/news-url-crawl
  ② 取上次已抓的详情页 url list                {news_list_url, known_urls}
  ③ 调接口（同步，等 2~4 分钟）               跑一次 Agent：
     （异步化由本侧负责）                        · known_urls 进提示词
  ④ 拿到「没抓过的」url list                    · 看到熟悉的 url 就停翻页
  ⑤ 落库（url_norm 去重）                <──  返回 {news_urls, stop_reason}
```

**职责一句话**：gd25 只负责「跑 Agent，返回没抓过的 list」；exhibition 负责「传 url + 传历史 list → 落库」+ 异步与超时。

## 三、v1 → v2 的收缩（为什么要改）

初版在 gd25 侧设计了**任务表、`asyncio.Queue` 消费者、`pending/running/success/failed` 状态机、轮询接口、心跳与僵死回收**。

**这些需求从未要求** —— 异步是 exhibition 的职责，gd25 只该提供一个跑完就返回的接口。v2 全部删除：

| v1（已废弃） | v2 |
|---|---|
| 任务表 `gd2502_news_crawl_task` | ❌ 删除 |
| 队列 + 消费者协程 | ❌ 删除 |
| 状态机 + 轮询接口 + `task_id` | ❌ 删除 |
| 心跳 / 僵死回收 | ❌ 删除 |
| 需要 `ENABLE_DATABASE=true` | ❌ 解除（本功能不碰数据库） |
| 两个接口（建任务 / 查任务） | → **一个同步接口** |

**收益**：gd25 侧无状态、不碰数据库，部署上只需解决「装 Node + claude CLI」一件事。

## 四、五个必须知道的关键点

### 1. `known_urls` 是省钱的核心机制（`01` §5）

需求原文「给最近 N 条，发现重复就不翻页」→ 实现为**两层**：

| 层 | 位置 | 作用 |
|---|---|---|
| L1 | Agent 提示词 | 命中 `known_urls` → **短路停止翻页**（省钱） |
| L2 | Agent 返回前 | 减去 `known_urls`（保证返回值干净） |
| L3 | exhibition 落库 | `url_norm` 唯一索引（最终保证） |

**不硬停**：同一页可能既含历史又含新条目（实验里首页混着滚动推荐）。硬停会丢新 URL。

**经济意义**：全量 ≈$0.73，短路 ≈$0.20。**`known_urls` 传对是唯一有效的省钱杠杆。**

### 2. 能力边界（实验结论，不可越界）

> Agent 能解决**「下一页的 URL 是什么」**；解决不了**「下一页的内容服务端根本没给」**。

- ✅ 发现入口页新闻 URL、翻页、区分列表页/详情页/导航、用历史 URL 判断已抓过
- ❌ 打开详情页抽正文（本次不做，未验证）
- ❌ 绕过 JS 渲染 / 反爬（通道问题，实测 Agent 治不了）

### 3. 通道问题必须显式暴露（`01` §3.3）

站点若靠 JS 渲染，Agent 会**正确**返回「零链接」。这不是正常空结果 —— 靠 `stop_reason=no_detail_links` 区分：

- gd25 返回 **200**（执行成功）
- exhibition 记 **FAILED + 告警**（业务上需人工介入）

### 4. 超时责任在 exhibition（`01` §6）

Agent 单次 2~4 分钟。gd25 服务端墙钟 **600s** → 504；exhibition 客户端给 **620s**。

⚠️ **若前置 Nginx / 网关，必须同步调大 `proxy_read_timeout`**（默认常为 60s），这是最容易漏的一环。

### 5. `url_norm` 规则两侧必须逐字一致（`03` §6.4）

⚠️ **本设计最容易出静默错误的地方**。规则含两个反直觉细节（都来自实验中的真实 bug）：

- **仅当无 query 时才去 path 尾斜杠** —— 否则 `/news/html/?109.html` 被破坏
- **query 参数需排序** —— 否则 `?a=1&b=2` 与 `?b=2&a=1` 存成两条

不一致的后果：L1 短路失准 + 去重出现重复行。**建议加跨语言一致性测试。**

## 六、与既有机制的关系（避免误用）

| 既有机制 | 复用? | 说明 |
|---|---|---|
| `RadarAgentClient` (Java) | ✅ 只加方法 | 不新建 HTTP 客户端 |
| `RadarAsyncTaskRunner` (Java) | ✅ 复用 | JVM 内队列，新增 `NEWS_CRAWL` 类型 |
| Quartz `JobHandler` (Java) | ✅ 复用 | 定时/批量驱动 |
| `RadarCrawlTaskStatusEnum` | ❌ 不复用 | 那是巨潮采集（MySQL）的状态 |
| `radar_crawl_task` 表 | ❌ 不动 | 巨潮采集线，另一条数据线 |
| `radar_raw_document` | ❌ 不写 | 结果落新专表，避免双源 |
| `company_news_crawl` | ➖ 不替换 | 规则版仍是日常热跑路径，本次是**增量** |
| `rewritten_queue_service` (Python) | ❌ 不再照抄 | v1 曾照抄其形状，v2 已删除这套 |

**特别注意**：项目里**没有** Celery / RQ / arq / APScheduler / FastAPI `BackgroundTasks` / SSE / WebSocket（已全量确认）。异步一律用既有机制。

## 八、验收口径

```text
单站成功 = list_pages_fetched >= 3  AND  news_urls 非空
```

**回归基线**：可抓站点应保持实验的 **3/3 通过、run 间方差为零**。

**上线前三条工程自查**（来自实验的方法学教训 —— **裁判比被测对象更容易错**）：

1. 用真实数据验证 `url_norm` 去重有效且不误合并（**两侧规则一致**）
2. 用真实 `known_urls` 验证短路：`stop_reason=hit_known` 且成本显著下降
3. `news_urls=[]` 时能从 `stop_reason` 区分「站点真没新闻」与「通道阻断」

> 实验里出了 5 个判分器 bug（全是假阴性），其中一个会**惩罚能力更强的 Agent**（因为它发现了裁判没假设到的翻页路径）。线上更可能的失败模式不是「Agent 做不到」，而是**验收环节误判了 Agent**。
