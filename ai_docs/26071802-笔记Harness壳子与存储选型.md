# 笔记 Harness：软件壳与存储选型（v1）

承接 `[26071801-笔记Harness九大模块裁剪.md](./26071801-笔记Harness九大模块裁剪.md)`。本文回答两个启动问题，并回应「大库如何喂模型、要不要 ES + Embedding + Neo4j」的顾虑。

**约束前提（已采纳）**：人力有限、技术面不宜铺太开；前端可接受本仓「Vue 3 CDN + FastAPI 静态托管」这一档复杂度，以后再升级；笔记产品与本业务仓解耦，**另起小仓或独立目录**，不把医疗控制台改成笔记 App。

---

## 一、软件壳与部署形态：v1 选什么

### 1.1 结论（直接用）


| 项      | v1 选型                                                         |
| ------ | ------------------------------------------------------------- |
| **形态** | **本机 Web App**：浏览器打开本地服务                                      |
| **壳**  | FastAPI 托管静态页 + 简易笔记编辑区 + 对话区（Vue 3 CDN / Element Plus，与本仓同档） |
| **部署** | 本机一条命令起服务（`uvicorn`）；笔记库指向本机某个文件夹                             |
| **不做** | Electron/Tauri 桌面壳、独立前端工程化（Vite 多包）、K8s/多租户 SaaS、嵌进本仓医疗 Tab   |


一句话：**Obsidian 式「本地文件夹是库」+ 浏览器里的编辑器/聊天；后端只跑在你自己的机器上。**

### 1.2 为什么不是别的


| 候选                 | 为何 v1 不优先                                               |
| ------------------ | ------------------------------------------------------- |
| 纯 CLI              | 笔记体验差，难养成「每天写」；harness 调试可以 CLI，产品壳不行                   |
| Electron / Tauri   | 打包、更新、权限模型多一整层；人力不够时拖死进度                                |
| 完全复用本仓 `frontend/` | 现有是医疗 Agent 运维台（聊天调试 + 知识库/清洗），**无笔记编辑模型**；整仓复用成本高于新建两页 |
| 云端多用户 SaaS         | 同步、账号、权限、合规全开；与「个人技术笔记」目标不符                             |
| Dify/Coze 当壳       | 平台锁编排，笔记不是一等公民，偏离 harness 自建目标                          |


可借鉴本仓的：**对话面板交互习惯、REST 调** `/api`**、FastAPI 挂静态资源**；不要借鉴整页 Tab 业务结构。

### 1.3 v1 界面最小集

```
┌─────────────┬──────────────────────┬─────────────────┐
│ 笔记树/搜索  │  Markdown 编辑/预览   │  Agent 对话      │
│（当前库）    │  当前打开的一篇       │  绑定当前笔记     │
└─────────────┴──────────────────────┴─────────────────┘
```

后端职责对齐裁剪表 MVP：ReAct loop + 笔记工具 + 会话绑定当前路径。

### 1.4 以后再升级的路径（先知道即可）

- 觉得 CDN Vue 难维护 → 再迁 Vite + 组件化  
- 要「关浏览器也在托盘里」→ 再套 Tauri，**数据层不用动**（仍是本地 Markdown 库）  
- 要手机看 → 另议同步；v1 不碰

## 二、笔记内容放在哪：存储介质



### 2.1 结论（直接用）


| 层级                       | 介质                                      | 存什么                        | v1 是否要               |
| ------------------------ | --------------------------------------- | -------------------------- | -------------------- |
| **真相源（Source of Truth）** | **本机目录里的 Markdown 文件**                  | 正文、附件、双链写法（`[[wikilink]]`） | **必须**               |
| **元数据/会话**               | **SQLite**（单文件，与库并列或在 `.note-harness/`） | 路径索引、标题、修改时间、会话线程、当前绑定笔记   | **建议有**              |
| **全文检索**                 | SQLite **FTS5**（或先暴力扫盘 + ripgrep 级简单搜）  | 关键词检索                      | MVP 用 FTS5 或简单扫；够用再停 |
| **向量检索**                 | 本地向量库（如 LanceDB / Chroma，文件落在库旁）        | chunk embedding            | **库变大、语义搜痛了再上（P1）**  |
| **图**                    | 先 **SQLite 边表**（from_path → to_path）    | 双链出边/入边                    | MVP 解析链接写入边表即可       |
| Elasticsearch            | 独立 ES 集群                                | —                          | **个人笔记 v1 不做**       |
| Neo4j                    | 图数据库服务                                  | —                          | **v1 不做**；边表不够用再评估   |


原则：**人能用编辑器直接打开的 Markdown = 唯一真相；数据库只是索引与会话，可重建。**

这样：

- 备份 = 拷文件夹或 Git  
- Agent 的 Artifact Store 与裁剪文档一致  
- 坏了索引可以删 `.note-harness/` 重建，正文不丢



### 2.2 目录示意

```text
~/NotesMyVault/                 # 用户可见的笔记库（真相源）
  AGENTS.md                     # 可选：库级约定（P1 Prompt Assembly）
  inbox/
  topics/
    harness-notes.md
  .note-harness/                # 可 gitignore：机器生成
    meta.sqlite                 # 元数据 + FTS + 链接边表 + session
    vectors/                    # P1 才出现
```

## 三、大技术笔记怎么喂给模型？



### 3.1 核心错误 vs 正确做法


| 错误                      | 正确（与 harness 一致）                    |
| ----------------------- | ----------------------------------- |
| 把整个库塞进 prompt           | **当前笔记**（或截断）进窗 + **工具按需读取**        |
| 一上来上 ES + 向量 + Neo4j 三套 | **先文件 + SQLite**；语义搜痛了再加向量；图用边表     |
| 以为「索引越全模型越聪明」           | 模型聪明靠 **检索质量 + 进窗预算 + 工具循环**，不是堆中间件 |


喂模型的标准路径（对齐 26071801 Context 模块）：

1. UI 打开笔记 A → Session 绑定 `path=A`
2. 用户提问 → Prompt 带 A 的正文（过长则前 N 字 + 大纲）
3. 需要更多 → Agent 调 `search_notes` / `read_note` / `list_links`
4. 工具返回 **短片段或单篇**，再推理；大结果可先写入临时笔记再摘要（P1 compaction）

**「内容非常多」时，缺的是检索与分段，不是三个重型引擎同时在线。**

### 3.2 索引演进（按痛点，不按时髦）

```mermaid
flowchart LR
  M0[Markdown文件]
  M1[SQLite元数据_FTS_边表]
  M2[本地Embedding]
  M3[Neo4j或ES]
  M0 --> M1
  M1 -->|"语义搜不准/库很大"| M2
  M2 -->|"图分析成为产品功能"| M3
```




| 阶段        | 何时升级                        | 做什么                                             |
| --------- | --------------------------- | ----------------------------------------------- |
| MVP       | 现在                          | 文件真相源 + SQLite（元数据 + FTS5 + 双链边表）               |
| P1        | 关键词找不到「意思相近」的笔记             | 切 chunk → embedding → 本地向量库；检索 = 关键词 ∪ 向量 Top-K |
| 更晚        | 明确要「全局知识图谱分析/可视化」且边表 SQL 吃力 | 再评估 Neo4j；个人库多数情况 **永远不需要**                     |
| 不做（个人 v1） | —                           | 自建 Elasticsearch 集群                             |




### 3.3 你要不要「三者配合」？

**不需要。** 对个人/小团队技术笔记：

- **ES**：为分布式全文与运维设计，单机 SQLite FTS5 通常足够  
- **Embedding**：有价值，但是 **第二阶段**；且用本地轻量库即可，不必上云向量服务  
- **Neo4j**：双链先当「链接表」；Obsidian 类产品也是文件 + 索引，不是一上来图数据库

「配合」若出现，应是 **编排层（Agent 工具）同时查 FTS 与向量**，而不是三个重型中间件强耦合。

### 3.4 单篇「特别长」怎么办


| 策略       | 说明                                       |
| -------- | ---------------------------------------- |
| 进窗截断     | 当前篇只塞标题 + 大纲 + 相关章节                      |
| 工具分段读    | `read_note(path, offset, limit)` 或按标题锚点读 |
| 先拆笔记     | 鼓励长文拆成多篇 + 双链（产品与 harness 都更健康）          |
| 摘要缓存（P1） | 为长文维护一份短摘要笔记，检索先命中摘要再下钻                  |

## 四、与人力匹配的「最小开工清单」

1. 新仓（或独立目录）：FastAPI + 静态双栏/三栏页
2. 指定一个本地 vault 目录；只实现 `read/write/search/list/list_links`
3. SQLite：路径、FTS、链接边、session
4. 单 Agent ReAct；禁止读写 vault 外路径
5. **不上** ES / Neo4j / 桌面壳 / 云同步

验收仍以 26071801 的 MVP 五条为准。
