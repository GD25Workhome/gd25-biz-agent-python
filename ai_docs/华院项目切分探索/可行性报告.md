# 华院项目切分可行性报告

> 目标：把当前工程缩小为「只保留最基础模型调用能力」的精简服务，仅承载
> `huayuan_chat` / `huayuan_portrait` / `huayuan_radar_event` 三个接口所需的最小代码，
> 部署到 Docker 供公司其它服务（exhibition）调用，同时减少中间件组件。
>
> 结论先行：**可行，且推荐以"独立精简服务"方式切分**。三个华院路由的调用链完全不触碰
> PostgreSQL / Redis / pgvector / AutoGen / RAG 链路；切分的主要工作量不在"删代码"，
> 而在解开 4 个"全量注册/全量启动"的耦合点。预计 0.5～1 天改造 + 0.5 天验证。

---

## 1. 背景与需求

- 当前工程是"动态流程系统"：FastAPI + LangGraph 流程编排 + 医疗业务（血压、知识库、
  RAG、数据清洗、批处理、登录会话等），全量代码约 180 个 py 文件。
- 公司 exhibition 项目需要以 Docker 方式部署一个子服务，只用到三个华院接口：
  - `POST /api/v1/huayuan/chat` —— 固定流程 `huayuan_simple_agent`，单节点简单对话；
  - `POST /api/v1/huayuan/portrait` —— 固定流程 `huayuan_react_agent`（ReAct + `load_document_by_file_id` 按需加载证据）；
  - `POST /api/v1/huayuan/radar-event-score` —— 固定流程 `huayuan_radar_event_agent`（ReAct + `anysearch_web_search` / `anysearch_extract`）。
- 三个接口均**无 Session / Token 校验**，是独立的"请求 → 流程 → 结构化响应"链路。
- 诉求：减少中间件组件（当前部署需要 PostgreSQL、Redis 等），缩小镜像与运维面。

## 2. 现状盘点

### 2.1 三个华院路由的完整依赖链

以 `/huayuan/chat` 为例（另外两条仅在 tool 与 context 上多一层，结构一致）：

```
路由 backend/app/api/routes/huayuan_chat.py
 ├─ schemas: app/api/schemas/huayuan_chat.py            （纯 pydantic，无外部依赖）
 ├─ FlowManager.get_flow("huayuan_simple_agent")        domain/flows/manager.py
 │   ├─ FlowParser.scan_flows_directory                 domain/flows/parser.py（yaml 读取）
 │   ├─ GraphBuilder.build_graph                        domain/flows/builder.py
 │   │   ├─ langgraph.graph.StateGraph + MemorySaver     （内存检查点，无外部存储）
 │   │   ├─ FlowState / FlowInputSchema / FlowOutputSchema   domain/state.py（langchain_core）
 │   │   ├─ ConditionEvaluator                          domain/flows/condition_evaluator.py（simpleeval）
 │   │   └─ node_creator_registry                       domain/flows/nodes/registry.py  ← 耦合点①
 │   └─ FlowDefinition 模型                              domain/flows/models/definition.py（pydantic）
 ├─ domain/state.py                                     （langchain_core.messages）
 └─ create_langfuse_handler                             infrastructure/observability/langfuse_handler.py（可开关）
```

`type: agent` 节点的执行链（`AgentNodeCreator → AgentFactory.create_agent`）：

```
AgentFactory domain/agents/factory.py
 ├─ prompt_manager.cached_prompt          infrastructure/prompts/{loader,manager}.py（纯文件读取 + 占位符替换）
 ├─ tool_registry.get_tool(tool_name)     domain/tools/{registry,decorator}.py
 │    └─ 工具本体（仅华院需要的两个）：
 │         load_document_by_file_id       domain/tools/huayuan_document_tool.py
 │             └─ 请求级上下文            domain/tools/huayuan_portrait_context.py（contextvars，纯 stdlib）
 │         anysearch_web_search / anysearch_extract   domain/tools/anysearch_tool.py
 │             └─ 请求级上下文            domain/tools/huayuan_radar_event_context.py（contextvars，纯 stdlib）
 └─ get_llm(provider="doubao", ...)       infrastructure/llm/client.py
      ├─ ProviderManager                  infrastructure/llm/providers/{manager,registry}.py（读 config/model_providers.yaml）
      ├─ DoubaoChatOpenAI                 infrastructure/llm/doubao_chat.py（thinking 参数包装，必须保留）
      └─ langchain.agents.create_agent    （langchain 1.x，生成内部 ReAct 图）

```

### 2.2 中间件 / 外部依赖盘点

| 依赖 | 当前用途 | 华院三路由是否触及 | 处置结论 |
|---|---|---|---|
| **PostgreSQL**（SQLAlchemy 异步 + pgvector） | 主业务路由（chat/login/users/articles/knowledge_base/data_cleaning/batch_jobs）、启动时 `load_context_cache`、pipeline 队列、RAG 检索 | **否**（三路由零 DB 访问，checkpoint 用 MemorySaver） | 可完全移除；`Settings.DATABASE_URL` 需改为可选 |
| **Redis** | 代码中**零引用**（仅 `docker/deps.env` 提到容器、`requirements.lock` 有传递依赖） | 否 | 直接移除，无代码改动 |
| **Langfuse** | 可观测性 callback（`LANGFUSE_ENABLED` 开关，默认关闭） | 可选接入（关闭时 `create_langfuse_handler` 返回 None，无运行时依赖） | 代码与 SDK 可留可删；建议保留 handler + 开关，部署时默认关闭 |
| **pgvector / sentence-transformers / pandas / volcengine SDK** | RAG 导入、embedding 链路 | 否 | 移除（同时砍掉镜像中最大的 torch/sentence-transformers 体积） |
| **AutoGen**（autogen-agentchat/core/ext） | `autogen_team` 节点 | 否 | 移除 |
| **豆包 ARK API**（外部 HTTP） | LLM 调用（`https://ark.cn-beijing.volces.com/api/v3`） | **是** | 保留 |
| **AnySearch API**（外部 HTTP） | `anysearch_web_search` / `anysearch_extract` | **是**（仅 radar_event） | 保留 |
| **exhibition 文档工具**（外部 HTTP 回调） | `load_document_by_file_id` → `{document_tool_base_url}/radar/agent/tool/document/get` | **是**（仅 portrait） | 保留（对方服务，不在本服务镜像内） |

### 2.3 关键结论

1. 三个华院路由的运行期依赖只有：**FastAPI + LangGraph + LangChain(openai) + httpx + yaml + simpleeval + pydantic**，外加三个外部 HTTP 端点（豆包、AnySearch、exhibition 工具）。
2. 但是**按现状直接跑不起来精简版**：有 4 个"全量"耦合点在 import 层面就把重型依赖拖进来（见 §4）。

## 4. 四个关键耦合点与解耦改造（切分的实际工作量所在）

| # | 耦合点 | 现状 | 改法（改动很小） |
|---|---|---|---|
| ① | `domain/flows/nodes/registry.py` 的 `_init_default_creators()` 在 import 时**全量注册 8 类 creator** | import 该模块即连带 import `rag_agent_creator`（numpy/psycopg/pgvector）、`autogen_team_creator`（autogen 全家桶）、embedding（volcengine SDK）等 | `_init_default_creators()` 只 `register("agent", AgentNodeCreator())`，其余 creator 连同文件一并删除 |
| ② | `domain/tools/__init__.py` 的 `init_tools()` **全量导入 6 个工具** | 连带注册 blood_pressure/medication/symptom/health_event 等医疗工具 | 只导入 `huayuan_document_tool` 与 `anysearch_tool` |
| ③ | `app/api/routes/__init__.py` **聚合 11 个路由** | import 该模块即拉起全部医疗路由及其 DB repository | 只 `include_router` 3 个华院路由 |
| ④ | `main.py` lifespan 启动项与 `Settings` | 启动时：`load_context_cache()`（连 PostgreSQL）、`start_consumers()`（pipeline 队列）；`Settings.DATABASE_URL` 为**必填**字段，缺失时 `import backend.app.config` 直接抛 ValidationError | lifespan 只保留：加载 providers → `init_tools()` → `FlowManager.scan_flows()`（可选预加载）；`DATABASE_URL: Optional[str] = None` |

这四个点改完后，精简服务的 import 图就不再触达任何 DB / Redis / pgvector / AutoGen 代码。

## 6. 切分实施路线：三个方案对比

### 方案 A（推荐）：独立精简服务（新目录或新仓库，如 `huayuan-agent-service/`）

1. 新建独立工程目录，按 §3.1 清单复制文件（保持 `backend/...` 包结构不变，import 路径零修改）；
2. 执行 §4 的 4 个解耦改造；
3. 按 §5 裁剪 requirements，独立 `Dockerfile`（python:3.11-slim + `uvicorn backend.main:app`）；
4. 迁移 3 个华院测试文件，跑通验证（§7）。

- 优点：与主仓库彻底解耦、镜像最小、主仓库零回归风险、后续独立演进（新增规则三/四只动小仓库）。
- 缺点：与主仓库存在代码副本，未来修复需双写（可用"主仓库改 + 定期同步脚本"缓解，或干脆把精简版建成主仓库的发布产物）。

### 方案 B：同仓库瘦身子模块 + 启动开关

- 在主仓库新增 `backend_huayuan/` 或复用现有结构，用环境变量（如 `HUAYUAN_ONLY=true`）控制路由注册与 lifespan 步骤。
- 优点：无代码副本，改一处全生效。
- 缺点：共享代码仍会被主仓库演进"误伤"（回归风险）；镜像仍按全量 requirements 构建，**体积收益拿不到**；开关逻辑散落各处，长期腐化。

### 方案 C：不切代码，只减 Docker 组件

- 仅部署时不起 PG/Redis，`DATABASE_URL` 填 dummy。
- 结论：**不可行**——main.py lifespan 的 `start_consumers()`（pipeline 队列）会连 DB 且异常会导致启动失败（需改代码）；且镜像依旧携带 torch/autogen 等全部重型依赖，体积问题完全没解决。仅可作"临时过渡"。

**推荐：方案 A。** 理由：需求是"给公司其它服务用的稳定 Docker 子服务"，独立、小镜像、低回归风险是第一优先级；三个接口本来就是无状态的独立链路，与主仓库的医疗业务没有运行时耦合。

## 8. 风险与注意事项

| 风险 | 说明与对策 |
|---|---|
| 豆包 thinking 参数丢失 | 三份 flow.yaml 都配了 `thinking: {type: disabled}`，`get_llm` 会走 `DoubaoChatOpenAI` 包装类——**必须保留 `llm/doubao_chat.py`**，否则参数语义变化可能影响输出 |
| 精简版与主仓库代码漂移 | 方案 A 的固有风险；用"主仓库为唯一真源 + 同步脚本/CI 检查"缓解 |
| 多 worker 部署时 MemorySaver 语义 | 现实现本来就是每请求独立 `thread_id` 的 MemorySaver，与多 worker 兼容；若未来华院接口要跨请求会话，再考虑外部 checkpointer（届时才需要引入存储） |
| Langfuse trace_id 格式 | 32 位 hex 规范化逻辑在 `langfuse_handler.py`；若删除 Langfuse 则无此问题，保留则代码原样迁移 |
| AnySearch 无 Key 时匿名调用 | 工具设计上允许匿名（响应带 `anonymous` 标记）；部署时建议配置 Key 以保证配额稳定 |
| `find_project_root()` 依赖 `.env` 定位 | 容器内需保证工作目录/`.env` 布局与 `backend/app/config.py` 的向上查找逻辑一致（或直接挂载 `.env`） |

## 9. 工作量评估与结论

| 事项 | 工作量 |
|---|---|
| 4 个耦合点解耦改造 + main.py / config.py 瘦身 | 0.5 天 |
| 目录裁剪 + requirements / Dockerfile / .env 模板 | 0.5 天 |
| 迁移 3 个测试文件 + 启动冒烟 | 0.25 天 |
| 真实联调（豆包 / AnySearch / exhibition 工具）+ Docker 验证 | 0.5 天 |
| **合计** | **约 1.5～2 人天** |

**结论：可行，风险低。** 三个华院接口是无状态、无数据库依赖的独立链路；切分收益明确——
中间件从"PostgreSQL + Redis + Langfuse（可选）"缩减为**零必需中间件**（仅外部 HTTP 调用豆包 / AnySearch / exhibition 工具），镜像体积从 GB 级降至数百 MB。建议按方案 A（独立精简服务）执行，并按 §7 的验证清单逐项验收。
