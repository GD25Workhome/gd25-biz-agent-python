# 00 - 结论摘要

## TL;DR

**可行，且值得做。但"可信度"分三块，差别很大：**

| 判断 | 可信度 | 依据 |
|------|--------|------|
| 当前站间通用抽取（尤其翻页）几乎没有拦截能力 | **高（实测）** | 6 站 A/B，翻页增量 = 0 |
| 把"不确定"交给 Agent 后翻页能过 | **中（单站单次，n=1）** | 平安 5 页 125/125，但只跑过 1 个站 |
| 详情内容抽取也会一起变好 | **低（实测反而没变好）** | ClaudeTest01 正文仍混入日期与公示噪声 |
| 做成生产服务可行 | **中（未验证）** | 成本/延迟/并发/SDK 依赖均未在目标工程验证 |

**推荐路线：两层架构 + 按站族摊薄 Agent 成本**，而不是"日频批量让 Agent 逐站爬"，也不是"Agent 仅做失败修复"。

---

## 1. 可行性判定

### 1.1 技术上可行

- Claude Agent SDK（Python，`claude_agent_sdk`）可用 **进程内 MCP 工具**（`create_sdk_mcp_server`）把「抓 HTTP / 洗 HTML / 落库」这些确定性动作交给 Python 代码，把「判断哪条是新闻、哪条是下一页」交给模型。实验已经跑通。
- 关键设计点已经被验证有效：**工具只回"简化后的同域链接清单"，不预分类**，让模型做辨识。这一条是把 25/25 做出来的真正原因。
- 工具层可以用返回值**引导循环**（`pages_remaining`、`hint`），不依赖模型自觉。这是工程可控性的抓手。

### 1.2 但"更稳定"的收益要正确归因

现有实验里 Agent 拿到的是**已经过规则清洗的链接清单**：

```
simplify_list_html()：剔除 script/style → 只保留同域 http(s) 链接 → 去重 → 归一化 URL
                       → 每条约会输出 href / text / title / nearby / date_in_text
```

也就是说 **"找得到链接"是规则干的，"认得出哪条是新闻"才是 Agent 干的**。

→ 结论：Agent 的增量价值是**辨识与定界**，不是**发现**。任何把 Agent 说成"能突破抓取能力上限"的说法，在这份证据里都不成立。它能突破的是**规则未命中先验时的判断力上限**。

### 1.3 经济上：单站篇篇开不成立

| 口径 | 成本 |
|------|------|
| 规则爬一站的 LLM 成本 | **0** |
| Agent 爬一站列表页（ClaudeTest02，5 页/125 条 URL） | **$0.82**，12 turns |
| Agent 爬一站列表+详情（ClaudeTest01，2 页/20 篇） | **$0.48**，9 turns |

企业库规模：**2904 站**（`实验/材料/平安类筛查260912/`）。

- 若"日频 × 全库 × 篇篇开 Agent" → 单轮 $1400~2400 量级，**不可接受**。
- 若"冷启动一次性 Agent 定界 → 沉淀 profile → 日常跑规则" → Agent 成本被**摊薄到每站一次**，与规则成本相比可忽略。

→ **Agent 的正确卖点不是省 token，而是省人**（省掉"人工为该站写选择器"和"改版后人工修规则"）。见 `02-实验证据评估.md` §5。

## 2. 推荐架构（一句话版）

```
┌─ 冷启动 / 改版触发（低频，用 Agent） ────────────────────────┐
│  规则探针失败 → Agent 看简化 HTML → 产出 site_profile        │
│  {list_item, item_link, item_title, item_date, pager_next,   │
│   detail_body, url_path_allowlist, parse_version}            │
│  → 小样本验收（N 条：日期可解析 + 正文长度合理 + 不回溯失败） │
│  → 写入 profile 库                                          │
└──────────────────────────────────────────────────────────────┘
                              ↓ 沉淀
┌─ 日常热运行（高频，纯规则） ──────────────────────────────────┐
│  profile 驱动抽取 → 质量门 → 不达标样本攒起来 → 触发 profile 重建 │
└──────────────────────────────────────────────────────────────┘
```

**Agent 不常驻日常链路，但它是"能力来源"**。这与既有 `实验260912-1/04` 的"Agent 只做旁路修复"不同：旁路修复是**逐次**付 LLM 钱，本方案是**一次性**付钱后沉淀为确定性规则。两者都保留，但主次不同。

详细设计见 `03-推荐架构.md`。

## 3. 三个必须先解决的工程前提（当前都是缺口）

这三条不解决，架构再漂亮也落不了地：

1. **`claude_agent_sdk` 未安装在本工程**。实测当前 Python 环境 `ModuleNotFoundError: No module named 'claude_agent_sdk'`；PyPI 最新 `claude-agent-sdk 0.2.152`，而实验跑的是更早的 API（该包 0.x 迭代快，`allowed_tools`/`setting_sources` 等签名可能已变）。
   → 动手前先钉版本并跑通一个最小 smoke。
2. **本工程 `.env` 里没有任何 `ANTHROPIC_*` 变量**（实测 grep = 0）。本工程只有 `OPENAI_BASE_URL=https://ark.cn-beijing.volces.com/api/v3` + `LLM_MODEL=doubao-*`（豆包/Ark）。
   实验能跑，靠的是**实验者本机 shell 环境**里的 `ANTHROPIC_BASE_URL=…unidtai.com` 第三方兼容网关 + `ANTHROPIC_AUTH_TOKEN`。
   → 这是**未登记的隐性运行时依赖**：本机能跑 ≠ CI/容器能跑。必须决定走哪条路（见 §4）。
3. **SDK 是 CLI 子进程模型，不是纯 Python 库**。它依赖本机 `claude` CLI（实验里 v2.1.113）。容器化/批量并发要做好进程管理、超时与清理，成本模型与纯 API 调用不同。
   → 见 `04-验证与落地计划.md` §4。

## 4. 三条路线，必须选一条（这是当前最大的架构分歧点）

| 路线 | 做什么 | 优点 | 代价 | 适用 |
|------|--------|------|------|------|
| **A. Claude Agent SDK** | CLI 子进程 + MCP 工具循环（复刻实验） | 能力最全（子 Agent/MCP/skills）；已有可跑代码 | 依赖本机 CLI；对第三方网关的依赖未登记；成本最高；0.x API 不稳 | **离线站点攻坚 / profile 冷启动** |
| **B. 原生 API 工具循环**（`anthropic` SDK + 自己的 tool loop，或 `langchain-openai` 走现有 Ark 网关） | 把"简化链接清单 → 返回结构化槽位 JSON"做成一次函数调用 | 纯 Python、无 CLI、可进容器、走**已有**的 `OPENAI_BASE_URL` 网关 | 无子 Agent/MCP 生态；需自己写循环 | **嵌入日常链路，做质量门修复/单页定界** |
| **C. LangGraph 编排 + 上述任一做 LLM 节点** | 显式状态机，LLM 只占节点 | 与主工程一致；可测、可限流、可回放 | 编排代码量最大 | **生产主流程** |

**我的建议（不是"都要"，是分层用）：**

- **离线攻坚 / profile 冷启动 → A**（Claude SDK，交互式试错体验最好，实验已证）
- **线上嵌入 / 修复节点 → B**（走现有 Ark 豆包网关，零新增基建，可控成本）
- **总编排 → C**（LangGraph，接入主工程既有 flow 体系）

理由：A 的 CLI 子进程模型天然不适合高并发生产 runtime（既有分析 `实验260912-1/04` 的判断是对的）；但 A 的"自己试到抽出合格字段"能力对**低频、难站、一次性**的场景确实最优。而 B 能用你**已经付过钱的** `OPENAI_BASE_URL`，不引入新供应商依赖。

→ 如果只允许选一条先做：**先做 B**。它风险最低、能立刻嵌进现有工程，且能验证"LLM 做槽位定界"这个核心假设本身成不成立（与用什么 Agent 框架无关）。

## 5. 明确的"不做"清单

- ❌ **不要让 Agent 逐页自由爬**（既有分析已判定，本文补充经济证据：单站 $0.48~0.82 × 2904 站不可持续）
- ❌ **不要把"翻页成功"当作"抓取稳定"的证明**（详情抽取实测未改善，见 `02` §3）
- ❌ **不要在没有质量门的情况下扩大抓取量**（当前无质量门，10 国 50 站实测有 7 站日期全空仍会入库）
- ❌ **不要在 `company_news_crawl` 里直接改**（先在本目录把设计与验收标准定死，再决定是扩展现有包还是新建包）
- ❌ **不要引入 Playwright 作为主路径**（现有实现在反爬场景未验证；先确认反爬是不是真瓶颈 —— 6 站里没有一站的失败主因是反爬）
