# 03 - 推荐架构

> 前置：路线选型（A/B/C）见 `00-结论摘要.md` §4。本文默认 **A 做冷启动、B 做线上节点、C 做编排**。

---

## 1. 总原则

1. **规则做确定性动作，Agent 做判断性动作。** 抓 HTTP、洗 HTML、归一化 URL、落库 —— 永不交给 Agent。
2. **Agent 的输出必须是"可沉淀的配置"，不是"一次性结果"。** 每次 Agent 调用如果不留下 `site_profile`，就是纯烧钱。
3. **能一次性摊销的判断，绝不做成逐次调用。** 这是与"失败才修复"路线的核心差异。
4. **每个 LLM 输出都要能被校验、能被反驳。** 无质量门的 LLM 输出不进库。

---

## 2. 两层架构

```
════════════ 冷启动层 / 重建层（低频，Agent 参与） ════════════

  输入：新站 list_url（或失败率超阈的老站）
    ↓
  [规则探针] 试跑多套列表族解析器（list_with_date / generic_cms / ...）
    ├─ 稳定抽出 ≥N 条 {url, title, date} → 【直接产出 profile，不调 Agent】
    └─ 失败 ↓
  [Agent 定界] 只看 1~2 页简化 HTML，产出候选槽位 JSON
        list_item / item_link / item_title / item_date / pager_next
        detail_title / detail_date / detail_body / url_path_allowlist
    ↓
  [小样本验收] 按 profile 抓 5 条：
        日期可解析 ∧ 正文长度 ∈ [下限, 上限] ∧ 标题非导航词 ∧ 日期可回溯到原文
    ├─ 过 → 写 profile 库（version=1）
    └─ 不过 → 带失败样本重试 Agent（最多 K 次）→ 仍不过则标记 manual_required
    ↓
  profile 库：{site_id, family, slots, parse_version, fail_rate, last_ok_at}

════════════ 热运行层 / 日常（高频，纯规则 + 编排） ════════════

  读 profile → 规则抽取（含翻页，带早停）
    → 质量门（无 LLM）
    ├─ pass → 去重 → 落库
    └─ fail → 记入失败样本池（不逐条调 LLM）
    ↓
  失败率升高 → 触发【重建层】→ 新 profile（version+1，可回滚）
```

**两张网的区别：**冷启动层是**成本中心**（每次调 LLM 都要有明确产出物）；热运行层是**利润中心**（零 LLM 成本产出数据）。

## 3. site_profile 契约（核心数据结构）

这是把 Agent 的一次性判断固化成可复用资产的地方。**没有它，本方案退化成"逐次烧钱"。**

```jsonc
{
  "site_id": "000001",
  "domain": "bank.pingan.com",
  "family": "list_with_date",          // 站族，非像素级
  "list_url": "http://bank.pingan.com/bankPingAnCom/about/news",

  "slots": {
    // 每个槽位是【多候选】列表，按顺序尝试，不是单一选择器
    "list_item":    ["ul.news-list > li", ".news-item", "li:has(a[href*='/news/'])"],
    "item_link":    ["a[href]", "a::attr(href)"],
    "item_title":   ["a::text", "a::attr(otitle)", "a::attr(title)"],
    "item_date":    ["span.date::text", "a::text", "//parent::*//text()"],
    "pager_next":   ["a:contains('下一页')", "a[href*='index_']"],
    "detail_title": ["h3", "h1.title"],
    "detail_date":  ["h5", "time[datetime]"],
    "detail_body":  [".wrapper", ".article-content"]
  },

  "url_path_allowlist": ["^/about/news/\\d+\\.shtml$"],   // 强噪声抑制
  "pager": { "kind": "index_n", "template": "/about/news/index_{n}.shtml", "start": 2 },

  "quality": {
    "hit_rate": 0.96,          // 上次验收的命中率
    "fail_rate": 0.0,          // 热运行失败率（触发重建的指标）
    "sample_ok": 5,            // 验收通过的样本数
    "verified_at": "2026-09-13T20:00:00"
  },

  "parse_version": 1,          // 重建则 +1，旧版本保留可回滚
  "source": "agent_cold_start" // rule_probe | agent_cold_start | manual
}
```

**设计要点：**

- **`slots` 是多候选列表**，不是单一值 —— 这是"同类不同布局"的落点（既有分析 `新思路/02` 已提出，本文把它落成具体结构）。
- **`url_path_allowlist` 是性价比最高的一个字段**。平安一条 `^/about/news/\d+\.shtml$` 就能把 `/gonggao/`、导航、产品页全滤掉 —— 而这正是 P3 噪声的根治手段。**甚至可以在规则层就用正则自动推导候选白名单，连 Agent 都不用调。**
- **`pager.template` 让翻页退化为算术**。Agent 发现 `index_{n}.shtml` 后，日常翻页是 `for n in 2..N`，不需要每页再判断 —— 这是把 Agent 成果固化的最大收益点。
- **`parse_version` + 保留旧版本**，让 profile 可回滚（既有 `新思路/02` 的稳定性清单已列出）。

## 4. MCP / 工具契约

沿用实验里被证明有效的形状，但**收紧三处**。

### 4.1 沿用（已验证有效）

- 工具**只回简化后的同域链接清单，不预分类**
- 工具返回值携带 `pages_remaining` / `hint` **引导循环**
- 超限时工具**拒绝执行**并给出下一步指令（不靠模型自觉）
- 裁判与提示词**严格分离**

### 4.2 收紧 1：给"预算"一个显式工具

实验的预算控制是 `max_turns`（30/40）—— **粗粒度**，Agent 可以在 turns 内把 token 烧完。

新增：

```python
@tool("get_budget", "查询剩余预算（列表页数/详情篇数/LLM 调用次数）。", {})
```

并在每次 `fetch_*` 时**先扣预算再执行**。理由：`max_turns` 管的是"调用次数"，管不住"每次调用返回多长的 HTML"。**必须按资源量而非轮次设限。**

### 4.3 收紧 2：强制 `record_*` 落"可沉淀"的结构

实验里 `items_json` 是自由 JSON 数组，靠提示词举例约束。改为**在工具侧强校验**：

```python
@tool("record_news_urls", ..., {"page_url": str, "items_json": str, "next_page_url": str})
async def record_news_urls(args):
    # 校验失败 → 返回 ok=False + 具体错误 + 正确格式示例，让 Agent 自纠
    # 1. items_json 必须是数组
    # 2. 每项必须有 url，且 url 必须 ∈ 本次 fetch 返回的候选集  ← 关键：防幻觉
    # 3. published_at 若提供，必须能在【原文对应链接的 nearby 文本】里回溯到
    # 4. url 必须 ∈ url_path_allowlist（若 profile 已存在）
```

**第 2、3 条是防幻觉的核心**：Agent 只能从"我给它看过的"链接里选，日期必须指回原文。这两个约束能把幻觉风险压到接近零，且成本极低。

> 实验里没有这两条校验 —— 它之所以没出错，是因为平安页面干净、模型（`deepseek-v4-pro`）表现好。**这是运气，不是设计。**

### 4.4 收紧 3：区分"列表页"与"详情页"两组工具

实验把两者混在一起（ClaudeTest01 有 `extract_articles`）。建议**物理隔离**：

| 工具组 | 何时可见 |
|--------|----------|
| `list_*`（`fetch_list_page` / `record_news_urls` / `probe_pager`） | 冷启动定界阶段 |
| `detail_*`（`fetch_article` / `record_article_fields`） | profile 已存在，仅做字段修复时 |
| `profile_*`（`get_profile` / `propose_profile` / `validate_profile`） | 冷启动收敛阶段 |

理由：实验已证明"限制工具集"有效（`disallowed_tools` 挡掉 Bash/WebFetch）。**按阶段给最小工具集**，比一次给全套更可控，也让 prompt 更短。

## 5. 质量门（无 LLM，热运行层核心）

实验**没有质量门** —— 这是当前实现与"生产可用"之间最大的单点缺口。规则版也是如此：`中粮集团成员企业` 被采了 33 次，没有任何机制拦住它。

### 5.1 门禁规则

```python
def quality_gate(article, list_ctx, profile) -> tuple[bool, str]:
    # 硬失败
    if not article.url_norm: return False, "no_url"
    if not (article.content_text or "").strip(): return False, "empty_body"
    if len(article.content_text) < profile.min_body_len: return False, "body_too_short"

    # 标题：必须是"不相等"式的判定，不能用精确匹配黑名单
    # ← 直接修既有实现 `_is_nav_title()` 的缺陷
    if is_nav_like(article.title, article.content_text): return False, "nav_title"
    if article.title and article.title in article.content_text[:200]:
        pass  # 正常：标题出现在正文开头
    else:
        return False, "title_not_in_body"   # 标题与正文对不上，可疑

    # 日期：必须有，且【可回溯】
    if not article.published_at: return False, "no_date"
    if not date_traceable(article.published_at, list_ctx.nearby_text):
        return False, "date_not_traceable"

    # 噪声：许可证公示 / 招聘 / 免责声明等
    if NOISE_PATTERNS.search(article.content_text[:300]): return False, "noise_head"

    # 正文头部不能是裸日期（ClaudeTest01 实测缺陷）
    if BARE_DATE_HEAD.match(article.content_text.strip()[:40]): return False, "date_in_body"

    return True, "ok"
```

### 5.2 关键：`is_nav_like` 而不是精确黑名单

既有 `_is_nav_title()` 用 `title == keyword` 精确匹配 → `中粮集团成员企业 - 中粮` 溜过。改为：

```python
def is_nav_like(title, body):
    t = (title or "").strip()
    if not t or len(t) < 4: return True
    # 1. 包含式黑名单（不是相等）
    if any(kw in t for kw in NAV_KEYWORDS): return True
    # 2. 同一标题在本次批量里重复出现 ≥M 次 → 几乎必然是导航/栏目文案
    #    ← 这条能一次性拦掉"中粮集团成员企业 ×33"
    if title_repeat_count[t] >= 3: return True
    # 3. 标题与正文首段毫无重叠 → 可疑
    return False
```

**第 2 条是本方案里最便宜、最有效的单条规则**：它不依赖任何站点知识，用**批内重复度**识别"被重复采集的导航文案"。大悦城的 33 次、神州数码的 49 次 `产品及解决方案` 都逃不掉。

## 6. 翻页的执行策略

Agent 负责**发现规律**（一次性），规则负责**执行规律**（日常）。三层降级：

```
1. profile.pager.template 存在？
   → 直接算术生成 index_2..index_N，无需每页判断  【最优】

2. 不存在模板，但发现"下一页"锚点？
   → 规则跟随，带 visited 集合防环 + max_pages 硬顶

3. 前两者都不行（JS 分页 / 无规律）？
   → 本次循环内让 Agent 判断（少量），或标记该站为 hard_site 转人工/P5 通道
```

**早停条件（增量场景，来自既有 `新思路/03`）：**

```
连续 1 整页的 item 全部满足 url ∈ seen 或 date < watermark  → 停止翻页
（注意：date == watermark 但 url 未见过 → 仍需抓，同日可多篇）
```

## 7. 增量与去重（三层，沿用既有设计）

既有 `新思路/03` 的设计已足够好，本文只补两条工程约束：

| 手段 | 角色 | 补的约束 |
|------|------|----------|
| `url_norm` 唯一 | **主去重** | 归一化必须覆盖：scheme 统一、去尾斜杠、去跟踪参数、**去 fragment** |
| `watermark_date` | 控翻页范围 | ⚠️ **解析失败时不能唯一下刀** —— 否则一次解析事故会把整批新文当旧的跳过 |
| `content_hash` | 辅去重 | ⚠️ 正文抽脏时 hash 会漂 → **必须在质量门之后才算 hash**，否则脏正文产生脏 hash |

**新增一条：`ArticleRecord` 必须加 `page_index` / `source_list_url` 字段。**

理由：既有 `实验260913-2` 之所以要靠"发明 A/B 差分校验"来判断翻页是否生效，就是因为**输出里无法知道一篇文章来自哪一页**。这是可观测性缺陷，加上这个字段后，翻页是否生效变成一个直接的 SQL 问题。

## 8. 可观测性（当前完全空白）

必须补，且是**结构化**的：

| 指标 | 用途 |
|------|------|
| 每站 `list_pages_fetched` / `items_found` / `items_passed_gate` / `items_dropped` (含 drop reason) | 判断"是抽取坏了还是门太严" |
| 每站 `agent_turns` / `agent_cost_usd` / `llm_calls` | 成本归因，防超支 |
| `profile.parse_version` / `fail_rate` | 触发重建 |
| 失败样本池（HTML 片段 + 门禁拒绝原因） | **重建层/Agent 的输入**，形成闭环 |
| 结构化 trace（JSONL），而非 `agent_trace.txt` 全量文本 | 可查询、可回放、可比较 |

**最后一条是闭环的关键**：质量门拒绝的样本不是丢弃，而是**攒成下一轮 profile 重建的训练/提示素材**。这样系统会随运行自行发现需要重建的站。

## 9. 与既有 `company_news_crawl` 的关系

**不要推倒重写，也不要直接在里面改。**

| 复用（已验证可用） | 新增 | 替换 |
|--------------------|------|------|
| `http_client.py` 的 httpx + 限速 + 重试骨架 | 质量门模块 | `list_extractor` 的 URL 关键词启发式 → profile 驱动 |
| `models.py` 的 `SiteProfile` / `ArticleRecord` | site_profile 库 + 版本管理 | `content_extractor` 的固定选择器 → 槽位多候选 |
| `db/schema.sql` 的 DDL（已有 `uk_url_norm` / `uk_content_hash`） | profile 表、失败样本表、page_index 字段 | `_is_nav_title` 精确黑名单 → `is_nav_like` |
| `crawl_batch` / `crawl_one` 的编排骨架 | 冷启动层（Agent）、重建触发 | 翻页的发现与入队逻辑（当前仅 1/6 站生效，且那 1 站是靠关键词蒙中） |

**注意三处既有缺陷**（顺手修）：

- **翻页无优先级**：`extract_pagination_links` 返回 `sorted(list(...))`，在 `crawl_one` 里当 FIFO 消费 —— **"下一页"没有任何优先级**，第 1 页与第 20 页等价。这是翻页失效的直接原因之一
- **`http_client` 重试面过窄**：重试**只**发生在 `TimeoutException`；`ConnectError` 与其他异常直接返回，非 200 **从不重试** → 神州数码的 521 是偶发，这类必须重试
- **UA 是截断字符串**（`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36`），无 `Accept-Encoding` / `Referer` → 反爬场景偏弱

> 另注意：`crawl_one.py:128` 的 `all_list_items[:max_articles]` 截断发生在**详情抓取之前**，所以 `--max-articles` 只省了详情请求，**并未减少翻页与列表页请求**。做成本控制时不能指望这个参数。

**结论：以 `company_news_crawl` 为底座，新增 profile 层与质量门，把"Agent"作为冷启动的外部工具而非主链路依赖。**

## 10. 边界（什么情况本架构不适用）

- **SPA / 强 JS 渲染站**：拿不到 HTML，Agent 无从判断 → 需 P5 通道（浏览器），本架构不覆盖
- **API 型站（JSON）**：不该走 HTML 链路，应直连 API
- **强反爬（验证码/登录）**：Agent 不能治，需代理/凭证管理
- **站点数极少（<10）**：冷启动的 Agent 成本不值得，直接人工写选择器更快

对 2904 站的整体策略应是**分流**：`list_with_date` 族走本架构；235 个 hard/portal/SPA 走单独通道；不要用一套架构硬套全部。
