# 商机发现与事件归族 —— 决策记录

## 1. 要解决的问题（上推一层）

**现象**：Agent 每次运行都重新联网搜同一家公司 → 会**再次发现同一个展厅商机** → 又插一条新事件 → 雷达里又冒出一条"新商机"。
后果：**人工已经下过的结论被冲掉**（已发布/已退回/已签约），销售被迫重看，甚至**把已关闭的商机复活**。

**本质**：机器"重新发现"必须**尊重人工已处置**——而因为我们已决定「**只插、不更、不关**」，这个"尊重"**只能靠读状态来挡**；
否则"插入"这个动作本身就等于**制造重复 + 打扰**。

**三件事是一组**（缺一不可）：

| # | 能力 | 解决什么 |
|---|---|---|
| A | **多事件输出** | 一次没发现全（只取一个主簇） |
| B | **父关联 / 归族（时间线）** | 同一商机的多条事件串不起来 |
| C | **状态门控**（读人工处置状态） | 已经有结论的商机被重新翻出来 |

A + B + C 合起来 = 商机的 **发现 → 归族 → 尊重人工** 闭环。

---

## 2. 目标 / 非目标

**目标（本期）**

1. 一次运行能输出**多个**展厅事件（不再只取一个主簇）。
2. 同一商机的多次运行 → 事件串成**族**（第一条为根，`parent_event_id` 指向根）。
3. 命中**已发布 / 已关闭 / 已签约**商机 → **不落库**（不打扰、不复活）。
4. 判断（是否同一商机）归 **Agent**；代码只做**校验 + 落库**。

**非目标（本期不做）**

- 不写「更新」/「关闭」（高危动作，Python **只读**这些状态）。
- 不重算老数据（既定）。
- 不新建独立"商机"表行（`radar_opportunity` 由 Java 维护，我们只读）。

## 4. 目标模型（口径定稿）

**关系**：唯一性落在**商机**上；`radar_event` 是**时间线**（一商机多条事件，第一条为根）。

- **族键**：`root_id = COALESCE(parent_event_id, id)`。
- **商机身份** = 「(公司, 规范化 `event_name`)」；**由 Agent 判断**，代码兜底。
- **动作表**：

| Agent 发现 | history 里有该商机？ | 动作 |
|---|---|---|
| 有需求 / 潜在信号 | 无 | INSERT（`parent_event_id = NULL`，成为根） |
| 有需求 / 潜在信号 | 有，未发布未关闭 | INSERT（`parent_event_id = 根`） |
| 有需求 / 潜在信号 | 有，**已发布** | **不落库**（结果带 parent） |
| 有需求 / 潜在信号 | 有，**已关闭 / 已签署** | **不落库** |
| 展厅已完成 / 无需求 / 不相关 | — | **不落库** |

- **状态门控（取或）**：`radar_event.published=1` **或** `radar_opportunity.status ∈ {closed, signed}` **或** 事件自身失效 → 不落库。
- **`suspended`（撤回）不算关闭**（事件会回 `PENDING_VERIFY`，本就要再看）。

## 5. 需要实现的逻辑（分步 · 落点 · 验收）

### 5.1 history 族去重 + 只看最新 ✅ 已实现（261020）

**落点**：`radar_score/prepare.py`

**做法（Python 侧分组——避开 MySQL 5.7 无窗口函数）**

1. SQL 仍取该企业最近 N 条（`LIMIT` 可放宽到 ~100：分组后会显著变少）——SQL 见 §3.8。
2. **Python 分组**（拿到行后处理）：
   - `root_key = str(row["parent_event_id"] or row["id"])`（**约定子事件都直接指向根、单层**，见"边界"）；
   - 按 `root_key` 聚组；
   - 每组内按 `(update_time, id)` 倒序，**取最新一条**作代表；
   - **组内状态取"或"**（**关键**）：`published = any(组内 published)`、`closed = any(组内 expired_or_done 或 validity_status ∈ {EXPIRED, INVALID})`——**不能拿"最新一条"的 `published` 当代表**（已发布那条往往不是最新）；
   - 输出：代表行 + `root_event_id` + 聚合 `published` / `closed` + `member_count`；整体按 `update_time desc` 给模型。

**收益（正是你说的两点）**
- 给模型的数据从"最近 N 条"降到"**每个商机一条**"；
- 模型的"指认"从"在一堆同族里挑"**简化为比对去重后的列表**：命中 → 填 `matched_event_id` + `event_relation`；`published` / 已关闭 → 直接 `ignored`。

**边界**
- **单层 vs 多层**：约定"子事件只指向根"（`parent_event_id` = 根 id），故 `root = parent_event_id or id` 即可；若将来出现多层需向上回溯（建议仍保持单层）。
- **根不在本批**：分组只需根的 **id**，不要求根行也在本批（`parent_event_id` 本身就是根 id）→ 不受 `LIMIT` 影响。
- **老数据**：`parent_event_id` 目前全空（仅 v3 新增）→ 各自成组，等价于现状；这正是 §5.5 要回填的原因。

**验收**：3182 的历史里，5637 / 5639 / 5640（同族）**只出现一条**，且其 `published` 为**族内聚合值**。

### 5.2 批量补商机状态 ✅ 已实现（261020）

- **落点**：`radar_score/prepare.py`（新函数，或并入 `load_history_events`）
- **做法**：一次批量查询（避免 N+1）：
  ```sql
  SELECT source_event_id, status, close_reason, closed_at
  FROM radar_opportunity
  WHERE deleted = b'0' AND tenant_id = %s AND source_event_id IN (<该企业事件 id 集>)
  ```
  按族回填：`opportunity_status` / `opportunity_close_reason`（族内任一条命中即取）。
- **边界**：未发布过的商机**没有** `radar_opportunity` 行 → 只按事件自身判。
- **验收**：对已退回的商机，history 出现 `opportunity_status='closed'`。

### 5.3 决策用「Agent 指认 + 商机状态 + 算 root」 ✅ 已实现（261020）

- **落点**：`radar_score/event_update.py`
- **做法**：
  1. 校验 Agent 的 `matched_event_id` ∈ 本企业 history（防跨企业/乱指）；
  2. **强制闸门**：命中项若 `published=1` **或** `opportunity_status ∈ {closed, signed}` **或** 事件失效 → 一律 NOOP（哪怕 Agent 写了 new/continue，也压回"不落库"）；
  3. 未发布未关闭 → INSERT；**`parent_event_id` = 命中项的 `root_event_id`**（或 NULL=根）。
- **验收**：对已退回商机重跑 → `NOOP`；对未发布商机重跑 → INSERT 且 `parent_event_id` 指向根。

### 5.4 提示词补 `opportunity_status` ✅ 已实现（261020）

- **落点**：`prompts/radar_event_v3.md`（输入 history 的字段说明 + 指认规则）
- **做法**：说明 history 每条带 `opportunity_status`；补规则"`opportunity_status ∈ {closed, signed}` → `event_relation=ignored`"。
- **验收**：模型对已关闭商机输出 `ignored`。

### 5.5 老数据回填 + 合并（一次性脚本）⏸ **不做（用户决定，261020）**

- **决定**：**不回填老数据**（`parent_event_id` / `event_name` 保持为空），也不合并既有重复。
- **影响**：老事件在 history 里各自成组（每商机看着是"多条"），但**新数据不受影响**（新插入会挂族根）。
- **保留**：若将来要清，按 (company, 规范化名) 聚组、选主、其余置 `EXPIRED` 并置 `parent_event_id` 指向主。

### 5.6 Java 读取侧补列 ✅ 已实现（261020，仅 Java；前端不加）

- **已做**：`RadarEventDO` + `RadarEventRespVO` 补 `eventName`（`event_name`）/ `parentEventId`（`parent_event_id`）；复用既有 `BeanUtils.toBean` 自动映射，**Java 编译通过**。
- **不做**：前端暂不展示（用户决定）。
- 备注：`radar_opportunity` 的商机状态**未落库到 `radar_event`**（运行时只读），故不在 DO/VO 内；如需展示须另接。
