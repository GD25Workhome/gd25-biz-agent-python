# 巨潮采集 Worker 迁入华院后端 — 总体设计

> 范围：将 `exhibition_py` 独立脚本迁入本仓库，作为可开关的后台任务。  
> 日期：2026-09-11  
> 详细设计另文补充。

---

## 1. 要解决什么

`exhibition_py` 已是可用的「客户雷达采集」脚本：Java 往 MySQL 写爬取任务，Python 轮询抢任务，去巨潮拉公告列表、再抽 PDF 正文，写回 `radar_raw_document`。画像 Agent 再用 `file_ids` 去 exhibition 拉正文。

现状问题：

- 脚本独立仓库、独立进程，和华院 Agent 服务分开部署、配置两套
- 上 K8s 时要单独管镜像 / 环境变量 / 保活
- 希望并入当前华院后端，**服务起来后自己抓任务跑**，少一套运维面

本期目标：迁入本仓库，作为后台 Worker 常驻运行；**不改** Java 任务表契约、不改画像 HTTP 接口。

---

## 2. 现状与目标形态

| 项 | 现状（exhibition_py） | 目标（本仓库） |
|----|----------------------|----------------|
| 运行方式 | 两个 `while True` 进程 | 同一套代码，K8s 上可跟 API 分开部署，也可同镜像不同启动命令 |
| 数据库 | 直连 exhibition **MySQL** | **仍连这套 MySQL**（与华院 Postgres 无关） |
| 业务 | 巨潮列表 + PDF 抽字 | 不变 |
| 与 Agent | 间接：产出证据给画像 | 仍间接；**不**做成 LangGraph 节点 |

两条流水线保持不变：

```text
Java 写入 radar_crawl_task
        │
        ▼
   阶段 A  crawl_worker     抢任务 → 巨潮检索 → 插入 radar_raw_document（仅元数据）
        │
        ▼
   阶段 B  pdf_fill_worker  抢无正文文档 → 下 PDF → 回填 content_text
        │
        ▼
华院画像  POST /huayuan/portrait  按 file_ids 拉正文（已有 HTTP 工具）
```

## 3. 总体架构

### 3.1 原则

1. **采集是独立可发布服务，不是 Agent，也不挂 FastAPI lifespan。**
2. **双数据源。** 华院 API 继续可不连 Postgres；采集 Worker 只连 `RADAR_DB_*` MySQL。
3. **进程 / Deployment 隔离。** 生产 API 与爬虫分两个 Deployment（可同节点），避免长任务抢 API 资源。
4. **契约稳定。** 表结构、任务状态机、画像读证据方式尽量不动。

### 3.2 推荐部署（已落地目录）

代码位置：仓库根目录 `radar_crawl/`（由 exhibition_py 迁入）。

```text
镜像 A  Dockerfile              → huayuan-api（uvicorn）
镜像 B  Dockerfile.radar-crawl  → radar-crawl（python -m radar_crawl crawl|pdf）
```

K8s 示例：`deploy/k8s/huayuan-agent.yaml` + `deploy/k8s/radar-crawl.yaml`。

本地 / 容器入口（**一个命令启动全部任务**）：

```bash
python -m radar_crawl
```

以后加新 Worker：只改 `radar_crawl/registry.py` 的 `WORKERS` 列表，启动命令不变。排障才用 `python -m radar_crawl crawl` / `pdf`。

### 3.3 模块落位

```text
radar_crawl/
  config.py              # RADAR_DB_* 等
  db/repository.py       # 抢任务 / 写证据
  adapters/cninfo.py     # 巨潮 HTTP + PDF
  workers/crawl_worker.py
  workers/pdf_fill_worker.py
  __main__.py            # 统一入口
```

依赖：`requirements-radar-crawl.txt`（pymysql / requests / pypdf / python-dotenv）。

## 4. 配置怎么走

与现有华院 `.env` / K8s「环境变量」同一套注入方式，**另加一组采集专用变量**，例如：

| 变量 | 含义 |
|------|------|
| `ENABLE_RADAR_CRAWL_WORKER` | 是否启动采集循环（API 进程默认关，Crawler 进程开） |
| `RADAR_DB_HOST/PORT/USER/PASSWORD/NAME` | exhibition MySQL |
| 原脚本已有限速、并发、是否抽 PDF 等 | 原样迁入，不改语义 |

K8s 网页「环境变量」按 `KEY=VALUE` 填写即可；**不要**把 `.env` 打进镜像。

---

## 5. 边界与非目标（本期不做）

- 不把采集做成 LangGraph / ReAct 工具（除非产品明确要「Agent 自己决定爬什么」）
- 不把 MySQL 换成 Postgres、不迁表到本仓库
- 不改 Java 创建任务、不改画像 `document/get` 协议
- 不做通用任务调度框架（K8s Job/Cron 另议）
- 不在本期解决扫描件 PDF（无字可抽）的 OCR

---

## 6. 风险（只记方向）

- **阻塞**：同步 HTTP + PDF，必须独立进程或线程，避免拖垮 API
- **多副本抢任务**：沿用现有行锁 / 租约；A、B 各保持单逻辑消费者或依赖库锁
- **失败语义**：列表成功 ≠ 正文已齐；画像仍可能读到空正文
- **出网**：Worker 必须能访问巨潮；MySQL 必须从集群打到 exhibition 库
