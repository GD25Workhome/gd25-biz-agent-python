# 千问评判 vs 当前改动对照

> 原文见同目录「千问评判流程的input不合理的地方.md」  
> 核对时间：2026-09-10

## 千问指出的问题

| 问题 | 原文要点 |
|------|----------|
| `evidence_briefs` 三处重复 | 同时出现在 `flow_msgs` / `edges_var` / `persistence_edges_var`，约 30 条完全一致 |
| `queries` / `discarded_briefs` 同样三处复制 | 状态膨胀，若整包当 Prompt 会浪费 token |
| 建议 | 只保留一份；进模型前清洗 |

## 改动是否覆盖

| 项 | 状态 | 说明 |
|----|------|------|
| `edges_var` 不再塞全量 briefs | ✅ | 仅 `brief_count` / `prompt_brief_count` / `discarded_count` |
| `persistence` 不再塞全量 briefs | ✅ | 已去掉 `evidence_briefs` / `evidence_briefs_full`；只保留 `queries` |
| `prompt_vars` 只留 **一份压缩** briefs | ✅ | Top12 + 短字段 + 紧凑 JSON；终评 system 只替换这一次 |
| `discarded` 压缩且单份 | ✅ | Top15，仅在 `prompt_vars.discarded_briefs` |
| 终评 prompt 瘦身 | ✅ | 去掉 planned_queries / 大段示例；去掉未使用的 max_*、query_hint |
| HumanMessage 与 system 任务重复 | ✅ | 采集后改为短指令 |
| `flow_msgs` 里出现 briefs | ⚠️ 部分 | 采集是 function 节点，**不会**把 briefs 写入 `flow_msgs`。终评前 `flow_msgs` 里通常只有 **planner 的 queries JSON**（`add_messages` 累加，无法轻易清空）。这 **不会**进终评 LLM（agent 只用 `current_message` + system），但 Langfuse 的节点 input 仍可能看见 planner 那条消息——体积远小于 30 条 briefs |

## 真正进终评模型的内容

1. `SystemMessage`：`radar_event_score.md`（短规则）+ `{company_json}` + `{evidence_briefs}`（≤12）+ `{discarded_briefs}`（≤15）  
2. `HumanMessage`：一句输出格式说明  

**不会**把 `edges_var` / `persistence` / 全量 30 条 briefs 拼进 chat completions。

## 仍需知悉

- Langfuse 展示的是 **节点完整 state**，不是「纯 LLM messages」；哪怕已去重，input 面板仍可能含 `flow_msgs`（planner 输出）等字段，不要和「模型 token」划等号。  
- 若仍觉得观测脏：可再考虑终评改用无 Agent 的纯 LLM 节点，或自定义观测序列化只上报 `prompt_vars` 摘要。
