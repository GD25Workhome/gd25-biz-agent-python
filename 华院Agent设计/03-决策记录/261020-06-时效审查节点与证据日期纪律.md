## 2. 设计原则：分层，且每层都可验证

```
                ┌──────────────────────── 谁最可靠 ────────────────────────┐
  规则形态       │  代码（确定性）        │  LLM（语义）                     │
  ──────────────┼───────────────────────┼──────────────────────────────────│
  日期算术       │  ★ 放 self_check      │  不要（会给自己放行）            │
  字段/枚举校验  │  ★ 已有 R1–R6         │  不要                            │
  正文比对       │  需要流程内 function  │  不要（事实比对不该靠模型）      │
  证据是否支持结论│  做不了               │  ★ 只能 LLM                      │
  是否回顾文章冒充│  做不了（需读懂文意）  │  ★ 只能 LLM                      │
```

配套一条**度量**原则：复核节点写下的每一次修订都要留痕（`score_revision`），**触发率就是决策数据** —— 高触发说明该规则应前移回提示词；零触发说明这个节点是白花钱。

## 3. 关键技术设计

### 3.1 确定性硬闸（共享纯函数：图内 `rule_gate` **修订** + 图外 `self_check` **守门**）

现状：`radar_score/self_check.py` 已实现 R1–R6，并且**已经在改写等级**（`level_final`：`_cap_at_most` 封顶、"以区间为准"）；`execute.py` 里 `check()` 不通过就**跳过该事件不落库**。

建议新增：

| 编号 | 规则 | 动作 |
|---|---|---|
| R7 | **12 个月闸门**：主簇最早事实时间 相对 `current_date` ≥ 12 个月 | `expired`：`admission_pass=0`、`validity_status=EXPIRED`、`expired_or_done=1`、`system_level/final_level/total_score/evidence_score/specificity_score` 置 `null` |
| R8 | **招采截止日**：报名/投标/递交/响应/开标截止日 已过 或 <14 天 | 该证据 `discard`（现状仅提示词要求，无硬约束） |
| R9 | **日期纪律**：`evidences[].publish_date == 跑批日` | **剔除该条证据**（不是整体判失败）+ 记 `stats` |

要点：
- R7 依赖 **D8 口径**（"主簇最早事实时间"如何取、是否允许"新确认重置"）——**口径不定，代码不写**。
- 这三条都是纯计算，**单测可直接覆盖**（边界：11.9 vs 12.1 个月）。
- **同一份实现、两处调用**：R7–R9 抽成纯函数模块（`radar_score/rules/`），图内 `rule_gate` 用它**修订**、图外 `self_check` 用它**守门** —— 避免两处口径漂移。R7 未定口径前，图内先只做 R8/R9。

### 3.2 正文交叉核验（需要流程内的 function 节点）

**只有这一层必须进流程**，原因很实在：判断"模型给的 `publish_date` 是否真来自页面"，要拿 `deepseek_fetch` 的**正文**；而正文留在 flow 的 state（消息）里，flow 外的 `self_check` 拿不到。

- 节点形态：`type: function` + `function_key`（示例实现：`backend/domain/flows/implementations/radar_rule_gate_node.py`）。
- 做法：从 state 的工具返回里抽日期候选 → 与 `evidences[].publish_date` 比对 → 找不到该日期 ⇒ 剔除该条证据并记 `stats`。
- 判定：**留空优于拒绝证据**（有些公告页确实无日期），只在"日期在正文里根本不存在"时才剔除。

### 3.3 LLM 复核节点（语义，**只降不升**）

```
[radar_event_react_node(agent)] --> [rule_gate(function)] --(有违规)--> [auditor(agent)] --> END
                                                            \--(无违规)--------------> END
```

- 输入：第一节点 JSON + 证据 + `{current_date}` + 规则清单；输出：**完整修订对象**（不建议只给 patch，避免合并歧义）。
- 只判语义类：`quote` 是否支撑 `cite_reason`、是否回顾文章冒充新信号、证据是否同簇。
- **三条护栏**：
  1. **只许向下**：降级 / 置 `expired` / 剔除证据 / 置 `null`；**禁止升级、禁止新增证据或事实**。理由：一旦允许"补事实"，复核节点就从审查变成第二个生成器，越改越错比漏检更危险。
  2. **越界由代码拒绝**：复核输出当 patch 处理，做白名单 + **单调性校验**（等级只能变差、分数只能变小、证据只能减），越界即丢弃原值并告警。
  3. **可计算的规则不许交给它**：否则它会给自己放行（同源偏差）——D8 的现状正是"连按哪个时间算都没定"。

### 3.4 两个实现坑（必须写进设计，否则"改了也不生效"）

**坑 1 — 第二节点改分不生效（静默）**

路由取分数的顺序是：

```
for bag_name in ("edges_var", "persistence_edges_var"):   # edges_var 优先
    for key in ("radar_event_scores", "radar_event_score"):
        ... 一旦解析成功就 return                          # 命中即返回
```

第一节点（agent）写的是 `edges_var`。所以第二节点**不能只写 `persistence_edges_var`** —— 必须**同时覆盖 `edges_var` 的同名 key**，否则旧值遮住修订值，表现为"复核跑了但分数没变"。

**坑 2 — 浅拷贝污染上游**

节点里 `new_state = state.copy()` 是**浅拷贝**，写 `persistence_edges_var[k]` 前必须先 `.copy()`（`backend/domain/flows/nodes/agent_creator.py` 已这么做，function 节点照抄）。

### 3.5 留痕载体（已裁定：job 独立列 + 老列升级）

新增 `radar_event_job.revision_json`（mediumtext）：

```json
{ "gate":   {"level_before":"S1","admitted":true,"rule_hits":["R7","R9"]},
  "by":     [{"node":"rule_gate","changes":[…]},{"node":"auditor","model":"…","cost_ms":8123,"changes":[…]},
             {"node":"self_check","blocked":false}],
  "before": { …复核前的完整事件对象… },
  "after":  { …复核后… } }
```

- **存"修改前全量"而不是只存 diff**：可回溯、可重放、能对照；几 KB/job 可接受。
- **`stats_json` 由 varchar(2000) 升为 mediumtext**：它原本在写入时会被 `[:2000]` **截断**（多事件场景已知会丢），是既存缺陷。
- **不用 `acp_raw_json` 承载**：保持它＝"Agent 原始返回"，便于新旧对照。
- 查询：`radar_event_job.event_id` → 事件；也可直接按 `revision_json` 筛"被复核改过"的 job。
- **触发率即度量**：某规则命中率高 → 该前移回提示词；从不命中 → 这节点白花钱。

### 3.6 编排（已裁定：图内 3 节点 + 条件边）

```
[react_node(agent)] --> [rule_gate(function)] --(条件：经硬闸后仍有分)--> [auditor(agent)] --> END
                                              \--(否则)-------------------------> END
```

- `flow.yaml`：`nodes` 加 2 个节点 + `edges` 加条件边（`condition` 变量取 `persistence_edges_var` 与 `edges_var` 合并，后者优先）。
- **路由条件** ＝ `total_score` 非空 且 `exhibition_related` 且 非 `expired_or_done`（即"至少 S4"）。**不需要**写"或 `rule_gate` 发现异常"——被硬闸判成无分的事件**已不落库**，送 LLM 只是白花钱。
- **已知残留浪费**：图内**不知道**最终会不会落库（已发布/已关闭门控在 `decide_action`，跑在 flow 之后）→ 命中已发布而最终 NOOP 的事件会白花一次复核（本轮 20 家 5 家）；要省掉可把 `auditor` 挪图外（**LLM 复核不需要正文**）。
- 成本：function ≈ **0**；LLM 复核 ≈ 一次无检索调用（**+5~15s / 准入事件**，相对 node1 每事件 8~20 次调用约 **+5~10%**）。

### 3.7 图内外两层审核的分工（已定）

```
[1 解析层 schema]  ->  [2 图内 rule_gate(function)]  ->  [3 图内 auditor(LLM)]  ->  [4 图外 self_check]  -> 落库
  格式/契约校验           确定性规则（含需正文的核验）      语义规则，只降不升         只判过/不过 fail-closed
  不改分                  可修订                          可修订                  不改分（除 level_final 推导）
```

1. **分工**：图内允许**改**；图外只**判过不过**，不通过就不落库 —— 语义上是"**改派 vs 守门**"，不冲突。
2. **同一规则只写一份代码**（关键）：R7–R9 抽纯函数，`rule_gate` 与 `self_check` 都调它。否则"两处审核"会退化成"两套规则"，**口径漂移比没有审核更危险**。
3. **外层永远权威 + 漏检留痕**：同一纯函数跑两遍成本≈0，属**纵深防御**；若出现「图内放过、图外拦住」，必须写进 `revision_json` —— 这正是"图内节点值不值"的指标。
4. **保留 `self_check` 的理由**：它是 fail-closed 的最后一道，挪进图内就失去"独立复核"的意义；且它决定"落不落库"，位置本来就对。**不把 R1–R6 搬进图内**。

### 3.8 「12 个月事实有效期」（已裁定 W1：滚动窗口）

**定义**：有效事实区间 ＝ **评估时刻（`current_date`）往回 12 个月**，**每次评估现算、随时间自然滑动**；**不落在** `radar_event_job.time_from/time_to` 上（那字段仍归采集侧口径，评分侧不用）。

**一处定义、四处分工**：

| 位置 | 职责 |
|---|---|
| 节点1 `react_node`(agent) | 提示词把"12 个月事实边界"写成 **§二 规则条款**（从"输入清单（仅提示）"移入）：**只有窗内事实可作定档依据；更早的只作时间线背景，且须在 `score_reason` 标明超期** |
| 节点2 `rule_gate`(function) | 硬判可计算部分：最早事实 ≥12 个月 → `expired`（两维分与总分置 `null`）；剔除"跑批日戳"证据 |
| 节点3 `auditor`(LLM) | 按下面的**时效核查清单**逐条给结论，**只许向下修正** |
| 图外 `self_check` | 最后守门：同一纯函数再跑一遍，不通过就不落库 |

**节点3 时效核查清单（6 条）**：

1. 主簇**最早事实时间**是哪个？距今天几个月？（须给出日期 + `evidence_no`）
2. 有没有把**重申 / 回顾 / 转载**当成新信号？（比对 `publish_date` 与**实际事实时间**）
3. 有没有**跑批日戳**（`publish_date` == 跑批日，或页面查不到日期）？
4. `signal_time` **有没有出处**、且与所指证据的时间一致？
5. 若声称**重置**：该证据是否**针对同一展厅需求**、是否**新的实质动作**（招采/定单位/签约/施工/资金定向/备案续期）？
6. 结论：**维持 / 降级 / 置 `expired`**（置 `expired` 时总分为 `null`）。

**留痕**：本次评估用的**窗口下界**（`current_date − 12 个月`）写入 `revision_json` / `stats_json` —— 否则事后无法复现"当时按哪个窗口判的"。

**副作用（须知）**：窗口**滚动** ⇒ 老信号会随时间**自然过期**，存量受影响面**逐月扩大**（与 D8 的存量清单同源，见 §5）。

## 4. 形态对比（已裁定取 C）

| 形态 | 组成 | 能判什么 | 成本 | 同源偏差 | 结论 |
|---|---|---|---|---|---|
| **D** | 只加 `self_check` 硬闸 | 日期算术、字段/枚举 | **0** | 无 | 备选（原推荐） |
| **A** | + function 节点 | 正文比对、URL/host 抑制 | ≈0 | 无 | 被 C 覆盖 |
| **B** | + LLM 复核节点 | 语义（quote 支撑、回顾冒充） | +1 次调用 | 有 | 被 C 覆盖 |
| **C** | A + B | 全部 | 同上 | 有（护栏限制） | **已采纳（图内 3 节点）** |

**为什么不是 D**：D 拿不到检索正文（判断"日期是否真来自页面"必须有正文），而且"能改"与"守门"无法分层。
**成本锚点**：全库 5556 家企业只有 **331 家**（6%）有等级 → 复核只发生在准入事件上；准入集合内 S3+ 占 47%~93% → **门限不应设在等级上，而应设在"准入"这一步**（见 3.6 的路由条件）。

1. **先定 D8 口径**（"主簇最早事实时间"如何取、是否允许"新确认重置"）—— R7 写不了，5333 这类拦不住。

3. **先落 R9**（`publish_date == 跑批日` → 剔除该条证据）：**无口径依赖，立刻可做**。
4. **图内 3 节点**：`react_node` → `rule_gate`(function，含正文核验) → 条件边 → `auditor`(LLM，只降不升)。
5. **留痕 DDL**：`revision_json` 新列 + `stats_json` 升 mediumtext（Java DO 同步）。
6. **用 `revision_json` 触发率**，把稳定规则前移回提示词，最终收敛节点数量。
