# 正文任务「域名/站点打散」调度方案

**文档编号**：26091801  
**状态**：方案设计（待评审后落地）  
**范围**：`radar_kb` 统一调度中的 **content（正文抓取）**；发现（discover）仍可按企业顺序。  
**参考输入**：产品侧思路（先取 200 条 → 按 URL 域名分组排序 → 连续同域休息 5～10s）；业界 Mercator / URL Frontier 礼貌抓取结构。

---

## 1. 背景与问题

### 1.1 现状

- 正文抢任务：`claim_content_task` 对 `radar_news_content_task` 使用 **`ORDER BY id ASC LIMIT 1`**（FIFO）。
- 发现成功后会按同一 `company_id` 批量插入大量 PENDING 正文（例如一次 upsert 数十条）。
- 结果：调度长时间连续处理**同一企业、常为同一 `source_url_id`/同站** 的 URL。
- 为防封，执行侧已有 `SiteRateLimiter`（按 `source_url_id` 最小间隔）；但在 **FIFO + 同站长串** 下，限速会变成「同一站上反复 sleep」，**吞吐被人为拉得很长**，其它企业的正文饿着。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 防封 | 连续请求不要打同一 host / 同一信息源 |
| 公平 | 多企业、多站点交替推进，避免一家占满队列窗口 |
| 吞吐 | 在礼貌约束下尽量用「换站」代替「干等」 |
| 改动可控 | 优先在 claim/调度层改造，少动抓取执行器 |

---

## 2. 你的思路（作为基线）

> 先查约 200 个 PENDING → 按 URL（域名）分组 → 排序保证相邻任务不是同一家/同域 → 若被迫与上一家同域，则休息 5～10 秒。

**优点**

- 直观，易实现，和「打乱队列」目标一致。
- 批量窗口内即可显著降低「同公司长龙」。

**需要补强的点**

1. **礼貌键选什么**：仅「域名」偏粗（同域多栏目）；仅「company_id」又可能同司多站仍连打一站。本仓库既有约定是 **`source_url_id`（信息源）**，建议作主键，域名作辅键。
2. **先查 200 再排 ≠ 已抢锁**：必须 **批量 claim（置 RUNNING）** 或 `FOR UPDATE SKIP LOCKED`，否则多实例会抢同一批。
3. **窗口耗尽后**：需再 refill 200，算法要可循环。
4. **与现有限速关系**：排序打散是「调度公平」；`SiteRateLimiter` 是「同站硬间隔」。二者应叠加，而不是二选一。
5. **同域被迫相连时的 5～10s**：合理，但应优先用打散避免相连；相连时的等待可与限速器合并，避免睡两次。

## 3. 业界更稳的做法（Mercator URL Frontier）

经典搜索爬虫（Mercator / II R「URL frontier」）不把所有 URL 放进一个 FIFO，而是：

```
┌─────────────────────────────────────────┐
│ Front：优先级/公平（可选）                │
└─────────────────┬───────────────────────┘
                  ▼
┌─────────────────────────────────────────┐
│ Back queues：每个 host 一条 FIFO         │
│ 调度：只对「已到 next_allowed_time」的 host │
│ 派发 1 条，然后换下一个 host（round-robin    │
│ 或最小堆）                                 │
└─────────────────────────────────────────┘
```

要点：

- **按 host 分队列**，线程/worker 取「到点的队列头」，天然不会连续打同一站（除非只剩一站）。
- **礼貌间隔**：`next_allowed = now + gap`（常取与上次耗时相关，或固定 Crawl-delay）。
- 有活可干时 **换站干活**，而不是死等同一站。

这与你的「分组 + 交替」本质相同，只是把「排一次序」升级成「持续维护 per-host 队列 + 时间堆」。

参考：

- Stanford IR：《The URL frontier》
- Mercator 论文 / 现代综述：[URL frontier design](https://blog.crawlex.net/blog/url-frontier-design/)

## 4. 推荐方案（结合本仓库）

采用 **「批量认领 + 内存 per-key 轮询调度」**（轻量版 Frontier），分两期。

### 4.1 礼貌键（politeness key）

优先级建议：

| 优先级 | 键 | 用途 |
|--------|-----|------|
| P0 | `source_url_id` | 与现有 `SiteRateLimiter`、Agent 闸门一致 |
| P1 | URL host（归一化） | `source_url_id` 缺失时兜底；辅助日志 |
| P2（可选） | `company_id` | 额外公平：轮询时也可在「企业层」再打散 |

**推荐默认**：调度交替以 **`source_url_id`** 为主；若同一 `source_url_id` 下 URL 极少、但仍希望跨企业，可在 refill 时对窗口做 **company 轮询二次交错**。

### 4.2 调度流程（目标态）

```
unified content 轮次：
  1. 若内存队列空：batch_claim(N=200) → RUNNING，写入内存 Frontier
  2. Frontier.pop_next()：
       - 在「已冷却」的 key 中 round-robin 取一条
       - 若没有已冷却的 key，但有未冷却任务：
           sleep(min(各 key 剩余冷却, max_wait))
           或暂时跳过该 key，取其它 key（优先换站）
  3. execute(task)
  4. 更新该 key 的 next_allowed_at（固定间隔或 上次耗时×系数）
  5. 任务成功/失败回写 DB；队列空则回 1
```

与你思路的对应：

| 你的想法 | 落地点 |
|----------|--------|
| 先查 200 | `batch_claim(limit=200)` |
| 按域名分组 | 按 `source_url_id`（+host）建 back queue |
| 连续不同家 | round-robin / 时间堆，默认相邻不同 key |
| 同域休息 5～10s | `next_allowed_at = now + uniform(5,10)` 或配置项；与 `NEWS_CONTENT_SITE_MIN_INTERVAL_SECONDS` 取 **max** |

### 4.3 打散算法（窗口内，可独立单测）

对 batch 内任务做一次 **交错展开**（实现简单，适合 P0）：

```
groups = group_by(politeness_key)  # 组内保持 id ASC，保局部公平
result = []
while groups 非空:
    按「组剩余长度」或 round-robin 取一个组，pop 队头进 result
    （可选）禁止与 result[-1] 同 key；若只剩同 key，允许并标记 need_gap=True
```

更优（P1）：不预排死序列，而是 **运行时** 从多队列取「冷却完成」的队头（真正的 Frontier），适应执行耗时抖动。

### 4.4 与现有组件关系

| 组件 | 现状 | 改造建议 |
|------|------|----------|
| `claim_content_task` | 单条 `ORDER BY id` | 新增 `claim_content_tasks_batch(limit)`，`FOR UPDATE SKIP LOCKED` |
| `SiteRateLimiter` | 按 `source_url_id`；**每次 execute 新建实例**（radar_kb 路径几乎无效） | 进程级单例；与 Frontier 的 `next_allowed` 对齐 |
| `has_active_crawl` 让路 | 发现进行中则不跑正文 | 保持；发现清空后再 refill 正文 |
| 空表步长 | 正文空则 60s 不查 | batch 全失败/空才触发；有内存队列时不查库 |

### 4.5 多实例

- Claim 必须用 **`SKIP LOCKED`**，各实例认领不同子集。
- 限速仍是进程内；多实例时同站有效间隔会变短 → 文档注明「正文 worker 建议单实例」，或后续用 Redis 共享 `last_fetch_at`（非本期）。

## 5. 方案对比

| 方案 | 防封 | 公平 | 吞吐 | 复杂度 | 建议 |
|------|------|------|------|--------|------|
| A. 保持 FIFO + 加大同站 sleep | 中 | 差 | 差 | 低 | 不推荐 |
| B. 你的：200 批 + 域名交错 + 同域 5～10s | 好 | 好 | 较好 | 中 | **P0 可落** |
| C. Mercator 式 per-key 队列 + 时间堆 | 最好 | 最好 | 最好 | 中高 | **P1 目标态** |
| D. SQL `ORDER BY RAND()` | 不稳定 | 一般 | 差（全表） | 低 | 否 |

**结论**：以 **B 快速落地**，数据结构按 **C 预留**（内存 `dict[key, deque]` + `next_allowed`），避免先写死「一次性 sort 列表」再推倒。

## 8. 风险与验收

| 风险 | 缓解 |
|------|------|
| 批量 claim 后进程崩溃，任务停在 RUNNING | 沿用/加强 `reset_stale_content_tasks` |
| 窗口内只有 1～2 个站 | 接受同站 gap；日志告警「低多样性」 |
| 打散后「老任务」更晚执行 | 组内仍 `id ASC`；跨组轮询，不刻意饿死老 id |
| 与发现让路叠加 | 发现 active 时不 claim 新正文；已 claim 的可跑完或放回（二选一，建议跑完当前内存队列） |

**验收**

1. 连续 100 次正文执行，相邻 `source_url_id` 相同比例显著下降（目标 &lt; 10%，单站窗口除外）。
2. 多企业 PENDING 时，1 小时内至少 N 家企业有成功正文（相对 FIFO 提升）。
3. 同站 QPS 不超过限速配置；封禁/403 率不升。
4. 僵尸 RUNNING 发现不再导致正文长期 0 消费（配 P1 超时回收）。

## 9. 小结

- **可以、也应该**从「按 id 顺序单条领取」改为「批量认领 + 按站点/信息源打散」。
- 你的「200 + 分组交错 + 同域间隔」是正确方向，与业界 Frontier **同构**。
- 本仓库落地时礼貌键优先用 **`source_url_id`**，域名作补充；限速用**进程单例**与 gap **合并**。
- 推荐 **P0 交错队列 → P1 时间堆 Frontier**，在防封的同时用「换站」换吞吐，而不是靠拉长全局休息。
