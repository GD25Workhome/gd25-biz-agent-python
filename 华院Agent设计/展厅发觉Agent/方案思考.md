# 当前想法

1. AnySearch表现一般
2. 尝试使用更多工具进行查询，然后把结果汇总到一起
3. 第一个节点先进行前期发散式查询，交给一个子Agent去找这家企业的信息，然后返回比较合适的查询语句（3～5个）
4. 后续节点根据查询条件，并行的调用不同工具，依次调用查询工具进行查询，没个工具都总结查询结果返回。（如果有结论，需要给出网站来源，以及网站为何你觉得可以提供证据）
5. 最终总结节点，总结结论，生成最终返回的结果。
6. 借助材料【千问的工具建议.md】

# 是否可行的思路总结

**结论：可行。** 目标形态与现有 `huayuan_radar_event_agent`（单节点 ReAct + AnySearch）差距明确，但本仓库的 LangGraph 流程引擎**已经支持多节点串行 + 条件边**；「真并行 fan-out」需要额外设计，不必一上来改引擎。

## 1. 现状 vs 目标


| 维度   | 当前                                                                 | 目标（本文件想法）                                        |
| ---- | ------------------------------------------------------------------ | ------------------------------------------------ |
| 图结构  | 单节点 `radar_event_react_node` → END                                 | 至少 3 段：发散规划 → 多工具检索/摘要 → 终评汇总                    |
| 工具   | 仅 `anysearch_web_search` / `anysearch_extract`                     | 多源组合（博查主搜 + AnySearch 补漏 + Tavily/Firecrawl 深读等） |
| 检索控制 | 全靠 prompt 内「阶段 A/B/C」让同一 ReAct 自己扇形展开                              | 查询词由子 Agent **显式产出 3～5 条**，再交给下游执行               |
| 证据形态 | 终态一次吐出评分 JSON                                                      | 中间态每工具先「结论 + URL + 为何可作证据」再汇总                    |
| 对外契约 | `POST .../radar-event-score` 解析**最后一条 AI 文本**为 `radar_event_score` | **可保持不变**（仅终评节点输出该 JSON）                         |


当前 `flow.yaml` 实质是「一个 create_agent(ReAct) 包办搜、判、打分」。瓶颈不只是 AnySearch 召回，还有：**规划 / 检索 / 评分耦合在同一 prompt 里**，模型容易早停、漏意图、或把坏链当证据。

## 2. 引擎能力边界（改编排前先认清）

**已具备（改配置即可用）：**

- 多 `agent` / `function` 节点串行（如 `medical_agent_v6.3`）
- 条件边按 `edges_var` 路由（如 `plan_execute_agent`）
- 节点间用 `edges_var` / `prompt_vars` 传结构化中间结果
- 单节点内挂多 tool；ReAct 一轮可发多个 tool call（**模型级并行**，非图级 fan-out）

**尚不具备（真「图级并行多工具」要额外做）：**

- `GraphBuilder` **无** LangGraph `Send` / map-reduce 式一对多扇出
- 同一 `from` 多条 `always` 边是串接语义，不是并发执行多个子图
- 工具注册表目前只有 AnySearch；博查 / Tavily / Firecrawl / 巨潮需先封装再挂到节点

因此：「并行调用不同工具」建议拆成两层理解——

1. **短期可落地**：查询规划节点产出 query 列表 → **一个（或少数）检索 Agent** 带多工具，按 query×工具路由（prompt 或轻量 function 节点 `asyncio.gather`）→ 终评节点。
2. **中期可选**：新增 `map`/`parallel` 节点类型或自定义 function，对「每条 query × 每个搜索源」做真并发，再 reduce。



## 3. 推荐改造形态（与现有引擎对齐）

```text
[query_planner]  →  [evidence_gather]  →  [score_summarizer] → END
   无/轻工具           多搜索+extract         无工具，只评只输出
   产出 3～5 query      每条命中带 source 理由   固定 radar_event_score JSON
```



### 节点职责

1. **query_planner（发散子 Agent）**
  - 输入：`company_json`、时间窗、`query_hint`
  - 可先用 1～2 次广搜了解主体别名/主业（可选）
  - 输出结构化：`queries: string[3..5]`（单意图、公司名加引号），写入 `edges_var`
  - Prompt 吸收「千问」的语义发散，但**不要**在此节点打分
2. **evidence_gather（执行 + 分工具摘要）**
  - 工具建议（对齐《千问的工具建议》）：
    - **主**：博查（中文招采/公告/新闻）
    - **补**：现有 AnySearch
    - **深**：Tavily advanced 或 Firecrawl（摘要不够时）
    - **专项（可选）**：巨潮/交易所公告检索
  - 对每条有效线索强制结构化：`title / url / quote_or_summary / why_evidential / tool_name`
  - 无效页（Example Domain / 404 / 验证码）进 `discarded`，禁止据其给分
  - 输出：`evidence_briefs[]` + `discarded[]` → `edges_var`（**仍不打最终分也可**，或给粗筛标签）
3. **score_summarizer（终评）**
  - **无工具**，只读上游 briefs
  - 复用现有评分枚举与准入规则（实体空间 + 项目动作；有展厅无动作拒识等）
  - **唯一**产出当前 API 解析的 JSON，保证路由与 Schema 不用大改



### 与「plan_execute」的关系

若希望「规划步可重试」，可复用现成 `planner → plan_executor → replanner` 模式：planner 产出的 step = 单意图 query，executor 调搜索工具。对本任务而言，**固定三节点流水线更轻、更可控**；线索挖掘场景查询空间相对封闭，不必一上来上动态重规划。

## 4. 改造成本分层


| 层级     | 内容                                                        | 工作量 | 收益                       |
| ------ | --------------------------------------------------------- | --- | ------------------------ |
| L0 工具  | 注册博查（优先）+ 保留 AnySearch；可选 Tavily/Firecrawl                | 中   | 直接改善中文召回                 |
| L1 编排  | 拆成 planner / gather / summarizer 三个 agent 节点 + 中间 JSON 约定 | 中   | 解耦「发散 / 取证 / 打分」，可控性明显上升 |
| L2 并行  | function 节点内对多 query×多工具 `gather`，或扩展 GraphBuilder        | 中高  | 时延下降；逻辑更清晰               |
| L3 专项源 | 巨潮公告工具                                                    | 中   | 招采类召回率                   |


**建议落地顺序：L0 → L1 → 再视 latency/召回决定 L2/L3。** 不要先改 GraphBuilder。

## 5. 风险与约束

- **对外契约**：终评节点必须仍输出可被 `parse_radar_event_score_from_ai_text` 解析的 JSON；中间节点勿抢最后一条 AI 消息（或路由改为显式读 `edges_var.radar_event_score`）。
- **成本与配额**：多工具 × 多 query 会放大调用次数；沿用 `HuayuanRadarEventContext` 的 search/extract 限额，并按工具分别计数。
- **评分纪律**：发散与「隐性需求」只影响**检索覆盖**；终评仍应遵守现有「禁止自创档位 / 无项目动作不准入」，避免销售向幻觉抬分（除非产品明确要改枚举）。
- **上下文长度**：gather 节点应要求「短摘要 + quote≤200」，禁止把全文堆进终评。
- **可观测性**：Langfuse tag 按节点区分（`planner` / `gather` / `summarizer`），便于对比 AnySearch-only 基线。



## 6. 一句话决策

**可以对当前工作流与 LangGraph 编排做改造，且优先用「三节点流水线 + 多搜索工具」在现有** `GraphBuilder` **上完成；「图级真并行」不是前置条件。** AnySearch 不必废弃，降为补源；博查作主搜更贴合上市企业中文信源场景。
