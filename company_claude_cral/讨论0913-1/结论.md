> 时间：2026-09-13
> 议题：是否可借助 Claude 在当前项目实现更稳定的网页内容抓取 Agent
> 输入：`GD26_harness_Geek04/claudeAgentSDKTest`（ClaudeTest01/02 实验）+ `company_news_crawl`（MVP + 实验记录）

---

## 一、总判定

**可行，值得做。但"证据可信度"分三块，差别很大 —— 不能打包接受。**

| 判断 | 可信度 | 依据 |
|------|--------|------|
| 现有实现的站间通用能力很弱 | **高（实测）** | 6 站 A/B；平安 `index_2.shtml` 有 25 条新链，规则版命中 0/25 |
| 交给 Agent 后翻页能过 | **中（单站单次，n=1）** | 平安 5 页 125/125，但只跑过 1 个站 |
| 详情内容抽取也一起变好 | **低（实测反而没变好）** | ClaudeTest01 正文仍混入裸日期与公示噪声 |
| 可生产化 | **未验证** | 成本/延迟/并发/SDK 依赖/凭证全空白 |

## 二、三条与传统判断不同的结论

### 2.1 Agent 的价值在"辨识"，不在"发现" —— 这决定它值不值这个钱

实验里 `simplify_list_html()` **已经用规则**做了同域过滤、去重、URL 归一化、`date_in_text` 提取。Agent 拿到的是一份**洗干净的链接清单**。

所以：

| 环节 | 谁干的 |
|------|--------|
| 找到链接、洗干净、归一化 | **规则** |
| 认出哪条是新闻、哪条是翻页 | **Agent** |
| 抓 HTML、抽正文 | **规则** |

→ **Agent 不提高抓取能力上限，只提高"规则未命中先验时的判断力上限"。**

**由此得出关键经济论点：** 单站 $0.48~0.82，相对纯规则（成本 0）是**净增支出**。所以：

> 优化方向不是"让 Agent 更便宜"，而是"让 Agent 调用次数更少"。

→ **Agent 的正确用法：冷启动一次性定界 → 沉淀 `site_profile` → 日常热运行零 LLM。**

（这与既有 `实验260912-1/04-设计取向.md`"Agent 只做运行期失败修复"的**实质分歧**：逐次修复是逐次付钱，沉淀是一次性付钱。）

### 2.2 实例确认：Agent 版详情抽取并没有变好

`ClaudeTest01` 的 `published_at 20/20` 是**列表字段兜底**撑出的假象 —— 标题/日期走的都是 `fallback_title`/`fallback_date`，不是在详情页抽对的。

正文实测仍脏，抽查 3 篇**开头都是裸日期**：

```
2026-08-26
35年前，中国正式加入APEC大家庭。今年，中国第三次担任APEC会议东道主……

2026-08-26
平安银行（平安银行，深交所000001）今日向深圳证券交易所提交了2026年半年度业绩报告……
```

详情页的 `h5` 日期被吞进了 `content_text`。因为 `ClaudeTest02` 的裁判根本不检查正文，这个缺陷两次实验都没被拦住。

→ **"翻页发现"与"详情抽取"是两个独立难题，必须分别设裁判，不能打包论证。**

### 2.3 翻页失败的直接原因：`pagination_urls` 是 `sorted()` 后当 FIFO 用

源码核对（`list_extractor.py` / `crawl_one.py`）：

- `extract_pagination_links()` 返回 `sorted(list(pagination_urls))` → **第 1 页与第 20 页等价，"下一页"没有任何优先级**
- `crawl_one.py:128` 的 `all_list_items[:max_articles]` 截断发生在**详情抓取之前**（step 5 在 131 行）→ `--max-articles` 只省详情请求，**并未减少翻页请求**
- `SiteProfiler` 的 `pagination_keywords` 里**有** `index_`（平安翻页形如 `index_2.shtml`，理论上能命中）→ 说明失败在**发现之后**（入队/排序/消费），不是发现规则

## 三、一处重要勘误（对既有结论，也对我自己的初稿）

### 既有"翻页生效 1/6"—— 数字是对的

我初稿断言"0/6，华岭股份是假阳性"，**复核后判定为我误判**：

| 代码 | 公司 | A | B | 交集 | only-B | 判定 |
|------|------|---|---|-----:|-------:|------|
| 920139 | 华岭股份 | 39 | 64 | 39 | **25** | **真增量** |

**推翻我初稿的两条证据：**
1. `交集 = A_count = 39` —— B 是 A 的**严格超集**，A 的 39 条全被 B 包含。若是"截断位置不同"，A 应有 B 没有的尾部（`only_A > 0`），而实测 `only_A = 0`
2. 新增 25 条 URL 形态不同（`/news/html/?15.html` 这类文章 ID 页 + 带 `page=1` 的列表 URL）→ 是**第二个列表页**的产物形态

**但归因需补充：** 华岭能成功，是因为它的 URL 都落在 `/news/` 下、**撞上 `NEWS_KEYWORDS` 里的 `news` 子串**（实测这三个 URL 各只命中 `news` 一个词；`NEWS_KEYWORDS` 里**没有** `html` —— 我初稿这里也写错了）。是**关键词蒙中**，不是翻页逻辑正确。

**净结论：** 翻页能力 = 1/6，那 1 站靠关键词巧合；在唯一被人工逐条核对的平安上明确为 **0/25**。

## 五、能力边界（必须划清，否则会浪费钱）

| 问题类型 | 例子 | Agent 能治吗 |
|----------|------|--------------|
| **定界类** | 入口不是新闻列表、翻页不跟随、噪声链接混入 | ✅ **能，已验证** |
| **抽取类** | 标题变导航、日期空、正文含公示噪声 | ⚠️ **部分**，且实测未改善 |
| **通道类** | 反爬、JS 渲染、需登录 | ❌ **不能** —— 拿不到 HTML 就无从判断 |

→ 6 站里**没有一站的失败主因被证实是反爬**。现在上 Playwright 是在给一个还没被证实的瓶颈买单。

## 六、成本模型

| 场景 | 单站 | 2904 站 |
|------|-----:|--------:|
| 纯规则（现状） | $0 | $0 |
| 日频 × 全库 × Agent | $0.48~0.82 | **$1400~2400 / 轮** ❌ |
| 冷启动一次性 Agent | $0.48~0.82 | $1400~2400 / 一次性 ⚠️ |
| **规则自动推导 profile** | $0 | $0 ✅ 优先榨干 |
| 上述 + Agent 只兜底 | 仅兜底站花钱 | ✅ **目标形态** |

**成本控制三个抓手（按性价比）：** ①规则自动推导 profile（零成本）②按站族共享推导器 ③分批冷启动。

## 七、待决策的三个问题

1. **凭证路线**：走本机第三方 Anthropic 网关（`unidtai.com`），还是走本工程已有的 Ark/豆包网关（`OPENAI_BASE_URL`）？后者零新增基建但要放弃 Claude Agent SDK。**影响全部代码。**
2. **Agent 产出**：固化成 `site_profile`（本文主张），还是运行期按需调用（既有 04 主张）？**决定成本模型是否成立。**
3. **范围**：奔 2904 站，还是只服务 235 个 hard/portal/SPA？

> 问题 3 的答案会显著简化设计 —— 若只服务难站，profile 体系的复杂度可大幅削减。

## 八、结论一句话

**不是"用 Agent 替换爬虫"，也不是"Agent 只做失败修复"。**
是 **规则做确定性抽锁 + Agent 做定界/清洗 + 沉淀 site_profile 回到规则** 的两层闭环。
单站篇篇开 Agent 不成立（不是效果不好，是经济性不成立）；**按站族 + 冷启动一次性摊销**才成立。
