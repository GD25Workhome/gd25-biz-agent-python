# 《26092102 列表与正文跨站并发、同站串行设计》评审

**被评审文档**：`ai_docs/26092102-列表正文跨站并发同站串行设计.md`  
**评审依据**：现网代码（`radar_kb/`、`backend/domain/news_content/`、`backend/domain/news_crawl/`、`radar_crawl/adapters/`）+ 生产 MySQL（`unidt_exhibition`）实测数据 + `26092101`（现状）、`26091801`/`26091802`（前置探讨）、`26091608`（巨潮 403）  
**结论**：**方向正确、抽象选得对（SiteGate + 双池 + list 优先三层），但存在 4 个会直接推翻目标的设计缺陷（P0）和 6 处落地必需信息缺失（P1）。当前状态可作为"概念共识稿"，不宜直接进入接口/落地设计。**

## 1. P0：会推翻目标的设计缺陷

### P0-1 「站点键 = `source_url_id`」选错了层级，直接满足不了需求 #3

文档 §2 定「站点键：优先 `source_url_id`；缺失回退 `host`」。实测两边都不成立：

**(a) `source_url_id` 单独不唯一。** 它来自两张独立自增的表：`radar_company_source_url` 与 `radar_global_source_url`（`radar_kb/repository.py:214-238` 的 `_resolve_source_table` 正是靠任务行里的 `source_ref_type` 才分辨得出来）。任务行里**已经带 `source_ref_type`**（`repository.py:399-403` 解析、`:567` 写正文任务时一并写入）。

- 隐患已存在于现网：`radar_global_source_url` 只有 1 行且 `id=1`（巨潮 `www.cninfo.com.cn/new/fulltextSearch/full`）；company 侧目前 id=1 不存在（实测 `WHERE id=1` 空集），所以**尚未触发**。但 `ContentFrontier` 的礼貌键就是裸 `src:{id}`（`radar_kb/content_frontier.py:43-46`），一旦两边 id 撞上，巨潮的 23 条正文任务会和企业源 #1 的正文互相锁在同一个键上。
- 新设计照抄该键 = 把这个 bug 固化进 SiteGate。

**(b) 用 `source_url_id` 做键会漏掉"同站"。** 实测 2903 个 company 源对应 2899 个 host，host 重复的只有 4 组，但都是真会影响外发请求的：

```
mp.weixin.qq.com    -> 源 1955, 2188
dnspod.qcloud.com   -> 源 2052, 3171
hengli.com          -> 源 2121, 2644
crrcgc.cc           -> 源 2154, 2444
```

另有 company 源 3511（`zccninfo.com`）与 global 巨潮源同域族。这些组在 `source_url_id` 键下**会在同一 host 上并发两个请求**——需求 #3 写的是"同一站点"，这里就破了。数量虽小（4 组），但闸门的键一旦选错就是系统性的，靠"数据里恰好只有 4 例"兜底不可接受。

> 注：`26091608` 的根因是 `static.cninfo.com.cn` 的 WAF 按 TLS 指纹拦截，**与频率/IP 无关**，因此本条的动机是"需求 #3 的语义正确性"，不是"避免晋级 403"。但该文 §8 结尾明确要求巨潮侧"保持低频"，所以同域并发的争议应显式记录，不要用 403 归因去论证。

**建议**
- SiteGate 的**主键用归一化 host**（`content_frontier.extract_host` 已有实现，去 `www.`、小写），"站"的定义就是 host；
- 在此之上再叠一层 **source 键**承载礼貌/优先级语义：`key_source = (source_ref_type, source_url_id)`；
- 若不想两级，最低限度也要把键改成 `(source_ref_type, source_url_id)`，并**显式列出** `mp.weixin.qq.com` 这类同域多源被当作独立站的处理口径（文档目前把 host 当作"缺失兜底"，方向反了：host 才是"同站串行"的定义，source 是礼貌键）。
- 顺带修 `polite_key_for_task` 的 `src:{id}` → `src:{ref_type}:{id}`。

### P0-2 §4.1 硬优先 `N_c_low=0` 默认可开 → 正文被永久饿死，与需求 #2 直接冲突

文档 §4.1 把「有 list 可跑 → `N_c_low=0`（详情暂停接新任务）」标为**默认可开**；§10 又承认「List 长期占满导致详情饿死」并建议软优先。两处默认值自相矛盾，且**按实测数据，硬优先会让正文小时级停摆**：

| 事实 | 数据 |
|------|------|
| 发现任务按源灌入 | `radar_news_crawl_task` 现存 492 条 news_html（462 SUCCESS / 31 FAILED），且存在**同一源重复行**（id=1、id=2 的 `source_url_id` 都是 3675、seed_url 相同）。company 源共 2903 个 → 一轮完整发现会灌入 ≈2900 条 |
| 列表翻页间隔将放大一个量级 | 现状 `crawl_tools._fetch_html` 的间隔是 `NEWS_CRAWL_REQUEST_INTERVAL=0.4`s（`backend/domain/news_crawl/agent_runner.py:162-164`、`.env.example:44`）。改由 5~9s 闸门后，`max_pages=3` 的一个列表任务仅冷却就 ≈10~18s，加 Agent 多轮 LLM，单任务 ≈30~60s |
| 清空一轮发现所需时间 | `N_d=2~4`、单任务 ≈45s → ≈9~18 小时 |

这 9~18 小时里 `discover_pending_or_running` **恒为真** → `N_c_low=0` → 正文一条不跑。"正文并发"这个需求被自己的优先级策略抵消。文档全程没有量化这个耦合。

**建议**
- 默认取**软优先**（`N_c_low ≥ 1`），把「硬优先」降级为可选开关；
- 硬优先必须配**有界抢占**：如「连续发现 ≥ T 分钟后强制放行正文 N_c 个槽位」，或「发现积压 < 阈值才允许硬优先」；
- 明确定义 `discover_pending_or_running` 的口径（全局所有 kind？同 kind？同源？）——现网 `has_active_crawl_tasks` 是**按 kind 的全局查询**（`repository.py:787-810`），照搬会得到"有一个源在发现就全站禁正文"的粗粒度，这正是文档想摆脱的。
- §10 的「发现空窗周期性抬升详情」要给出可实现的判据（时间片？积压比？），不能只是一句缓解。

### P0-3 §2 伪代码把「持锁冷却」与「时间戳冷却」混在一起，冷却会吃掉池子槽位

伪代码写的是：

```text
async with site_gate.acquire(site_key, priority=...):
    # 2) 若 now < next_allowed_at → sleep 差值     ← 在锁内 sleep
    ...
    finally: next_allowed_at = now + random(5,9)
```

这两种语义（持锁串行等待 vs 释放后按时间戳节流）混写了，产生两个后果：

1. 该站锁在整个 5~9s 冷却期内不可用，等待队列的优先级只在"锁空闲"时才有意义；更糟的是**发请求的协程在这 5~9s 里仍占着池信号量**。
2. 若某时刻"处于冷却期的站点数 > N_c"，池子被全部占满在 sleep 上 → **头阻塞（HOL）**，文档 §10 的"用跨站并发补吞吐"失效。

**建议**
- 明确写成：**请求一结束即释放锁，冷却只体现为 `next_allowed_at` 时间戳**（这样高优先级任务到达时能立刻抢到锁、只等时间戳）。
- 池子不要 spawn「未到点」的任务：把 ready 判断前移到 gate（形态上就是现有 `ContentFrontier.pop_ready` 返回 `wait_sec` 的推广，`content_frontier.py:129-175`），或让 gate 暴露 `next_ready()` / `wait_ready()` 供 refill 侧挑站。
- 补一条量化关系：`N_d + N_c` 与「同一时刻处于冷却/排队的站点数」的关系，否则 HOL 会在站点数少、单站积压多时（实测源 2097 独占 731 条正文任务，占全部 7772 条的 9%）真实发生。

### P0-4 §8「避免双重睡眠」只清点了一半，且漏掉了最敏感、最难接的 cninfo 链路

文档 §8 列的是「Frontier gap + SiteRateLimiter → 收敛进 SiteGate」。实际的限速点至少还有两处，而且第 4 条是**同步路径**：

| # | 限速点 | 位置 | 落地后怎么处理 |
|---|--------|------|----------------|
| 1 | `ContentFrontier._compute_gap` 5~10s | `radar_kb/content_frontier.py:189-195` | 收敛进 SiteGate，**删掉**（否则 5~9 与 5~10 叠成 10~19s） |
| 2 | `SiteRateLimiter.acquire` 按 `source_url_id`，**start-to-start 间隔且无互斥** | `backend/domain/news_content/rate_limiter.py:41-60` | 收敛进 SiteGate。**注意：它不保证"同站 ≤1 in-flight"**（第 2 个调用者按 `_last_at` 排到点即发，第 1 个若仍在飞就重叠了）。文档应把这点写出来——这正是"为什么必须换成带 Lock 的 SiteGate"的理由 |
| 3 | 列表 Agent 内部 `request_interval`（默认 0.4s，闭包内 `asyncio.Lock`） | `backend/domain/news_crawl/crawl_tools.py:231-280` | 由 SiteGate 接管 |
| 4 | 巨潮适配器 `threading.Lock` + **持锁 sleep**，间隔 `base 5s + U(0,4)` | `radar_crawl/adapters/cninfo.py:52-114`（由 `radar_kb/config.py:113-117` 注入） | **文档完全没提** |
| 5 | `ChannelBudget.request_interval_ms` 后置 sleep（news_html 默认 0，cninfo 显式 0） | `radar_kb/scheduler.py:278-280`、`registry.py:35-54` | 确认为 0/删除，避免恢复后叠加 |

第 4 条有两个硬问题：

- **双重节奏**：cninfo 同时受 adapter（5~9s）与新 SiteGate（5~9s）→ 实际 10~18s，正是 §8 声称要避免的量级。
- **同步 vs 异步闸门**：`CninfoPdfExecutor.execute` 是**全同步**调用（`radar_kb/executors/cninfo_pdf.py:42` → curl_cffi，无 await）。放进 asyncio 内核只能 `to_thread`，而 `to_thread` 里**无法 await `asyncio.Lock` 版 SiteGate**。要么做**同步版闸门**（`threading.Lock` + `time.sleep`）并与异步版**共享同一份 `next_allowed_at` 状态**，要么把 cninfo 排除在站点串行之外并显式记录"巨潮由 adapter 自管节奏"。文档 §11 的落地顺序（先正文池、再列表池）也完全没覆盖 cninfo。
- 反过来说：cninfo 全通道只有一个 global 源（`radar_global_source_url` 仅 1 行），23 条正文任务，**在 SiteGate 下天然并发=1**——文档应写明"巨潮不参与跨站并发收益"，避免验收时被误判失败。

## 2. P1：落地必需但文档缺失的信息

### P1-1 认领层缺少「同源去重」，N_d 个槽位会砸到同一个源

文档 §3 写「Discover：按 kind / 源公平取若干条（**站点数少时 N_d 自然受限**）」——方向与数据相反：

- `claim_crawl_task` 是 `ORDER BY id ASC LIMIT 1 FOR UPDATE`（`repository.py:88-139`），**既不按 source 去重，也没有 `SKIP LOCKED`**；
- 表里同一 `source_url_id` 存在多行（实测 id=1、id=2 同为源 3675）；
- 并发 N_d 后，3 个槽位很可能全是同源/重复任务 → 三个 Agent 抓同一个站（白烧 LLM 配额），然后一起排在**同一个** SiteGate 后面（槽位空转）。"站点数少时自然受限"并不成立：受限的是**入队顺序**，不是并发选择。

**建议**：claim 侧加"在跑 source 不重复"判据（DB 侧过滤在跑集合，或内存侧 gate 已有者跳过）；`SKIP LOCKED` 文档已提，建议与去重一并写进 claim 伪代码。

### P1-2 租约超时 vs 闸门排队：长排队会被自己的 stale reset 回收

`_content_once` 每次 refill 都执行 `reset_stale_content_tasks(conn, 1800)`（硬编码 1800s，`radar_kb/scheduler.py:291`），crawl 侧用 `crawl_stale_timeout_sec`（默认 1800）。

并发化后任务"**先认领、再在 SiteGate 队列里等**"，而等待时长在严格优先级下**无上界**（见 P0-2/P2-3）。租约一旦到期，任务被打回 PENDING → 另一协程再认领 → 同站两条在飞（进程内闸门还挡得住，多进程/多实例就是真重复抓），并重复消耗 Agent 配额。

**建议**：把"认领时机"后移到**拿到站点闸门之后**（顺带解决 §4.3 说的"占着槽位排长队"），或明确"排队等待不计入租约"。二者选一必须写进设计，否则 §7「任务租约」与 §12 的成功标准 4 都是空的。

### P1-3 DB 并发访问没设计，`asyncio.to_thread` 只写了半句

现状是**每轮一个连接**贯穿 claim→finish 全流程（`radar_kb/scheduler.py:289-394`、`:216-228`）。并发池里 N 个任务各自写库时：

- 单连接被多个 `to_thread` 线程并发使用会串包 → 必须**每 task 一连接**或连接池；
- `to_thread` 用的是默认 executor（默认 32 线程），`N_d + N_c` 一大，DB 调用会排在 executor 上反而成瓶颈；
- `discover_post_success` 的"单事务"语义（`26092101` §3）必须保持。

文档 §5 只写「同步 pymysql：`asyncio.to_thread`」，建议补齐：连接获取/归还策略、事务边界、executor 容量与 `N_d+N_c` 的关系。

### P1-4 进程内单例与"独立事件循环"的绑定关系没写

`content_fetcher._client`（进程级 `httpx.AsyncClient` 单例，`backend/domain/news_content/content_fetcher.py:39-56`）、`get_milvus_chunk_store()`、`get_shared_site_rate_limiter()`（`rate_limiter.py:67-81`）目前都在"每任务一个 `asyncio.run`"下被**跨循环复用**（httpx 连接池是绑 loop 的，现状其实是隐患）。新设计恰好能修好，但前提是文档要写明：

- 这些单例必须绑定**调度器那个长期 loop**；若 FastAPI 进程内另有使用者，要各自实例化；
- `embed_stub_document` / `embed_full_document` 内部也是 `asyncio.run`（`radar_kb/embed.py:19-23`），并发化时必须改成直接 await 并加 Embed 信号量——文档 §8 提了 Embed Semaphore，但没说这两处也得一起拆。

### P1-5 「禁止绕闸」的范围要扩大到所有 worker 入口

`NEWS_CONTENT_WORKER_IN_APP` 的 legacy worker（`backend/domain/news_content/worker_loop.py`，自带 claim / stale reset / 自己的循环）与 legacy `radar_crawl` 只在"radar_kb 已启动则跳过"这一层互斥（`26092101` §1）。新内核上线后若 legacy 路径仍可开启，它会**绕开 SiteGate 直接打站**，需求 #3 直接破功。文档 §10 已写「重试也必须经 SiteGate，禁止绕闸」，建议把范围写成"**任何出站 HTTP 入口**"，并在 §11 落地顺序里加一步"关闭/改造 legacy worker 入口"。

### P1-6 Agent 侧并发是独立资源，需要第三条闸门

列表发现每个任务 spawn 一个 `claude` CLI 子进程（SDK 子进程模型，`backend/domain/news_crawl/agent_runner.py:196`），`N_d=2~4` 即常驻 2~4 个子进程；正文兜底 Agent 并发时再叠加。文档 §10 只说"List Agent 重、配额易打满"，建议与 Embed Semaphore 并列，明确一条 **Agent 并发闸门**（并说明它与网关配额、`AgentFallbackGuard` 日配额的关系）。

### P1-7 吞吐上界推导缺失（验收标准 3 没有量）

给定 SiteGate 语义后，单站完成时间有硬下限：`该源积压条数 × 5~9s`。实测源 2097（`source_ref_type=company`，`source_url_id=2097`）独占 731 条正文任务（全量 7795 条中企业源 7772 条，它占 9%）→ 仅这一个源就要 ≈66~110 分钟才能清完，`N_c=8` 也帮不上（同站串行）。文档建议补一段"吞吐上界 = f(N_c, 站点数, 单站积压分布)"，否则 §2.6 的成功标准 3（"list 吞吐不被详情挤死"）无法判断达标。

## 3. P2：口径与表述问题

### P2-1 验收标准 2 是恒真式，且当前无法测量

> 「相邻请求间隔 ∈ [5, 9]s（允许配置）」

`random.uniform(5,9)` 下只要不排队，间隔必然落在 [5,9]；一旦排队必然 >9s。应改成：**相邻请求 start 间隔 ≥ 5s；同站无竞争排队时 ≤ 9s**。

更关键的是**可测量性**：现在没有任何 per-request 时间线。`SiteRateLimiter` 只有 `_last_at`、`ContentFrontier` 只有 `next_allowed`，都不落日志；§11.5 提了指标，但 §2.6 的验收口径要先落到"哪条日志/指标能证明"。建议在 §11 里明确一项前置工作：**SiteGate 每次 acquire/release 打一条含 `site_key / priority / wait_ms / gap_ms / in_flight` 的日志**。

### P2-2 5~9s 与现网配置不一致；冷却起点改变是**放宽**

- 现网是 5~10（`RADAR_KB_CONTENT_SAME_KEY_GAP_MIN_SEC=5` / `MAX_SEC=10`，`radar_kb/config.py:143-148`），另有 `NEWS_CONTENT_SITE_MIN_INTERVAL_SECONDS=2.0` 与之取 max（`config.py:150-161` + `content_frontier.py:195`）。
- 更值得写进文档的：**冷却起点从"任务结束"改为"请求结束"会提高单站请求密度**。现状 `mark_fetched` 在任务（含 embedding + 写库）返回后调用，有效间隔 ≈ `embed 耗时 + 5~10s`；改后变成纯 5~9s。这是**放宽**而不是收紧——对绝大多数站无影响（巨潮 403 根因是 TLS 指纹，与频率无关，见 `26091608`），但该文同时要求巨潮侧"保持低频"，所以这条属于**需要业务侧确认的放宽**，不应默默生效。

### P2-3 「站点闸门优先」缺少等待上界

§4.2 只说"详情再急也要等"，没给"等多久"。严格 `discover > content` 且无 aging 时，某站的正文可无界等待（与 P0-2 同源）。至少给一条：单站等待 > T 后提升 content 优先级（aging），或限制连续 discover 抢占次数。

### P2-4 Gate 对象生命周期没写

进程内 `dict[key] → Gate` 会随 host / 源数量无界增长（实测 2899 个 host、2900+ 个源，且源会继续新增）。文档 §2 只说"进程内单例即可"，建议补 eviction（空闲 N 分钟回收）与对应单测口径。

### P2-5 「Agent 内部翻页也必须走同一 Gate」缺落点，但其实是可行的——写清楚

实施者读到 §2 设计要点 2 会不知道改哪里。实际上注入点很明确、而且是**好消息**：

- 列表：HTTP 全在父进程内的 in-process MCP tool `crawl_tools._fetch_html`（`backend/domain/news_crawl/crawl_tools.py:248-280`），`store` 由闭包持有、每个发现任务一套（`build_crawl_server` 注释已声明"不同请求之间不会共享任何状态"），在 `_fetch_html` 上加 gate 即可；
- 正文兜底：同理 `agent_fallback.build_detail_server._fetch_html`，且它**已经**在调 `limiter.acquire(store.site_key)`（`backend/domain/news_content/agent_fallback.py:335-337`），换成 SiteGate 是同一处替换。

同时建议记一笔**前提**：Agent 的出网被 `allowed_tools` 白名单封死（`agent_runner.py:173-179` 已 disallow `Bash/WebFetch/WebSearch`）——新设计成立依赖这一点，值得写成约束而不是巧合。

### P2-6 图表与注册表口径要对齐

- §6 sequence 图是 `claim → acquire(Gate)`；但 P1-2 建议的顺序是"先拿站、再认领"，图与结论需统一。
- §3 给的 `N_d=2~4 / N_c=4~8` 与注册表已声明值（news_html discover `max_concurrency=2`、content `max_concurrency=4`，`radar_kb/registry.py:35-54`）不一致，区间上限来源未交代。建议直接引用现值并写明"是否修改注册表"。
- §9 表格"registry `max_concurrency` 仅声明 → 成为真实池容量"是对的，但要提醒：**cninfo 通道的 `max_concurrency=1` 是刻意声明**（adapter 锁串行，`registry.py:55-65` 注释已说明），别被"统一按 max_concurrency 开池"误伤。

### P2-7 建议补一节「并发下依然成立、无需改动的机制」

文档 §7 只覆盖了防重的一部分。以下在并发下**依然成立且更有价值**，写明可减少实施者误改：

- `claim_content_tasks_batch` 的 `ROW_NUMBER` 分组 + `rn,id` 交错（`repository.py:642-690`）——**并发认领时更需要它**；
- `insert_content_task_if_absent`、`upsert_news_url` 的 `url_hash` 幂等；
- `reset_stale_*` 的回收语义（但计时口径见 P1-2）；
- 执行器"禁止写库"的 Protocol 约定（`radar_kb/types.py:60-75`）——并发下这个边界更重要。

## 5. 一句话总结

模型选对了（SiteGate 收敛节奏、双池做跨站重叠、DB 管唯一性），但**站点键选错层级**（P0-1）、**硬优先默认值会把正文饿死数小时且与需求 #2 冲突**（P0-2）、**闸门冷却语义与池槽位的关系没定**（P0-3）、**cninfo 这条同步链路被整体漏掉**（P0-4）——这四条修完再写落地设计，否则接口会把错误固化成代码。
